Tool use & integrations

A model can only talk until you hand it tools: functions it may call to search, query, compute or act. This chapter covers how to design tool schemas the model picks correctly, how to run tool calls in parallel, how the Model Context Protocol (MCP) standardises the plumbing, how to run model-written code safely in a sandbox, how to wrap existing APIs, and how to format tool results so they help rather than flood the context window.

01

Tool/function schema design

A tool definition is a contract written for a reader that cannot ask follow-up questions. The model sees only the name, the description and the JSON Schema — those three fields decide whether the right tool gets called with the right arguments.

Anatomy of a tool definition

Every major API represents a tool the same way: a name, a natural-language description, and a JSON Schema for the arguments [1][2]. The model never sees your implementation. It reads these fields, which are injected into the context alongside the system prompt, and decides whether a call is warranted and what to pass. Your code executes the call and returns a result that the model reads on the next turn.

{
    "name": "orders_search",
    "description": "Search a customer's orders by status or date. Use when the user asks about an existing order. Do NOT use for refunds (see orders_refund). Returns at most 20 orders, newest first, each with order_id, status, total and placed_at.",
    "input_schema": {
      "type": "object",
      "properties": {
        "customer_id": {"type": "string", "description": "Internal id from the session; never ask the user for it."},
        "status": {"type": "string", "enum": ["pending", "shipped", "delivered", "cancelled"]},
        "placed_after": {"type": "string", "format": "date", "description": "ISO date, e.g. 2026-09-01"}
      },
      "required": ["customer_id"],
      "additionalProperties": false
    }
  }

Names and descriptions are prompt text

Anthropic's guidance on writing tools for agents boils down to treating each definition as a small prompt: say what the tool does, when to use it, when not to, and what comes back [3]. Two rules follow. Namespace related tools by service and resource (asana_search, jira_search, asana_projects_search) so the model can tell look-alikes apart [3]. And describe the boundary, not only the happy path — the line "Do NOT use for refunds" above prevents a whole class of wrong calls.

Tight schemas reduce hallucinated arguments

Loose types invite guesses. Use enum for closed sets, format hints for dates, required only for what truly is required, and additionalProperties: false so invented fields are rejected. OpenAI's function calling supports strict: true, which constrains generation to the schema [2], and Anthropic offers strict tool use as well [1]. JSON Schema is the shared vocabulary underneath both [4].

DecisionWeak versionStrong version
Namesearchorders_search
Description"Searches orders."what, when, when-not, what it returns
Status argumentfree-text stringenum of four values
Unknown fieldssilently ignoredadditionalProperties: false
Identifiersask the user for an idtake it from session context

How many tools is too many?

Selection accuracy drops as the catalogue grows and as tools overlap. Research has pushed the scale up — ToolLLM trained models on 16,000+ real-world APIs [5], and Gorilla showed that retrieving API documentation reduces hallucinated calls [6] — but production agents still do best with a small, distinct set. The Berkeley Function Calling Leaderboard is a public yardstick for how well models pick tools and fill arguments [7]. Three mitigations:

  • Consolidate. One schedule_meeting tool beats list_users + list_calendars + create_event chained by the model [3].
  • Search instead of listing. For very large catalogues, Anthropic provides a tool-search server tool so definitions load on demand [1].
  • Route. Give each sub-agent only its own domain's tools (chapter 01).
Test descriptions like prompts. A one-word change in a description can shift tool-selection accuracy. Keep definitions in version control and rerun your tool-selection evals (chapter 05) on every edit.
🎛️Layman's versionplain English, no jargon

A tool is a button the AI is allowed to press. Out of the box, an AI can only write text. Give it a "look up order" button and it can check orders; give it a "send email" button and it can email. It decides which button to press purely by reading the label on each one.

So the label does all the work. A button labelled "search" gets pressed at the wrong moments. A button labelled "look up this customer's existing orders — not for refunds — shows the 20 newest" gets pressed at the right moments, with the right details filled in.

Fewer, clearer buttons beat a wall of buttons. If two buttons do nearly the same thing, the AI will mix them up. One "book a meeting" button is better than three smaller ones it has to chain together correctly.

The TV remote analogy: a universal remote with sixty unlabelled buttons defeats even a clever person. Label each button clearly, remove the ones nobody needs, group related ones together — then anyone, or any AI, finds "volume up" on the first try.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Tool হলো এমন একটি ফাংশন যা মডেল কল করতে পারে। মডেল আপনার কোড দেখে না; সে শুধু টুলের name, description আর JSON Schema পড়ে ঠিক করে কখন কোন টুল ডাকবে এবং কী argument দেবে [1]।

ভালো টুল ডিজাইনের মূল নিয়ম:

  • নাম অর্থবহ ও namespaced রাখুন, যেমন orders_search, jira_search — যাতে কাছাকাছি দেখতে টুলগুলো আলাদা করা যায় [3]।
  • description-এ লিখুন টুলটি কী করে, কখন ব্যবহার করতে হবে, কখন করা যাবে না, আর কী ফেরত দেয়।
  • schema কড়া রাখুন: enum, required, additionalProperties: false; সম্ভব হলে strict mode চালু করুন [2]।

টুলের সংখ্যা বাড়লে ভুল টুল বাছাইয়ের সম্ভাবনাও বাড়ে। তাই কাছাকাছি কাজের টুলগুলো একত্র করুন, বড় ক্যাটালগে tool search ব্যবহার করুন, অথবা আলাদা sub-agent-এর মধ্যে টুল ভাগ করে দিন।

রিমোট কন্ট্রোলের উপমা: ষাটটি লেবেলহীন বোতামের রিমোট বুদ্ধিমান মানুষকেও বিভ্রান্ত করে। প্রতিটি বোতামে স্পষ্ট লেবেল দিন, অপ্রয়োজনীয় বোতাম সরিয়ে দিন — তখন মানুষ বা AI প্রথম চেষ্টাতেই ঠিক বোতামটি খুঁজে পায়।
02

Parallel tool calling

When a model needs several independent facts, it can request several tool calls in one turn. Running them concurrently turns the wait from the sum of the calls into roughly the slowest one.

How it works on the wire

Both major APIs let the model return more than one tool call in a single response. With OpenAI the model "may choose to call multiple functions in a single turn", and setting parallel_tool_calls to false limits it to zero or one call [2]. With Anthropic the response contains several tool_use blocks; you execute them and send every tool_result back together in the next user message, and disable_parallel_tool_use turns the behaviour off [1].

Three independent lookups. Run serially, the user waits for the sum; run in parallel, they wait for the slowest call, and all three results return to the model together.
তিনটি স্বাধীন lookup। একটার পর একটা চালালে সময় যোগ হয়; একসাথে চালালে সবচেয়ে ধীর কলটির সমান সময় লাগে।

Executing a batch safely

import asyncio
  
  async def run_tool_batch(tool_uses, registry, timeout_s=15):
      """Run every tool_use block from one model turn concurrently."""
      async def run_one(tu):
          try:
              result = await asyncio.wait_for(registry[tu.name](**tu.input), timeout_s)
              return {"type": "tool_result", "tool_use_id": tu.id, "content": str(result)}
          except Exception as exc:  # report the failure, don't crash the turn
              return {"type": "tool_result", "tool_use_id": tu.id,
                      "content": f"ERROR {type(exc).__name__}: {exc}"}
      return await asyncio.gather(*(run_one(tu) for tu in tool_uses))

Three details matter: every result keeps its tool_use_id so the model can match answers to questions; a failing call becomes an error result instead of aborting the batch; and a per-call timeout stops one slow dependency from holding the whole turn hostage.

When not to parallelise

  • Data dependencies. "Find the customer, then email them" cannot run in parallel — the second call needs the first call's output.
  • Side effects. Two concurrent issue_refund calls can pay twice. Serialise writes, or make them idempotent (chapter 09).
  • Rate limits. Ten simultaneous calls to an API that allows five per second will fail. Wrap the batch in a semaphore.

Planning for parallelism

You can push further by having the model plan every call up front and only then execute them. That is the idea behind ReWOO, which reported 5× token efficiency and a 4% accuracy gain on HotpotQA by separating reasoning from observations [8]. The trade-off is less ability to change course mid-flight.

⚡Layman's versionplain English, no jargon

Ask for several things at once when they don't depend on each other. If your assistant needs the weather, the exchange rate and a list of hotels, there's no reason to wait for the weather before asking about hotels. Send all three questions and wait only as long as the slowest answer takes.

Some things must still happen in order. You can't email someone before you've looked up their address. And you never want two "refund this customer" requests flying at the same moment — both might go through.

The food court analogy: you and two friends are hungry. Queueing at the noodle stall, then the pizza stall, then the drinks stall takes ages. Splitting up and meeting at the table takes only as long as the slowest queue. But nobody can buy dessert until you know how much money is left — that step has to wait.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

একটি turn-এ মডেল একাধিক tool call চাইতে পারে। কলগুলো যদি একে অপরের ওপর নির্ভরশীল না হয়, তবে একসাথে (concurrently) চালালে মোট সময় সব কলের যোগফল নয়, বরং সবচেয়ে ধীর কলটির সমান হয়। OpenAI-তে parallel_tool_calls এবং Anthropic-এ disable_parallel_tool_use দিয়ে এটি নিয়ন্ত্রণ করা যায় [2][1]।

নিরাপদে চালানোর নিয়ম:

  • প্রতিটি ফলাফলের সাথে তার tool_use_id রাখুন।
  • একটি কল ব্যর্থ হলে পুরো batch থামাবেন না; error-টাই ফলাফল হিসেবে ফেরত দিন।
  • নির্ভরশীল কল (আগে খোঁজা, পরে ইমেল) আর টাকা-পয়সার মতো side effect-যুক্ত কল একসাথে চালাবেন না।
  • API-এর rate limit মানতে semaphore ব্যবহার করুন।
ফুড কোর্টের উপমা: তিন বন্ধু তিনটি আলাদা দোকানের লাইনে দাঁড়ালে সবচেয়ে লম্বা লাইনের সমান সময় লাগে। কিন্তু কত টাকা বাকি আছে না জেনে ডেজার্ট কেনা যায় না — সেই কাজটির জন্য অপেক্ষা করতেই হবে।
03

Model Context Protocol (MCP)

MCP is an open protocol for connecting AI applications to tools and data. Instead of a custom integration for every pairing of app and system, each side implements MCP once.

The N×M problem

Before MCP, every AI application — an IDE, a chat app, an internal agent — needed its own connector for every system: GitHub, Postgres, Slack, the file system. Anthropic introduced MCP in November 2024 as an open standard to replace those one-off connectors [9]. An app that speaks the protocol can use any MCP server, and a server written once works in every compliant app: N + M implementations instead of N × M.

Roles and primitives

The specification defines a host (the AI application), which runs one client per connection, and servers that expose capabilities [10]. Capabilities are split by who controls them:

PrimitiveOffered byControlled byExample
Toolsserverthe model decides to callcreate_issue, run_query
Resourcesserverthe application attaches as contexta file, a table schema, a ticket
Promptsserverthe user picks a template"summarise this pull request"
Samplingclientserver asks the host's model for a completiona server that needs an LLM but has no API key
Rootsclientuser and host scope the server's reachonly ~/projects/app
Elicitationclientserver asks the user for missing input"staging or production?"

The current revision also describes optional extensions such as Tasks, for long-running asynchronous work with polling and durable handles [10].

The host runs one MCP client per server. Local servers usually run as a subprocess over stdio; remote servers use Streamable HTTP with OAuth-style authorization.
Host প্রতিটি server-এর জন্য একটি করে client চালায়। Local server সাধারণত stdio-তে আর remote server Streamable HTTP-তে যুক্ত হয়।

Transports

The specification defines two standard transports: stdio, where the host launches the server as a subprocess, and Streamable HTTP for remote servers [10]. The official Python SDK speaks both, plus the older SSE transport for compatibility with legacy servers [11].

A minimal server and client

The official Python SDK provides decorators for tools and resources and a client that can call any server [11]:

# server.py — serve with:  uv run mcp run server.py --transport streamable-http
  from mcp.server import MCPServer
  
  mcp = MCPServer("orders")
  
  @mcp.tool()
  def orders_search(customer_id: str, status: str = "any") -> list[dict]:
      """Search a customer's orders. Use for order-status questions, not refunds."""
      return orders_db.find(customer_id, status)[:20]   # orders_db: your data layer
  
  @mcp.resource("orders://{order_id}")
  def order_detail(order_id: str) -> str:
      """Full order record as text, for attaching to the context."""
      return orders_db.render(order_id)
# client.py
  import asyncio
  from mcp import Client
  
  async def main() -> None:
      async with Client("http://localhost:8000/mcp") as client:
          result = await client.call_tool("orders_search", {"customer_id": "c_42"})
          print(result.structured_content)
  
  asyncio.run(main())

Security and context cost

An MCP server is code you are trusting, and its tool descriptions are text your model will read. The project's security best-practices guide covers confused-deputy attacks, token passthrough, session hijacking and user consent [12] — read it before connecting third-party servers. Context is the other cost: dozens of servers can inject hundreds of tool definitions into every request. Anthropic and Cloudflare both describe presenting MCP tools to the model as a code API it calls from a sandbox, so only what it needs is loaded [13][14]. Reference implementations live in the official servers repository [15].

Treat third-party MCP servers like third-party packages. Pin versions, review the tools they expose, run them with least privilege, and never let a server's tool descriptions override your system prompt.
📦Layman's versionplain English, no jargon

MCP is a common plug shape for AI tools. Before it existed, every AI app had to build its own connector for every service — one for code hosting, another for the database, another for files — and every new app had to build them all again.

With MCP, each service builds one connector and every AI app can use it. A company writes an "orders" connector once, and it works in a coding assistant, a chat app and its own internal agent.

A connector can offer three kinds of things: actions the AI may take (open a ticket), reference material the app can attach (a document, a database layout), and ready-made request templates a person can pick ("review this change").

Be choosy about which connectors you install. A connector is software you're trusting with your data, just like an app on your phone.

The shipping container analogy: before standard containers, every port loaded every ship differently, and cargo was unpacked and repacked at each stop. Once everyone agreed on one box size, any crane could lift any box onto any ship, train or truck. MCP is that standard box for AI connections.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

MCP (Model Context Protocol) হলো AI অ্যাপ্লিকেশনকে টুল ও ডেটার সাথে যুক্ত করার একটি open protocol। আগে প্রতিটি অ্যাপ ও প্রতিটি সিস্টেমের জন্য আলাদা connector লিখতে হতো (N × M); MCP-তে প্রতিটি পক্ষ একবার protocol বাস্তবায়ন করলেই চলে (N + M) [9]।

মূল ভূমিকা: host (AI অ্যাপ), প্রতিটি সংযোগে একটি client, আর ক্ষমতা প্রকাশকারী server [10]।

  • Server দেয়: tools (মডেল কল করে), resources (অ্যাপ context হিসেবে যোগ করে), prompts (ব্যবহারকারী template বাছাই করে)।
  • Client দেয়: sampling, roots ও elicitation।
  • Transport: local-এর জন্য stdio, remote-এর জন্য Streamable HTTP।

নিরাপত্তা: third-party server-কে third-party package-এর মতোই সতর্কভাবে দেখুন — version pin করুন, ন্যূনতম অনুমতি দিন, আর security best practices পড়ুন [12]। অনেক server যুক্ত করলে tool definition দিয়েই context ভরে যায়; তাই টুলগুলোকে code API হিসেবে দিয়ে প্রয়োজনমতো লোড করার কৌশল ব্যবহার করা হয় [13]।

শিপিং কন্টেইনারের উপমা: standard কন্টেইনার আসার আগে প্রতিটি বন্দরে মাল আলাদা নিয়মে তোলা-নামানো হতো। সবাই এক মাপের বাক্সে একমত হওয়ার পর যেকোনো ক্রেন যেকোনো জাহাজ, ট্রেন বা ট্রাকে বাক্স তুলতে পারে। AI সংযোগের জন্য MCP হলো সেই standard বাক্স।
04

Sandboxed code execution

Letting the model write and run code replaces dozens of narrow tools with one general one — and turns your infrastructure into something a prompt can program. Isolation is not optional.

Why code is a good action format

CodeAct proposed that agents act by writing executable Python instead of emitting JSON tool calls; across 17 LLMs it reported up to 20% higher success rates than the usual alternatives [16]. Code composes naturally (loops, conditionals, variables), does arithmetic exactly, and lets one action do the work of many tool calls. "Average order value per country for the last 30 days" is one pandas expression rather than a chain of query, filter, group and average tools.

Isolation layers

Model-written code is untrusted code. The common isolation technologies, from weakest to strongest:

LayerWhat isolates itTypical use
Process + seccompsyscall filtering on a shared kernelquick local experiments only
Containernamespaces and cgroups, shared kerneldev environments with extra hardening
gVisora user-space kernel that intercepts syscalls [17]multi-tenant containers
Firecracker microVMa lightweight VM with its own kernel [18]per-task sandboxes at scale

Hosted sandboxes package this up so you don't operate it yourself: E2B [19], Modal Sandboxes [20], Daytona [21] and Cloudflare Sandboxes [22] each give an agent an isolated environment for commands and code, with different trade-offs in start-up time, GPU access and persistence.

# E2B: create an isolated sandbox, run a command, read the output.
  from e2b import Sandbox
  
  sandbox = Sandbox.create()          # needs the E2B_API_KEY environment variable
  result = sandbox.commands.run("python3 -c 'print(sum(range(10)))'")
  print(result.stdout)                # 45

The hardening checklist

  • No secrets inside. Pass short-lived, narrowly scoped credentials only when a task needs them.
  • Egress allowlist. Default-deny outbound network; open only the hosts a task requires.
  • Resource limits. CPU, memory, disk and a wall-clock timeout per execution.
  • Ephemeral by default. A fresh sandbox per task or session; nothing persists unless you copy it out.
  • Cap the output. Truncate stdout before it reaches the model (see the last section of this chapter).
A sandbox with internet access and private data is an exfiltration channel. Simon Willison's "lethal trifecta" — private data, untrusted content, and the ability to communicate externally — is exactly the combination a code-running agent can assemble [23]. Remove at least one leg.

Code mode for tool-heavy agents

The same idea now tames large tool catalogues: present tools to the model as a typed code API and let it write a short script that calls them inside the sandbox. Anthropic describes this as a way to cut the tokens spent loading tool definitions and passing intermediate results through the model [13], and Cloudflare calls the same pattern "Code Mode" [14].

🧪Layman's versionplain English, no jargon

Sometimes the easiest way for an AI to answer is to write a tiny program and run it. "What's the average order size per country?" is one line of code, instead of a long back-and-forth of separate lookups.

But you never let a stranger's program run loose on your real computer. So the program runs in a sealed box: it can calculate, but it can't see your files, can't reach the internet unless you allow one specific address, can't run forever, and the box is thrown away afterwards.

The danger to watch: a box that can see private data and can also send messages to the outside world can be tricked into leaking that data. Take away one of those two powers.

The fume cupboard analogy: chemists do risky experiments inside a glass cabinet with its own air extraction. They can mix and heat whatever they need, but the fumes never reach the rest of the lab — and the cabinet is wiped clean before the next experiment.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

মডেলকে কোড লিখে চালাতে দিলে অনেকগুলো সরু টুলের বদলে একটি সাধারণ টুলেই কাজ হয়। CodeAct গবেষণায় JSON tool call-এর বদলে Python কোডকে action হিসেবে ব্যবহার করে ১৭টি মডেলে সর্বোচ্চ ২০% বেশি সাফল্য দেখা গেছে [16]।

কিন্তু মডেলের লেখা কোড অবিশ্বস্ত। তাই isolation দরকার: container, gVisor বা Firecracker microVM [17][18]। E2B, Modal, Daytona বা Cloudflare Sandboxes-এর মতো hosted sandbox এগুলো তৈরি অবস্থায় দেয় [19]।

নিরাপত্তা চেকলিস্ট:

  • sandbox-এর ভেতরে কোনো secret রাখবেন না।
  • বাইরের নেটওয়ার্ক ডিফল্টে বন্ধ রাখুন; শুধু প্রয়োজনীয় host allowlist করুন।
  • CPU, memory ও সময়ের সীমা দিন; প্রতিটি কাজ শেষে sandbox মুছে ফেলুন।
  • private data, অবিশ্বস্ত content আর বাইরে যোগাযোগের ক্ষমতা — এই তিনটি একসাথে থাকলে ডেটা পাচারের পথ খুলে যায় [23]।
ফিউম কাবার্ডের উপমা: রসায়নবিদ ঝুঁকিপূর্ণ পরীক্ষা কাঁচের বাক্সের ভেতরে করেন, যার নিজস্ব বাতাস বের করার ব্যবস্থা আছে। ভেতরে যা খুশি মেশানো যায়, কিন্তু ধোঁয়া বাকি ল্যাবে পৌঁছায় না, আর পরের পরীক্ষার আগে বাক্সটি পরিষ্কার করা হয়।
05

API wrappers as tools

Most tools are thin wrappers around APIs you already have. The wrapper translates between what an agent needs — intent-level actions, clear errors, safe defaults — and what the API offers.

Wrap intents, not endpoints

Mirroring a REST API one endpoint per tool hands the model a pile of low-level steps to chain correctly. Anthropic's tool-writing guidance recommends consolidating multi-step workflows into single tools — one scheduling tool that finds availability and books, rather than separate list and create calls [3]. Fewer, higher-level tools mean fewer chances to call them in the wrong order.

Errors the model can act on

An agent can recover from an error only if the error says what to do. RFC 9457, "Problem Details for HTTP APIs", is a good template for the envelope [24]; add a retryable flag so both the orchestrator and the model know whether another attempt makes sense. Return the error as the tool result rather than raising it — the model reads it and adapts [1].

import httpx
  from pydantic import BaseModel, Field
  
  billing = httpx.AsyncClient(base_url="https://billing.internal", timeout=10)
  
  class RefundInput(BaseModel):
      order_id: str = Field(pattern=r"^ord_[a-z0-9]{8}$")
      amount_cents: int = Field(gt=0, le=50_000)      # policy cap enforced in code
      reason: str = Field(max_length=200)
  
  async def orders_refund(args: dict, user) -> dict:
      data = RefundInput(**args)                      # re-validate server-side
      try:
          r = await billing.post(
              "/refunds", json=data.model_dump(),
              headers={"Idempotency-Key": f"refund:{data.order_id}",
                       "Authorization": f"Bearer {user.token_for('refunds:write')}"})
          r.raise_for_status()
          return {"ok": True, "refund_id": r.json()["id"]}
      except httpx.HTTPStatusError as e:
          return {"ok": False, "status": e.response.status_code,
                  "detail": e.response.json().get("detail", "refund failed"),
                  "retryable": e.response.status_code in (429, 502, 503)}

Credentials stay outside the model

The model should never see API keys or tokens. The wrapper attaches a credential scoped to the current user and to the minimum permission for that tool (refunds:write, not admin). A prompt-injected model cannot leak a key it never had.

Pagination and limits

Return a bounded page plus a cursor, not everything. Cursor-based pagination, as in Stripe's API, stays stable while data changes underneath [25]. Put the page size and "how to get more" in the tool description so the model can plan.

Classify side effects

Tag each wrapped tool as read-only, write, money-moving or destructive. The tag drives everything downstream: whether calls may run in parallel, whether they need an idempotency key, and whether a human must approve them (approval checkpoints are covered in chapter 01).

Most AI "tools" are a friendly front desk for systems a company already has. The billing system, the order database and the ticket system each have complicated controls. The wrapper turns them into simple requests the AI can make — "refund this order" rather than "open the ledger, find the line, reverse it, notify finance".

The front desk also holds the keys. The AI never sees passwords; the desk uses a key that only allows that one job for that one customer.

When something goes wrong, the desk explains it plainly — "too many requests, try again in 30 seconds" or "this order was already refunded" — so the AI can decide what to do next instead of guessing.

The hotel concierge analogy: you ask the concierge for a dinner table at eight. They phone the restaurant, use the hotel's account, and come back with "booked" or "full, but nine is free". You never get the keys to the restaurant or the hotel's card — just a clear answer you can act on.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

বেশিরভাগ টুল আসলে আপনার বিদ্যমান API-এর ওপর একটি পাতলা wrapper। এর কাজ হলো agent-এর প্রয়োজন (উদ্দেশ্যভিত্তিক action, স্পষ্ট error, নিরাপদ default) আর API-এর ক্ষমতার মধ্যে অনুবাদ করা।

মূল নীতি:

  • প্রতিটি endpoint-এর জন্য আলাদা টুল না বানিয়ে উদ্দেশ্য অনুযায়ী টুল দিন, যেমন একটি "meeting বুক করো" টুল [3]।
  • error এমনভাবে ফেরত দিন যাতে মডেল বোঝে কী হয়েছে এবং আবার চেষ্টা (retryable) করা উচিত কি না; RFC 9457 একটি ভালো কাঠামো [24]।
  • API key বা token কখনো মডেলকে দেখাবেন না; wrapper ব্যবহারকারীর জন্য ন্যূনতম অনুমতির token যোগ করবে।
  • সব ডেটা একবারে না দিয়ে cursor-সহ সীমিত page ফেরত দিন [25]।
  • প্রতিটি টুলকে read-only, write, টাকা-সংক্রান্ত বা destructive হিসেবে চিহ্নিত করুন; এর ওপরই নির্ভর করে parallel চালানো যাবে কি না এবং মানুষের অনুমোদন লাগবে কি না।
হোটেল কনসিয়ার্জের উপমা: আপনি কনসিয়ার্জকে রাত আটটায় ডিনার টেবিল বুক করতে বলেন। তিনি রেস্টুরেন্টে ফোন করেন, হোটেলের অ্যাকাউন্ট ব্যবহার করেন, আর ফিরে এসে বলেন "বুক হয়েছে" বা "আটটায় নেই, নয়টায় আছে"। রেস্টুরেন্টের চাবি বা হোটেলের কার্ড আপনার হাতে কখনো আসে না।
06

Tool result formatting for LLM consumption

Whatever a tool returns is pasted into the model's context and re-read on every later turn. A good result is short, high-signal, and written for a reader that thinks in language, not database ids.

Results are context, and context is finite

Anthropic's context-engineering guidance treats the context window as a scarce budget: low-value tool output dilutes the model's attention and is paid for again on every subsequent turn [26]. Claude Code, for example, caps tool responses at 25,000 tokens by default [3].

Make results readable for the model

  • Resolve ids to meaning. Anthropic reports that replacing opaque UUIDs with semantically meaningful names — or even a simple 0-based index — noticeably improves how precisely agents refer to items [3].
  • Offer a verbosity switch. A response_format parameter with concise and detailed values lets the agent ask for detail only when it needs it [3].
  • Lead with the answer. Put the summary line first ("3 open orders; 1 delayed"), details after.
  • Prefer compact text to raw JSON for reasoning steps; keep JSON when the next step is code.
orders_search → format=concise
  3 open orders for Rahim Uddin (customer since 2021):
  1. #A-1042  shipped   ৳4,200   placed 28 Sep   on time
  2. #A-1057  pending   ৳1,150   placed 03 Oct   payment awaiting confirmation
  3. #A-1061  delayed   ৳9,800   placed 05 Oct   carrier exception, ETA +3 days
  (showing 3 of 3 · ask for format=detailed to include line items)

Truncate with directions

When you must cut, cut at a record boundary and tell the model how to get the rest: "showing 20 of 312 — filter by status or pass the returned cursor". Silent truncation makes the model believe a partial list is complete.

Errors that teach

"Error 400" teaches nothing. "date must be YYYY-MM-DD; you sent 10/05/26" lets the model fix its own call on the next turn.

Tool output is untrusted input

A web page, email or document returned by a tool may contain text written to manipulate the model. Indirect prompt injection works precisely by planting instructions in data the model will read [27]. Label tool output as data, never as instructions, and keep the defences from chapter 07 in place.

A few recordsnumbered list or small table, summary first
Many recordstop N, counts, and how to page
One long documentthe relevant excerpt plus where it came from

Whatever a tool sends back, the AI has to read — and keeps re-reading for the rest of the conversation. Dumping a thousand rows of raw data is like handing someone the whole filing cabinet when they asked one question.

Good results are short and lead with the answer: "3 open orders, 1 is delayed" first, details after. Use names people recognise, not long code numbers. If a list was cut off, say so and say how to see more.

And treat anything that comes back from the outside world with suspicion. A web page or email can hide sneaky instructions aimed at the AI.

The cockpit dashboard analogy: during landing a pilot doesn't read every raw sensor value. The instruments show a handful of clear gauges, warnings in plain words, and a light when something needs attention. Tool results should be designed like that dashboard, not like the sensor log.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

টুল যা ফেরত দেয় তা মডেলের context-এ বসে যায় এবং পরের প্রতিটি turn-এ আবার পড়া হয় — তাই প্রতিটি অপ্রয়োজনীয় token খরচ ও মনোযোগ দুটোই নষ্ট করে [26]।

ভালো ফলাফলের নিয়ম:

  • আগে সারাংশ, তারপর বিস্তারিত।
  • অর্থহীন UUID-এর বদলে মানুষের বোঝার মতো নাম বা ছোট index দিন [3]।
  • response_format দিয়ে concise বা detailed বেছে নেওয়ার সুযোগ রাখুন।
  • কাটতে হলে record-এর সীমানায় কাটুন এবং বলে দিন বাকিটা কীভাবে পাওয়া যাবে।
  • error বার্তায় সমাধান বলুন, যেমন "তারিখ YYYY-MM-DD আকারে দিন"।

সতর্কতা: ওয়েব পেজ, ইমেল বা ডকুমেন্টে মডেলকে বিভ্রান্ত করার নির্দেশ লুকানো থাকতে পারে (indirect prompt injection) [27]। টুলের output-কে সবসময় ডেটা হিসেবে ধরুন, নির্দেশ হিসেবে নয়।

ককপিট ড্যাশবোর্ডের উপমা: অবতরণের সময় পাইলট প্রতিটি sensor-এর কাঁচা রিডিং পড়েন না; কয়েকটি স্পষ্ট মিটার আর সহজ ভাষার সতর্কবার্তা দেখেন। টুলের ফলাফলও সেই ড্যাশবোর্ডের মতো হওয়া উচিত, sensor log-এর মতো নয়।
