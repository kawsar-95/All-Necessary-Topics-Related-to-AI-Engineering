01

Offline evals: golden datasets, regression tests

A golden dataset is a versioned set of inputs with known-good expectations. Run it on every change to prompts, models, tools or retrieval, and block releases that regress.

What goes into a golden set

  • Real traffic first. Sample production inputs (with consent and redaction) across your main use cases; synthetic data fills the gaps later.
  • Expectations, not just answers. Each case states what "correct" means: an exact value, required facts, forbidden content, a rubric, or a check on the final state.
  • Coverage tags. Label cases by intent, difficulty, language and risk so you can see *where* a change helps or hurts.
  • Known failures. Every bug found in production joins the set (chapter 04's feedback loop).

Start small — 50 to 200 well-chosen cases beat 5,000 unexamined ones — and grow from real failures. Hamel Husain's essay argues that most of the value comes from this unglamorous loop of looking at data and writing targeted tests [1].

Many metrics, not one

HELM argued for evaluating models on many scenarios with several metrics each — accuracy, calibration, robustness, fairness, efficiency — because a single number hides trade-offs [2]. The same holds for your product: track task success alongside cost, latency, refusal rate and safety checks.

An offline eval as a release gate: every change to prompt, model, tools or retrieval runs the golden set, and ships only if the overall pass rate holds and no category regresses.
Release gate হিসেবে offline eval: prompt, মডেল, টুল বা retrieval-এর প্রতিটি পরিবর্তনে golden set চলে; সামগ্রিক pass rate ঠিক থাকলে এবং কোনো বিভাগ খারাপ না হলেই ship হয়।

Regression tests in CI

# tests/test_support_golden.py — runs in CI on every prompt/model/tool change
  import json
  import pytest
  from app.agent import answer
  from evals.checks import contains_all, no_pii, judge_passes
  
  CASES = [json.loads(line) for line in open("evals/support_golden.jsonl")]
  
  @pytest.mark.parametrize("case", CASES, ids=[c["id"] for c in CASES])
  def test_golden(case):
      out = answer(case["input"], user=case["user"])
      assert contains_all(out.text, case["must_include"])
      assert no_pii(out.text)
      if case.get("rubric"):
          assert judge_passes(case["input"], out.text, case["rubric"])

Treat the suite like any test suite: deterministic checks wherever possible, judge-based checks only where needed, and a pass-rate threshold (with per-category minimums) as the release gate.

Check typeExampleCostReliability

Variance is real. LLM outputs vary from run to run. Run flaky cases several times, report pass rates with confidence intervals on small sets, and don't celebrate a one-point move on fifty cases.
✅Layman's versionplain English, no jargon

A golden dataset is your AI's standing checklist. It's a fixed set of real situations, each with a clear note of what a good response must include and must never include. Every time anyone changes the instructions, the model or the tools, the AI is run through the whole list again.

If results get worse, the change doesn't ship. And every real mistake customers report becomes a new item on the list, so it gets better at catching problems over time.

Small and well-chosen beats huge and unexamined: a hundred carefully picked situations are worth more than thousands nobody has looked at.

The pre-flight checklist analogy: before every flight, pilots run the same checklist, however experienced they are and however small the change to the aircraft. One missed item and the plane stays on the ground. When an incident reveals a new risk, a line is added to the checklist for every future flight.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Golden dataset হলো বাস্তব input ও প্রত্যাশিত আচরণের একটি version-যুক্ত সংগ্রহ। প্রতিবার prompt, মডেল, টুল বা retrieval বদলালে এটি চালান; মান কমলে release বন্ধ।

  • আগে বাস্তব traffic থেকে নমুনা নিন, পরে synthetic দিয়ে ফাঁক পূরণ করুন।
  • প্রতিটি case-এ "সঠিক" মানে কী তা লিখুন: নির্দিষ্ট মান, আবশ্যিক তথ্য, নিষিদ্ধ বিষয়, rubric বা চূড়ান্ত state।
  • উদ্দেশ্য, কাঠিন্য, ভাষা ও ঝুঁকি অনুযায়ী tag দিন।
  • ছোট থেকে শুরু করুন (৫০–২০০টি ভালোভাবে বাছাই করা case), বাস্তব ব্যর্থতা দিয়ে বাড়ান [1]।

একটি সংখ্যা নয়, কয়েকটি মেট্রিক দেখুন — নির্ভুলতার পাশাপাশি খরচ, latency, প্রত্যাখ্যানের হার ও নিরাপত্তা [2]। LLM-এর output প্রতিবার একটু ভিন্ন হয়, তাই অস্থির case কয়েকবার চালান এবং ছোট dataset-এ এক পয়েন্টের পরিবর্তনকে বড় করে দেখবেন না।

উড্ডয়নের আগের চেকলিস্টের উপমা: অভিজ্ঞতা যত বেশিই হোক, প্রতিটি ফ্লাইটের আগে পাইলট একই চেকলিস্ট মেলান; একটি ঘর বাদ গেলে বিমান ওড়ে না। কোনো ঘটনায় নতুন ঝুঁকি ধরা পড়লে ভবিষ্যতের সব ফ্লাইটের চেকলিস্টে নতুন লাইন যোগ হয়।
02

LLM-as-judge: pairwise comparison, rubric-based scoring

Many qualities — helpfulness, tone, adherence to a policy — can't be checked with a regex. A strong model can grade them, but only if you design against its known biases and check it against human labels.

It works — with caveats

The MT-Bench study found that strong LLM judges such as GPT-4 matched both controlled and crowdsourced human preferences with over 80% agreement, the same level of agreement humans reach with each other [3]. The same paper documents the biases to design against: position bias (favouring one answer slot), verbosity bias (favouring longer answers) and self-enhancement bias (favouring its own outputs) [3]. Wang et al. showed that simply swapping the order of two candidates can flip a judge's verdict [4].

Pairwise versus rubric scoring

ModeHow it worksStrengthWeakness
Pairwise"Which answer is better, A or B?"relative judgements are easier and more consistentneeds two candidates; grows quadratically with variants
Rubric (pointwise)score 1–5 on defined criteria, with reasonsabsolute tracking over timescores drift; scales are fuzzy
Reference-basedcompare against a gold answergrounded and stableneeds a gold answer for every case

G-Eval showed that asking the judge to reason through the evaluation criteria before filling in a score improves agreement with people — a Spearman correlation of 0.514 with human ratings on summarisation, using GPT-4 as the backbone [5].

A debiased pairwise judge

JUDGE = """You are grading two answers to the same customer question.
  Criteria: correct per the policy excerpt, complete, concise, polite.
  Reason through each criterion, then output exactly one of: A, B, TIE.
  
  Question: {q}
  Policy excerpt: {policy}
  Answer A: {a}
  Answer B: {b}"""
  
  def pairwise(q, policy, x, y, judge):
      first = judge(JUDGE.format(q=q, policy=policy, a=x, b=y))    # x shown first
      second = judge(JUDGE.format(q=q, policy=policy, a=y, b=x))   # order swapped
      if first == "A" and second == "B":
          return "x"
      if first == "B" and second == "A":
          return "y"
      return "tie"          # verdict flipped with order: not a confident win

Calibrate against people — and keep calibrating

Before trusting a judge, have people label a sample and measure agreement with the judge (raw agreement plus Cohen's kappa). Shankar et al. found that evaluation criteria themselves drift as people grade more outputs — you discover what you care about by looking — so judge prompts and human labels need to evolve together [6]. A panel of several smaller, diverse judge models can also be cheaper and less biased than one large judge [7]. Public human-preference leaderboards such as Chatbot Arena apply the same pairwise idea at scale [8].

Don't let a model grade itself. Use a different model family as the judge where you can, and never judge with the exact prompt being evaluated.
⚖️Layman's versionplain English, no jargon

Some answers can't be marked by a simple rule. Is this reply polite? Did it follow the policy? Is it actually helpful? For those, you can ask a second, strong AI to act as the marker.

AI markers have known quirks: they tend to prefer whichever answer they read first, prefer longer answers, and go easy on answers that sound like their own writing. Good setups show the two answers in both orders, ask for reasons before the verdict, and compare the marker's decisions with real people's on a sample.

Only once the AI marker agrees with people often enough do you let it mark at scale — and you keep spot-checking it.

The figure skating panel analogy: skating competitions use several judges, a written scoring guide and rules that cancel out individual bias — extreme marks can be dropped, and a judge who keeps favouring one country gets reviewed. An AI judge needs the same safeguards.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

LLM-as-judge: যেসব গুণ regex দিয়ে মাপা যায় না (সহায়কতা, ভদ্রতা, policy মানা), সেগুলো একটি শক্তিশালী মডেল দিয়ে মূল্যায়ন করানো।

MT-Bench গবেষণায় শক্তিশালী LLM judge মানুষের পছন্দের সাথে ৮০%-এর বেশি মিলেছে — মানুষে-মানুষে মিলের সমান [3]। কিন্তু পক্ষপাত আছে: নির্দিষ্ট অবস্থানের উত্তরকে প্রাধান্য (position bias), লম্বা উত্তরকে প্রাধান্য (verbosity bias), আর নিজের লেখার মতো উত্তরকে প্রাধান্য (self-enhancement) [3][4]।

  • Pairwise: "A না B, কোনটি ভালো?" — দুই ক্রমে দেখিয়ে মিলিয়ে নিন।
  • Rubric: নির্দিষ্ট মানদণ্ডে ১–৫ স্কোর, আগে কারণ লিখিয়ে নিন; এতে মানুষের সাথে মিল বাড়ে [5]।
  • মানুষের label-এর সাথে মিল (agreement, Cohen's kappa) মেপে তবেই বিশ্বাস করুন; মানদণ্ডও সময়ের সাথে বদলায় [6]।
  • কয়েকটি ছোট ও বৈচিত্র্যময় মডেলের প্যানেল একটি বড় judge-এর চেয়ে সস্তা ও কম পক্ষপাতদুষ্ট হতে পারে [7]।
ফিগার স্কেটিং বিচারক প্যানেলের উপমা: স্কেটিং প্রতিযোগিতায় কয়েকজন বিচারক, লিখিত নম্বর-নির্দেশিকা আর পক্ষপাত কাটানোর নিয়ম থাকে — চরম নম্বর বাদ দেওয়া যায়, আর যে বিচারক বারবার একটি দেশকে বেশি নম্বর দেন, তাঁকে পর্যালোচনা করা হয়। AI judge-এরও একই রকম সুরক্ষা দরকার।

RAG metrics: faithfulness, answer relevance, context precision/recall (Ragas)

A RAG answer can fail in the retriever (wrong or missing context) or in the generator (ignoring or contradicting the context). Separate metrics for each stage tell you which half to fix.

The core metrics

Ragas popularised a set of largely reference-free metrics for RAG pipelines [9]; its documentation describes the current implementations and variants [10].

MetricQuestion it answersStage it diagnosesNeeds a reference answer?
Faithfulnessare the answer's claims supported by the retrieved context?generationno
Answer relevancedoes the answer address the question asked?generationno
Context precisionare the retrieved chunks mostly relevant, and ranked high?retrieval rankingsometimes
Context recallwas everything needed to answer actually retrieved?retrieval coverageyes
The three edges of a RAG answer. Retrieval metrics judge the question–context edge, faithfulness judges the context–answer edge, and answer relevance closes the loop back to the question.
RAG উত্তরের তিনটি সংযোগ: প্রশ্ন–context সংযোগ মাপে retrieval মেট্রিক, context–উত্তর সংযোগ মাপে faithfulness, আর উত্তর–প্রশ্ন সংযোগ মাপে answer relevance।

How they are computed

Faithfulness is typically computed by splitting the answer into individual claims and asking a judge model whether each one is supported by the context; the score is the supported fraction. Answer relevance can be estimated by generating questions from the answer and comparing them with the original question. ARES takes a different route: it fine-tunes lightweight judges on synthetic data and uses a small set of human labels with prediction-powered inference to put confidence intervals around the scores [11].

Add classic retrieval metrics

LLM-based metrics are slower and noisier than counting. Where you have labelled relevant documents per query, also track recall@k, MRR and nDCG for the retriever on its own — cheap, deterministic, and ideal for tuning chunking and reranking (see the RAG guide in this series).

High faithfulness doesn't mean a correct answer. An answer can faithfully repeat a wrong or outdated chunk. Pair faithfulness with context recall and with spot checks against ground truth.
📰Layman's versionplain English, no jargon

An AI that answers from documents can go wrong in two places. It might fetch the wrong pages, or it might fetch the right pages and then ignore or twist them.

So you check each step separately. Did it pull the right pages, and all the ones it needed? Does every claim in the answer actually appear in those pages? And did it answer the question that was actually asked?

Knowing which step failed tells you what to fix: the searching, or the writing.

The newspaper fact-checker analogy: a fact-checker asks whether the reporter gathered the right sources, whether every sentence in the article is backed by those sources, and whether the piece answers the editor's actual question. A beautifully written story built on the wrong sources still fails.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

RAG উত্তর দুই জায়গায় ব্যর্থ হতে পারে: retriever ভুল বা অসম্পূর্ণ context আনতে পারে, অথবা generator context উপেক্ষা বা বিকৃত করতে পারে। Ragas-এর মেট্রিকগুলো প্রতিটি ধাপ আলাদা করে মাপে [9]:

  • Faithfulness: উত্তরের প্রতিটি দাবি কি আনা context-এ আছে?
  • Answer relevance: উত্তর কি আসল প্রশ্নের জবাব দিচ্ছে?
  • Context precision: আনা অংশগুলো কি বেশিরভাগই প্রাসঙ্গিক এবং উপরের দিকে আছে?
  • Context recall: উত্তরের জন্য দরকারি সব তথ্য কি আনা হয়েছে?

ARES হালকা judge মডেল ও অল্প মানুষের label দিয়ে স্কোরের confidence interval দেয় [11]। পাশাপাশি recall@k, MRR, nDCG-এর মতো সস্তা retrieval মেট্রিকও রাখুন। মনে রাখবেন, উচ্চ faithfulness মানেই সঠিক উত্তর নয় — উত্তর ভুল বা পুরোনো তথ্যও বিশ্বস্তভাবে পুনরাবৃত্তি করতে পারে।

সংবাদপত্রের তথ্য-যাচাইকারীর উপমা: তথ্য-যাচাইকারী দেখেন সাংবাদিক ঠিক সূত্র জোগাড় করেছেন কি না, প্রতিবেদনের প্রতিটি বাক্য সেই সূত্রে আছে কি না, আর সম্পাদকের আসল প্রশ্নের উত্তর দেওয়া হয়েছে কি না। ভুল সূত্রের ওপর লেখা সুন্দর প্রতিবেদনও ব্যর্থ।
04

Agent evals: task success rate, trajectory analysis, tool-call accuracy

An agent's final answer can be right for the wrong reasons, or wrong after mostly good steps. Evaluate the outcome, the path and each tool call — and run tasks several times, because reliability matters as much as capability.

Outcome: did the task succeed?

The most robust check compares the end state, not the transcript: was the right database row changed, was the correct booking made, do the tests pass? τ-bench evaluates agents this way in simulated retail and airline domains, comparing the final database state with the goal [12]; SWE-bench checks whether a generated patch makes the repository's tests pass [13].

Reliability: pass^k, not just pass@1

τ-bench introduced pass^k — the probability that an agent succeeds on all k independent trials of the same task. Even strong function-calling agents such as gpt-4o succeeded on under 50% of tasks, and pass^8 fell below 25% in the retail domain [12]. For a customer-facing agent, inconsistency is a failure in itself.

def pass_hat_k(results_per_task: dict[str, list[bool]], k: int) -> float:
      """Share of tasks where the agent succeeded on every one of k trials."""
      tasks = [runs[:k] for runs in results_per_task.values() if len(runs) >= k]
      return sum(all(runs) for runs in tasks) / len(tasks)

Trajectory and tool calls

What to checkExample assertion
Tool selectionused orders_search before orders_refund
Argument correctnessrefund amount equals the order total, never more
No forbidden actionsnever called account_delete
Efficiencyfinished within 8 steps; no repeated identical calls
Recoveryafter a 429 error, waited and retried instead of giving up
Policyasked for confirmation before any write above a threshold

The Berkeley Function Calling Leaderboard measures single-call accuracy — choosing the right function and filling its arguments correctly — and is a useful reference point for tool-call accuracy [14].

Public benchmarks as context, not targets

AgentBench evaluates models as agents across several interactive environments [15], GAIA poses general-assistant questions that are simple for people but hard for models [16], WebArena uses realistic self-hosted websites [17], and OSWorld uses real computer environments [18]. They help with model selection; only your own task suite tells you whether *your* agent works.

Grade trajectories with code first. Most trajectory checks are simple assertions over the trace (chapter 04). Save LLM judges for genuine judgement calls such as "was the clarifying question reasonable?".
🚗Layman's versionplain English, no jargon

Testing an AI agent is like testing a driver, not a calculator. You check that it actually reached the destination — the order was really refunded, the meeting really booked — not just that it said so.

You also watch how it got there: did it use the right tools in a sensible order, avoid anything forbidden, ask permission before big actions, and recover when something went wrong?

And you run each task several times. An agent that succeeds two times out of three isn't ready to deal with customers.

The driving test analogy: the examiner cares that you reach the end of the route, but also whether you checked mirrors, signalled, kept to the speed limit and handled the unexpected cyclist. Passing once by luck isn't enough — a licence means you can do it reliably.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Agent-এর চূড়ান্ত উত্তর ভুল কারণে সঠিক হতে পারে, আবার ভালো ধাপের পরেও ভুল হতে পারে। তাই তিনটি স্তরে মূল্যায়ন করুন:

  • Outcome: transcript নয়, চূড়ান্ত state মিলিয়ে দেখুন — ঠিক row বদলেছে কি না, test পাস করে কি না [12][13]।
  • Reliability: τ-bench-এর pass^k — একই কাজ k বার চালালে সবকটিতে সফল হওয়ার সম্ভাবনা। gpt-4o-এর মতো শক্তিশালী agent-ও ৫০%-এর কম কাজে সফল হয়েছে, আর retail-এ pass^8 ছিল ২৫%-এর নিচে [12]।
  • Trajectory ও tool call: ঠিক টুল, ঠিক argument, কোনো নিষিদ্ধ কাজ নয়, অপ্রয়োজনীয় পুনরাবৃত্তি নয়, ব্যর্থতার পর সামলে ওঠা; single-call নির্ভুলতার জন্য BFCL একটি ভালো মানদণ্ড [14]।

AgentBench, GAIA, WebArena, OSWorld-এর মতো public benchmark মডেল বাছাইয়ে সাহায্য করে; কিন্তু আপনার agent কাজ করে কি না, তা বলে শুধু আপনার নিজের task suite।

ড্রাইভিং পরীক্ষার উপমা: পরীক্ষক দেখেন আপনি গন্তব্যে পৌঁছালেন কি না, সাথে আয়না দেখলেন কি না, সংকেত দিলেন কি না, গতিসীমা মানলেন কি না। একবার ভাগ্যক্রমে পাস করা যথেষ্ট নয় — লাইসেন্স মানে নির্ভরযোগ্যভাবে পারা।
05

Synthetic data generation for evals

When real examples are scarce — a new feature, rare edge cases, adversarial inputs — a model can generate test cases. Synthetic data scales coverage, but only human review and contamination checks keep it honest.

Generate from your own material

Self-Instruct showed that a model can bootstrap large instruction datasets from a small seed set, with filtering to remove low-quality and near-duplicate items [19]. For evals, the most useful variant is grounded generation: give the generator your documents, policies or API specs, and ask for questions whose answers can be verified in that material.

GEN = """From the policy excerpt below, write {n} realistic customer questions.
  Vary persona (new vs long-time customer), tone (calm vs angry),
  language (English, Bangla, mixed) and difficulty (direct lookup vs multi-step).
  For each, give the correct answer and the exact sentence that supports it.
  Return JSON lines: {{"question", "answer", "evidence", "persona", "difficulty"}}.
  
  Policy excerpt:
  {chunk}"""

Make it diverse on purpose

Left alone, generators produce bland, repetitive, easy cases. Steer diversity explicitly along axes — persona, intent, difficulty, language, length, adversarial style — and deduplicate by embedding similarity before keeping anything.

Keep people in the loop

Synthetic cases need review: generated "correct answers" are sometimes wrong, and generated questions drift away from what real users ask. A practical rule is to review everything that will enter the release-gating set and sample-review the rest.

Watch for contamination

If test items — or close paraphrases — appeared in a model's training data, scores measure memorisation rather than capability. Golchin and Surdeanu showed that contamination can be detected by prompting a model to complete partial test instances and comparing its completions with the originals [20]. Practical defences: build eval sets from private, recent material; keep a held-out human-written set that is never published; and be sceptical when a new model scores suspiciously well on an old public benchmark.

Use synthetic data forDon't rely on it for
coverage of rare intents and edge casesthe final verdict on real-user quality
adversarial and red-team inputscalibrating your LLM judge
multilingual variants of known casesreplacing production samples
load and latency testsmeasuring user satisfaction
🛩️Layman's versionplain English, no jargon

When you don't have enough real examples to test with, you can ask an AI to write practice questions — based on your own documents, so the right answers can be checked.

The trick is variety: questions from new and old customers, calm and angry, in English and Bangla, easy and tricky. Otherwise the AI writes a hundred versions of the same easy question.

People still review them, because generated "correct answers" are sometimes wrong — and you keep some questions completely private, so no model could have seen them in advance.

The flight simulator analogy: pilots practise engine failures and storms in a simulator because waiting for real emergencies would be absurd. The scenarios are invented, but instructors design them carefully — and nobody earns a licence on simulator hours alone.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

বাস্তব উদাহরণ কম হলে — নতুন feature, বিরল edge case বা আক্রমণাত্মক input — মডেল দিয়ে test case তৈরি করা যায়। Self-Instruct দেখিয়েছে অল্প seed থেকে মডেল বড় dataset তৈরি করতে পারে, তবে ফিল্টার করে নিম্নমানের ও প্রায়-অভিন্ন অংশ বাদ দিতে হয় [19]।

  • নিজের ডকুমেন্ট বা policy থেকে এমন প্রশ্ন তৈরি করান, যার উত্তর সেখানে যাচাই করা যায়।
  • বৈচিত্র্য ইচ্ছাকৃতভাবে আনুন: persona, মেজাজ, ভাষা (English, বাংলা, মিশ্র), কাঠিন্য।
  • Embedding-এর মিল দিয়ে প্রায়-অভিন্ন প্রশ্ন বাদ দিন।
  • Release-gating set-এ ঢোকার আগে মানুষ দিয়ে সবকিছু যাচাই করুন।
  • Contamination: test-এর প্রশ্ন মডেলের training data-তে থাকলে স্কোর আসলে মুখস্থবিদ্যা মাপে [20]; তাই একটি ব্যক্তিগত, কখনো প্রকাশ না করা human-written set রাখুন।
ফ্লাইট সিমুলেটরের উপমা: পাইলটরা ইঞ্জিন বিকল বা ঝড়ের অনুশীলন সিমুলেটরে করেন, কারণ বাস্তব বিপদের অপেক্ষা করা অযৌক্তিক। পরিস্থিতিগুলো বানানো, কিন্তু প্রশিক্ষকেরা যত্ন করে নকশা করেন — আর শুধু সিমুলেটরের ঘণ্টা দিয়ে কেউ লাইসেন্স পান না।
06

Frameworks: Promptfoo, DeepEval, Inspect, Braintrust, OpenAI Evals

Eval frameworks give you dataset handling, model runners, assertion libraries, judge templates, reports and CI integration. The concepts transfer between them; pick by language, workflow and where your results need to live.

The landscape

FrameworkStyleGood fit
Promptfoodeclarative YAML plus a CLI; side-by-side prompt and model comparisons [21]prompt iteration, CI gates, red-team scans
DeepEvalpytest-style test cases with a library of metrics, including G-Eval-style judges [22]Python teams who want evals to feel like unit tests
InspectPython framework from the UK AI Security Institute, built around tasks, solvers and scorers [23]rigorous, reproducible evals, including agentic and safety evals
Braintrusthosted platform linking datasets, experiments and production logs [24]teams that want eval history and logs in one interface
OpenAI Evalsopen-source framework and registry of evals [25]reusing community eval templates

A Promptfoo configuration

# promptfooconfig.yaml — run with:  npx promptfoo eval
  prompts:
    - file://prompts/support_v13.txt
    - file://prompts/support_v14.txt
  providers:
    - id: openai:chat:<model-a>
    - id: anthropic:messages:<model-b>
  tests:
    - vars:
        question: "My parcel A-1061 is late. Can I get a refund?"
      assert:
        - type: contains
          value: "A-1061"
        - type: llm-rubric
          value: "Explains the delay policy accurately and offers the correct next step without promising a refund"
        - type: latency
          threshold: 4000

Choosing

  • Where do evals run? In CI on every pull request (CLI-friendly tools), or as scheduled experiments (hosted platforms)?
  • Who writes them? Engineers (code-first) or product and domain experts (YAML or a UI)?
  • Agent support. Multi-step, tool-using tasks need trajectory access and sandboxed tools; check this before committing.
  • Data residency. Hosted platforms store your prompts and outputs; self-hosted tools keep them in your network.
The framework matters less than the dataset. Teams switch frameworks; a well-curated golden set with clear expectations moves with them.
📏Layman's versionplain English, no jargon

Evaluation frameworks are toolkits that run your AI against your test questions and produce a report: which version passed, which failed, where, and by how much.

They differ mainly in style: some are simple settings files run from the command line, some feel like a programmer's normal tests, and some are full websites with history and charts.

Whichever you pick, the precious part is your collection of good test questions — that's what you'd carry with you if you ever switched tools.

The surveyor's toolkit analogy: a builder can measure a room with a tape, a laser or a full surveying kit. The tools differ in speed and convenience, but the real asset is the plan — what needs measuring and what counts as within tolerance.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Eval framework dataset পরিচালনা, মডেল চালানো, assertion, judge template, রিপোর্ট ও CI-সংযোগ দেয়।

  • Promptfoo: YAML config ও CLI; prompt ও মডেল পাশাপাশি তুলনা [21]।
  • DeepEval: pytest-এর মতো test case, নানা মেট্রিক [22]।
  • Inspect: UK AI Security Institute-এর Python framework — task, solver ও scorer [23]।
  • Braintrust: dataset, experiment ও production log এক জায়গায় [24]।
  • OpenAI Evals: open-source framework ও eval registry [25]।

কোনটি নেবেন: eval কোথায় চলবে (CI নাকি নির্ধারিত experiment), কে লিখবেন (engineer নাকি domain expert), agent-এর জন্য trajectory সমর্থন আছে কি না, আর ডেটা কোথায় থাকবে। মনে রাখবেন, framework-এর চেয়ে ভালো dataset অনেক বেশি মূল্যবান।

জরিপকারীর যন্ত্রপাতির উপমা: একজন নির্মাতা ফিতা, লেজার বা পূর্ণ জরিপ-যন্ত্র দিয়ে ঘর মাপতে পারেন। যন্ত্র গতি ও সুবিধায় আলাদা, কিন্তু আসল সম্পদ হলো নকশা — কী মাপতে হবে আর কতটুকু বিচ্যুতি গ্রহণযোগ্য।
07

Online evals on production traffic

Offline sets go stale; real users keep finding new ways to break things. Online evals score a sample of live traffic continuously, so you see quality the way users experience it.

What to run on live traffic

LayerExamplesCoverage
Deterministic checksJSON-schema validity, required fields, banned phrases, PII leakage, length limitsevery response
Cheap model checksa small classifier for refusals, language, topic or toxicityevery response, or most
LLM-judge rubricshelpfulness, policy adherence, faithfulness to the retrieved contexta sample, for example 1–5%
Human reviewambiguous or high-risk cases, judge disagreementsa small, targeted queue

Run it off the hot path

Score asynchronously from the trace store (chapter 04) so evaluation never adds latency or new failure modes to user requests. Attach scores back to traces so you can slice them by prompt version, model, tenant and feature.

Use online scores well

  • Trend, don't panic. Online judge scores are noisy; alert on sustained shifts, not on a single bad answer.
  • Sample smartly. Over-sample new features, high-value tenants and risky intents rather than sampling uniformly.
  • Feed the offline set. Low-scoring production cases are the best candidates for the golden dataset.
  • Mind privacy. Sending user conversations to a judge model is a data flow; it needs the same consent, redaction and retention rules as the original.

Practitioners writing up a year of building LLM products make similar recommendations: assertion-style checks built from real samples, model-based evaluation where needed but not as a silver bullet, and people reading samples of real inputs and outputs regularly [26].

🏭Layman's versionplain English, no jargon

Tests written in advance can't predict everything real customers will do. So you also grade a slice of real conversations as they happen.

Simple automatic checks run on every answer — is it in the right format, does it leak private details, is it absurdly long? A smarter AI grader looks at a small random sample in more depth, and people review the confusing cases.

All of this happens in the background, so customers never wait for the grading — and the worst real examples get added to your test collection.

The bottling line analogy: a bottling plant doesn't only test its recipe in the lab. Sensors check every bottle's fill level as it passes, and an inspector pulls random bottles off the line for a taste test. Bad batches get traced back, and the lab tests get updated.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

আগে লেখা test আসল ব্যবহারকারীর সব আচরণ আন্দাজ করতে পারে না। Online eval চলমান traffic-এর একটি নমুনা ধারাবাহিকভাবে মূল্যায়ন করে।

  • প্রতিটি উত্তরে deterministic চেক: JSON-এর বৈধতা, আবশ্যিক field, নিষিদ্ধ শব্দ, PII ফাঁস, দৈর্ঘ্য।
  • সস্তা classifier: প্রত্যাখ্যান, ভাষা, বিষয়, বিষাক্ততা।
  • LLM-judge rubric: নমুনার ওপর (যেমন ১–৫%)।
  • মানুষের review: অস্পষ্ট বা ঝুঁকিপূর্ণ case।

মূল্যায়ন মূল request-এর পথ থেকে আলাদা করে (asynchronously) চালান, স্কোর trace-এর সাথে যুক্ত করুন, একক খারাপ উত্তরে নয় বরং স্থায়ী পরিবর্তনে alert দিন, আর কম স্কোরের বাস্তব case golden dataset-এ যোগ করুন [26]। Judge মডেলে কথোপকথন পাঠানোও একটি ডেটা-প্রবাহ — consent, redaction ও retention নিয়ম মানতে হবে।

বোতলজাতকরণ লাইনের উপমা: বোতলজাতকরণ কারখানা শুধু ল্যাবে রেসিপি পরীক্ষা করে না। সেন্সর প্রতিটি বোতলের পরিমাণ মাপে, আর পরিদর্শক লাইন থেকে এলোমেলো বোতল তুলে স্বাদ পরীক্ষা করেন। খারাপ ব্যাচের উৎস খুঁজে ল্যাবের পরীক্ষাও হালনাগাদ করা হয়।
08

Red teaming and adversarial testing

Red teaming means deliberately trying to make your system misbehave — leak data, follow injected instructions, produce harmful content, take unauthorised actions — before attackers or unlucky users do it for you.

Manual and automated red teaming

Anthropic's study of red teaming released a dataset of 38,961 red-team attacks and examined how vulnerability changes across model sizes and training methods [27]. Perez et al. showed that one language model can generate test cases that find failures in another at scale [28]. In practice you combine both: people find creative, high-impact failures; automation turns them into large, repeatable suites.

Tools

ToolWhat it does
garakNVIDIA's open-source LLM vulnerability scanner, probing for prompt injection, jailbreaks, data leakage and more [29]
PyRITMicrosoft's Python Risk Identification Tool for automating red teaming of generative AI systems [30]
Promptfoo red teaminggenerates adversarial test cases against your own application configuration [21]
AgentDojoa benchmark environment for prompt-injection attacks and defences in tool-using agents [31]

A practical process

  1. Threat-model the system. What can it read, which tools can it call, who are its users? The OWASP Top 10 for LLM applications is a good checklist of risk categories [32].
  2. Build an attack library per category: direct and indirect injection, jailbreaks, PII extraction, harmful content, excessive agency, runaway cost.
  3. Automate the library as an eval suite and track the attack success rate per category over time.
  4. Fix and re-test. Every successful attack becomes a regression test (see the first section of this chapter).
  5. Repeat on every major change — new tools, new model, new data sources — and on a schedule.
Agents raise the stakes. For a chatbot, a successful attack produces bad text. For an agent with tools, it produces actions: refunds, emails, deleted records. Red-team tool-using agents with their tools connected to realistic sandboxes, not mocks.
🔐Layman's versionplain English, no jargon

Red teaming is hiring people — and programs — to try to break your AI on purpose. Can they trick it into revealing private information, following hidden instructions in a web page, saying something harmful, or doing something it shouldn't, like issuing a refund it wasn't allowed to give?

Every trick that works becomes a permanent test, and the tests run again whenever anything important changes.

It matters most when the AI can take actions. A chatbot that's tricked says something silly; an assistant with access to your systems that's tricked can do real damage.

The locksmith analogy: a bank hires professional locksmiths to try to pick its vault before burglars do. Each lock they open leads to a better lock — and the bank keeps hiring them, because burglars keep learning new tricks.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Red teaming মানে ইচ্ছাকৃতভাবে সিস্টেমকে ভুল করানোর চেষ্টা — ডেটা ফাঁস, লুকানো নির্দেশ মানা, ক্ষতিকর বিষয়বস্তু, অননুমোদিত কাজ — আক্রমণকারী করার আগেই।

  • Anthropic-এর গবেষণা ৩৮,৯৬১টি red-team আক্রমণের dataset প্রকাশ করেছে [27]; Perez et al. দেখিয়েছেন একটি মডেল আরেকটির ব্যর্থতা খুঁজতে বড় আকারে test তৈরি করতে পারে [28]।
  • টুল: garak [29], PyRIT [30], Promptfoo red teaming, আর agent-এর prompt injection-এর জন্য AgentDojo [31]।
  • প্রক্রিয়া: threat model (OWASP Top 10 একটি ভালো চেকলিস্ট [32]) → বিভাগভিত্তিক আক্রমণের সংগ্রহ → স্বয়ংক্রিয় eval suite → সংশোধন ও পুনঃপরীক্ষা → প্রতিটি বড় পরিবর্তনে আবার।

টুল-ব্যবহারকারী agent-এ ঝুঁকি বেশি: সফল আক্রমণ মানে শুধু খারাপ লেখা নয়, বাস্তব কাজ — refund, ইমেল, রেকর্ড মুছে ফেলা।

তালাওয়ালার উপমা: ব্যাংক পেশাদার তালাওয়ালা ভাড়া করে, যাতে চোরের আগেই তাঁরা ভল্ট খোলার চেষ্টা করেন। প্রতিটি খোলা তালা আরও ভালো তালার পথ দেখায় — আর ব্যাংক তাঁদের ডাকতেই থাকে, কারণ চোরেরাও নতুন কৌশল শেখে।
