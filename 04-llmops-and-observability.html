LLMOps & observability

A traditional service is healthy when it returns 200 quickly. An LLM feature can return 200 quickly and still be wrong, rude, slow to stream, ten times over budget, or quietly worse than last week. LLMOps is the discipline of seeing all of that: tracing every step, metering tokens and cost per user, versioning prompts and agents, A/B testing changes, replaying failures, detecting drift, and turning user feedback into tests.

01

Tracing: Langfuse, LangSmith, Helicone, Arize Phoenix, Braintrust

A trace records one user request as a tree of spans — the model calls, tool calls, retrievals and checks it caused — with inputs, outputs, tokens, cost and timing on each. Without traces, debugging an agent is guesswork.

What a trace contains

A trace is the full story of one request: a root span for the request, and child spans for each model call ("generation"), retrieval, tool call, guardrail and sub-agent. Each span records start and end time, inputs and outputs, model and parameters, token counts and errors. For agents, the trace is the only way to see *why* the agent did what it did.

One support request as a trace. The timeline shows the tool call and retrieval running in parallel, the answer generation dominating latency, and a large share of input tokens served from the prompt cache.
একটি support request-এর trace। Timeline-এ দেখা যাচ্ছে tool call ও retrieval একসাথে চলেছে, উত্তর তৈরিতেই সবচেয়ে বেশি সময় লেগেছে, আর input token-এর বড় অংশ cache থেকে এসেছে।

Standard attributes: OpenTelemetry GenAI conventions

OpenTelemetry defines semantic conventions for generative AI so traces are portable between tools — attributes such as gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens [1], now maintained in a dedicated GenAI conventions repository [2]. OpenInference [3] and OpenLLMetry [4] add auto-instrumentation for popular SDKs and frameworks on top of OpenTelemetry.

from opentelemetry import trace
  
  tracer = trace.get_tracer("support-bot")
  
  def answer(question: str, user_id: str) -> str:
      with tracer.start_as_current_span("llm.answer") as span:
          span.set_attribute("gen_ai.provider.name", "anthropic")
          span.set_attribute("gen_ai.request.model", MODEL)
          span.set_attribute("app.user_id", user_id)
          span.set_attribute("app.prompt_version", "support-answer@v14")
          resp = client.messages.create(model=MODEL, max_tokens=800,
                                        messages=[{"role": "user", "content": question}])
          span.set_attribute("gen_ai.usage.input_tokens", resp.usage.input_tokens)
          span.set_attribute("gen_ai.usage.output_tokens", resp.usage.output_tokens)
          return resp.content[0].text

What to capture — and what not to

Capture prompts, outputs, tool arguments and results, model and parameters, prompt version, user and tenant ids, token usage and errors. Never capture secrets, and decide deliberately about personal data: redact or hash before export (chapter 07), restrict who can read raw traces, and set a retention period.

A trace store is a production database. It holds what users typed and what your tools returned. Give it the same access control, retention rules and breach planning as your customer data.
📦Layman's versionplain English, no jargon

A trace is the full receipt for one question someone asked your AI. It lists every step: what the AI was told, which tools it used, what it looked up, what it answered, how long each step took and what it cost.

Without it, problems are guesswork. When a customer says "the bot gave me a weird answer yesterday", you open their trace and see exactly where it went wrong — the lookup returned the wrong order, or an old version of the instructions was running.

Because traces contain what people typed, they need the same care as any customer database.

The parcel tracking analogy: a parcel's tracking page shows every hop — picked up, sorted, loaded, out for delivery — each with a time. When a parcel goes missing you don't guess; you look at the last scan. A trace is the tracking page for one AI request.

টুল: Langfuse (open source, prompt management-সহ) [5], LangSmith [6], Helicone (request-এর পথে বসানো যায়) [7], Arize Phoenix [8] ও Braintrust [9]।

Token, cost, and latency tracking per request and per user

Every model call should emit a usage record — tokens in and out, cached tokens, model, latency, cost — tagged with who and what caused it. Aggregated, those records answer every question finance and product will ask.

The usage record

FieldWhy it matters
input_tokens, output_tokensthe two numbers every price sheet is built on
cached input tokensprompt-cache reads are billed at a fraction of normal input (chapter 06)
reasoning ("thinking") tokensbilled as output on reasoning models; can dominate cost
model (exact id)prices and behaviour differ between model versions
TTFT and total latencythe user experience (chapter 03)
tenant_id, user_id, feature, prompt_versionthe dimensions you will group by
cost in currencycomputed from a versioned price table, never hard-coded

Compute cost from a versioned price table

Prices change, and differ by model, region, batch versus real-time, and cache read versus write. Keep a table keyed by model and effective date, compute cost when you write the record, and never rewrite history — last quarter's cost must stay last quarter's.

-- Daily calls, tokens, cost and p95 latency per tenant and feature
  SELECT
    date_trunc('day', created_at)                            AS day,
    tenant_id,
    feature,
    count(*)                                                 AS calls,
    sum(input_tokens)                                        AS input_tokens,
    sum(output_tokens)                                       AS output_tokens,
    round(sum(cost_usd)::numeric, 2)                         AS cost_usd,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms) AS p95_latency_ms
  FROM llm_usage
  WHERE created_at >= now() - interval '30 days'
  GROUP BY 1, 2, 3
  ORDER BY cost_usd DESC;

The dashboards that pay for themselves

  • Cost per feature and per active user — finds the one feature eating the budget.
  • Tokens per conversation over time — catches context bloat as histories grow.
  • Cache hit rate — tells you whether restructuring prompts actually worked.
  • p95 TTFT and error rate per model — the first place a provider incident shows up.
  • Top users by spend — abuse, runaway agents and loops appear here first (chapter 07).
Alert on the rate of change, not only on thresholds. "Cost this hour is 3× the same hour last week" catches a looping agent within the hour; a monthly budget alert catches it on day 28.
🧾Layman's versionplain English, no jargon

Every time the AI answers, it should leave a line on the bill: how much it read, how much it wrote, how long it took, what it cost, and who asked.

Added up, those lines answer the big questions: which feature costs the most, which customers use it heavily, whether a change made things cheaper, and whether something is running away overnight.

Prices change, so the bill should remember which price applied at the time — otherwise last month's numbers shift every time a vendor updates its rates.

The itemised phone bill analogy: a good phone bill doesn't just say "you owe 2,140 taka". It lists each call: who made it, to where, for how long, at what rate. That's how a family discovers that one teenager's international calls are the whole problem.

03

Prompt and agent versioning

An agent's behaviour is defined by more than code: the prompt text, the model id, sampling parameters, tool definitions and retrieval settings. Version them together, release them deliberately, and stamp the version on every trace.

Version the whole configuration

A "prompt change" that also swaps the model, or a model alias that silently moves to a new snapshot, makes regressions impossible to attribute. Treat the full configuration as one immutable, versioned artifact:

# agents/support-answer/v14.yaml — immutable once released
  id: support-answer
  version: 14
  model: "<exact snapshot id from your provider, not a floating alias>"
  temperature: 0.2
  max_tokens: 800
  system_prompt: prompts/support-answer/v14.md
  tools: [orders_search, orders_refund, policy_lookup]
  retrieval: {index: policies-2026-10, top_k: 5}
  eval_gate: {suite: support-golden, min_pass_rate: 0.95}

Registry, labels and rollback

Prompt-management tools store versions and attach labels such as production and staging; the application fetches "the production version" at runtime, so a rollback is moving a label rather than redeploying code [10]. If you keep prompts in git instead, get the same properties: review in pull requests, immutable tags, and a release record of which version is live.

Pin model versions

Providers publish both floating aliases and specific model snapshots, and document how aliases move to newer snapshots over time [11]. Production traffic should pin an exact id, so that "the model changed" is always a deliberate release rather than a surprise (see drift detection below).

Stamp versions on every trace

Put prompt_version, agent_version and the exact model id on every span. Then "quality dropped on Tuesday" becomes a query: which versions served Tuesday's bad traces?

Don't edit prompts in place in production. An admin-panel edit with no version history is a silent deploy that skips review, evals and rollback.
🎼Layman's versionplain English, no jargon

An AI feature's behaviour comes from its written instructions, the exact model, and a handful of settings. Change any one of them and the behaviour changes. So the whole bundle gets a version number, like an app update.

Every answer is stamped with the version that produced it. When something goes wrong, you know exactly which bundle was running — and going back to the previous one is a single switch.

Nobody quietly edits the instructions on the live system, for the same reason nobody should edit a live website without keeping a copy.

The orchestra sheet music analogy: every musician must play from the same edition of the score. If a wrong note appears in a concert, the conductor checks which edition was on each stand. Printing a corrected edition — and keeping the old one in the archive — fixes it without chaos.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Agent-এর আচরণ শুধু কোডে ঠিক হয় না — prompt-এর লেখা, মডেলের id, temperature-এর মতো parameter, tool definition ও retrieval সেটিং মিলে ঠিক হয়। এগুলো একসাথে একটি অপরিবর্তনীয়, version-যুক্ত configuration হিসেবে রাখুন।

  • Prompt registry-তে version ও label (production, staging) ব্যবহার করুন; rollback মানে শুধু label সরানো [10]।
  • Floating alias নয়, নির্দিষ্ট model snapshot id pin করুন [11]।
  • প্রতিটি trace-এ prompt_version, agent_version ও মডেল id লিখে রাখুন।
  • Production-এ সরাসরি prompt edit করবেন না — এটি review, eval ও rollback ছাড়াই গোপন deploy।
অর্কেস্ট্রার স্বরলিপির উপমা: সব বাদককে একই সংস্করণের স্বরলিপি থেকে বাজাতে হয়। কনসার্টে ভুল সুর বাজলে কন্ডাক্টর দেখেন কোন stand-এ কোন সংস্করণ ছিল। সংশোধিত সংস্করণ ছাপিয়ে পুরোনোটি আর্কাইভে রাখাই সঠিক সমাধান।
04

A/B testing prompts and models in production

Offline evals tell you a change is safe; online experiments tell you whether it is better for real users. A/B tests on LLM features follow the same statistics as any product experiment, plus a few LLM-specific traps.

The experiment design

  1. Gate with offline evals first (chapter 05) — never A/B test a variant that fails your golden set.
  2. Randomise by user, not by request, so each person sees a consistent experience.
  3. Choose one primary metric (task success, resolution rate) and several guardrail metrics (cost per conversation, p95 latency, escalation and complaint rates).
  4. Size the test before starting; don't stop the moment the dashboard looks good.
  5. Check for sample ratio mismatch: if a 50/50 split arrives as 53/47, assignment is broken and the result can't be trusted.

Kohavi, Tang and Xu's book on online controlled experiments is the standard reference for these practices, including sample-ratio checks and the dangers of peeking [12].

import hashlib
  
  def variant(user_id: str, experiment: str,
              split=(("control", 50), ("treatment", 50))) -> str:
      """Deterministic, sticky assignment: same user + experiment -> same arm."""
      digest = hashlib.sha256(f"{experiment}:{user_id}".encode()).hexdigest()
      bucket = int(digest, 16) % 100
      edge = 0
      for name, pct in split:
          edge += pct
          if bucket < edge:
              return name
      return split[-1][0]

LLM-specific traps

  • Novelty and verbosity. Longer, more confident answers often win thumbs-ups in week one and lose trust later. Watch retention and repeat-contact rates, not just first impressions.
  • Cost belongs in the decision. A variant that is 2% better but 40% more expensive may be a loss.
  • Non-stationarity. A provider-side model update during the test affects both arms; pin model versions.
  • Interference. Shared caches or rate limits can let one arm slow the other; isolate them where you can.
Shadow first, then split. For risky changes, run the new variant in shadow mode — generate but don't show — and compare judge scores on real traffic before exposing any users.
🥤Layman's versionplain English, no jargon

An A/B test shows two versions to two random groups of real users and measures which works better. Before that, the new version must pass your own internal checks — you never experiment on customers with something you already know is broken.

Each person stays in the same group, so their experience doesn't flip back and forth. You decide in advance what "better" means — more problems solved, fewer repeat complaints — and what must not get worse, like cost and speed.

And you wait for enough data before declaring a winner, because early results swing wildly.

The blind taste test analogy: two unlabelled cups of cola go to randomly chosen shoppers, and each shopper always tastes the same pair. You count preferences only after hundreds of tastings — and you also check that the "winning" recipe doesn't cost twice as much to make.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Offline eval বলে পরিবর্তনটি নিরাপদ; online experiment বলে আসল ব্যবহারকারীর জন্য সেটি ভালো কি না।

  • আগে offline eval পাস করান (অধ্যায় ০৫)।
  • Request নয়, user ধরে randomise করুন, যাতে একজন সবসময় একই সংস্করণ দেখেন।
  • একটি প্রধান মেট্রিক (সমস্যা সমাধানের হার) আর কয়েকটি guardrail মেট্রিক (খরচ, p95 latency, অভিযোগ) ঠিক করুন।
  • আগেই sample size ঠিক করুন; ড্যাশবোর্ড ভালো দেখালেই থামবেন না।
  • Sample ratio mismatch পরীক্ষা করুন [12]।

LLM-এর বিশেষ ফাঁদ: লম্বা ও আত্মবিশ্বাসী উত্তর শুরুতে বেশি পছন্দ পায়; খরচকে সিদ্ধান্তের অংশ ধরুন; পরীক্ষা চলাকালে provider মডেল বদলালে দুই দলই প্রভাবিত হয়।

অন্ধ স্বাদ পরীক্ষার উপমা: লেবেলহীন দুই কাপ কোলা এলোমেলোভাবে বাছাই করা ক্রেতাদের দেওয়া হয়। শত শত মানুষের মত নেওয়ার পরেই ফল গোনা হয় — আর দেখা হয় "জয়ী" রেসিপি বানাতে দ্বিগুণ খরচ হয় কি না।
05

Replay and debugging of failed runs

When an agent fails in production you need to reproduce the exact run: the same inputs, prompt version, model, parameters and tool results. Then you can fix it, prove the fix, and keep the case as a regression test.

Capture enough to replay

A replayable trace stores the full model inputs (system prompt, messages, tool definitions), the parameters, the exact model id, every tool result, and the prompt and agent versions. Tool results matter most: re-running live tools during a replay changes the world, or returns data that has since changed, so a replay should feed back the recorded results.

Why replays are not perfectly deterministic

Even at temperature 0, providers do not promise bit-identical outputs, because batching and hardware non-determinism affect floating-point results. Treat a replay as "reproduce the situation", then judge the new output with your evals rather than expecting identical text.

Fork from a step

Agent frameworks with checkpointing let you resume from any recorded step with modified state — change one tool result or one instruction and see what the agent does next. LangGraph exposes this through its persistence layer and its "time travel" feature [13].

def replay(trace, system_override=None, model=None):
      """Re-run the failing model call with optional changes. Tools are NOT re-executed."""
      call = trace.llm_calls[-1]                  # the step that went wrong
      return client.messages.create(
          model=model or call.model,
          system=system_override or call.system,
          messages=call.messages,                 # includes the recorded tool_result blocks
          tools=call.tools,
          max_tokens=call.max_tokens,
          temperature=call.temperature,
      )

Close the loop

Every production failure you debug should become a test: save the trace's inputs and the expected behaviour into your eval dataset (chapter 05), so the same bug cannot quietly return. Practitioners who have shipped many LLM products put "look at your data" — reading real traces regularly — at the centre of this loop [14][15].

🎬Layman's versionplain English, no jargon

When the AI gets something wrong, you want to watch exactly what happened, step by step. That means the record has to include everything it saw: the instructions, the conversation, and what each lookup returned at that moment.

You replay the moment with the recorded lookups, not fresh ones, because the world has moved on since. Then you try a fix and check whether the AI now does the right thing.

Each mistake you fix becomes a permanent test, so it can't sneak back in later.

The instant replay analogy: a referee reviewing a disputed goal watches the recorded footage from every camera angle, frame by frame — not a re-enactment by the players. Once the decision is made, the clip goes into the training reel for future referees.

Production-এ agent ব্যর্থ হলে ঠিক সেই run আবার তৈরি করতে হয়: একই input, prompt version, মডেল id, parameter ও tool result।

  • Replay-তে live tool আবার চালাবেন না; রেকর্ড করা tool result ব্যবহার করুন, কারণ ইতোমধ্যে ডেটা বদলে গেছে।
  • Temperature 0 হলেও provider হুবহু একই output-এর নিশ্চয়তা দেয় না; তাই হুবহু মিল নয়, eval দিয়ে নতুন output বিচার করুন।
  • Checkpoint-যুক্ত framework (যেমন LangGraph-এর time travel) দিয়ে যেকোনো ধাপ থেকে পরিবর্তিত state নিয়ে আবার চালানো যায় [13]।
  • প্রতিটি ঠিক করা ব্যর্থতা eval dataset-এ test হিসেবে যোগ করুন; নিয়মিত আসল trace পড়ার অভ্যাসই এই চক্রের কেন্দ্র [14]।
খেলার ইনস্ট্যান্ট রিপ্লের উপমা: বিতর্কিত গোল দেখতে রেফারি প্রতিটি ক্যামেরার রেকর্ড করা ফুটেজ ফ্রেম ধরে দেখেন — খেলোয়াড়দের দিয়ে আবার অভিনয় করান না। সিদ্ধান্তের পর ক্লিপটি ভবিষ্যৎ রেফারিদের প্রশিক্ষণে রাখা হয়।
06

Drift detection (model upgrades silently changing behavior)

Your prompt didn't change, your code didn't change, and yet quality did. Drift comes from provider model updates, serving bugs, and shifts in what users ask. You catch it only by measuring continuously.

It really happens

A Stanford and UC Berkeley study compared the March and June 2023 versions of GPT-4 and GPT-3.5 and found large behaviour changes; for example, GPT-4's accuracy at identifying prime versus composite numbers fell from 84% to 51% [16]. Drift also comes from serving infrastructure: Anthropic's September 2025 postmortem described three overlapping bugs — a context-window routing error, output corruption, and an approximate top-k XLA:TPU miscompilation — that intermittently degraded Claude's responses [17].

Three kinds of drift

KindCauseDetect with
Model driftthe provider updates a model or moves an aliasscheduled canary evals on a fixed set
Serving driftinfrastructure bugs, quantization or configuration changescanary evals plus output statistics
Input driftusers start asking different thingstopic and embedding-distribution monitoring

Canary evals on a schedule

Run a fixed, representative eval set against the production configuration every few hours and on every deploy, and alert when the pass rate falls outside its normal variance.

An illustrative canary chart: quality is stable for eight days, drops below threshold when the provider changes the model behind an alias, and recovers after the team pins the previous snapshot.
কাল্পনিক canary চার্ট: আট দিন মান স্থির ছিল, provider alias-এর পেছনের মডেল বদলানোয় সীমার নিচে নেমে যায়, আর আগের snapshot pin করার পর আবার ঠিক হয়।

Output statistics are cheap early warnings

Between eval runs, watch distributions you can compute on every response: answer length, refusal rate, tool-call rate, JSON-validity rate, response language, and judge scores on a sample. A sudden shift in any of them is a reason to look. Libraries such as Evidently compute drift statistics for both classic ML features and LLM outputs [18].

Defences

  • Pin model versions and upgrade deliberately, with your eval suite as the gate (see versioning above).
  • Canary new models on a small share of traffic before switching over completely.
  • Keep a rollback path: the previous model id and configuration, still deployable.
🛞Layman's versionplain English, no jargon

Sometimes an AI gets worse without anyone touching your product. The company behind the model updates it, a server bug slips in, or customers start asking new kinds of questions.

You only notice if you keep testing. A fixed set of known questions gets asked every few hours; if the score suddenly drops, an alarm goes off. Simple running checks — are answers suddenly longer, more often refusing, more often broken? — give early hints between those tests.

The defence is to lock to one specific model version and change it on purpose, after testing, with the old one kept ready to switch back to.

The wheel alignment analogy: a car's alignment drifts so gradually that you don't notice until the tyres are worn. Regular checks catch it early, and a mechanic's measurement — not a vague feeling — tells you when to act.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Prompt বা কোড না বদলালেও মান বদলাতে পারে — একে বলে drift।

  • Model drift: provider মডেল আপডেট করে। গবেষণায় দেখা গেছে, মার্চ থেকে জুন ২০২৩-এর মধ্যে GPT-4-এর মৌলিক সংখ্যা চেনার নির্ভুলতা ৮৪% থেকে ৫১%-এ নেমেছিল [16]।
  • Serving drift: infrastructure-এর bug; Anthropic-এর সেপ্টেম্বর ২০২৫-এর postmortem-এ তিনটি bug-এর কারণে Claude-এর উত্তরের মান মাঝেমধ্যে খারাপ হওয়ার বিবরণ আছে [17]।
  • Input drift: ব্যবহারকারীরা নতুন ধরনের প্রশ্ন করতে শুরু করেন।

সমাধান: নির্দিষ্ট সময় পরপর একটি স্থির eval set চালান (canary eval); উত্তরের দৈর্ঘ্য, প্রত্যাখ্যানের হার, tool-call হার ও JSON-এর বৈধতা নজরে রাখুন [18]; model snapshot pin করুন, নতুন মডেল আগে অল্প traffic-এ চালান, আর rollback-এর পথ খোলা রাখুন।

চাকার অ্যালাইনমেন্টের উপমা: গাড়ির চাকার অ্যালাইনমেন্ট এত ধীরে সরে যে টায়ার ক্ষয় না হওয়া পর্যন্ত বোঝা যায় না। নিয়মিত পরীক্ষাই আগেভাগে ধরে, আর অনুভূতি নয়, মিস্ত্রির মাপই বলে দেয় কখন ব্যবস্থা নিতে হবে।
07

Feedback loops (thumbs up/down → eval datasets)

User feedback is the cheapest source of real failure cases you will ever get. The loop that matters: capture signals, triage the bad ones, label them, add them to the eval set, fix, and verify the fix.

Explicit, implicit and outcome signals

SignalExamplesStrength and weakness
Explicitthumbs up/down, star rating, written commentclear intent, but sparse and skewed toward unhappy users
Implicitcopy, retry, regenerate, edit before sending, abandon, escalate to a humanplentiful, but noisy and needs interpretation
Outcometicket resolved, purchase completed, code mergedclosest to business value, but delayed

Eugene Yan's survey of LLM product patterns treats collecting user feedback as a core pattern precisely because it turns usage into evaluation and training data [19].

The feedback flywheel: every negative signal is a candidate test case. The loop only works if step 3 — a person deciding what correct looks like — actually happens.
Feedback flywheel: প্রতিটি নেতিবাচক signal একটি সম্ভাব্য test case। ধাপ ৩ — একজন মানুষ ঠিক করবেন সঠিক উত্তর কী — না হলে চক্রটি কাজ করে না।

Turning feedback into tests

  1. Route negative and ambiguous signals into a triage queue, with the full trace attached.
  2. Have a person — ideally a domain expert — write what the correct behaviour would have been: a reference answer, a rubric, or a pass/fail criterion.
  3. Add the case to the golden dataset, tagged by failure category.
  4. Fix, then require the new case and the rest of the suite to pass before release (chapter 05).

Watch the biases

Thumbs are given mostly by unhappy users; some people click thumbs-down to mean "I don't like the policy" rather than "the answer was wrong"; and feedback on refusals is often a user wanting something you shouldn't provide. Read before you act, and weight feedback by category. Hamel Husain's widely shared essay makes the same point: the leverage comes from systematically looking at the data, not from the thumbs counter itself [14].

🗺️Layman's versionplain English, no jargon

Every thumbs-down is a free bug report. So are quieter signals: the person who clicks "try again", rewrites the answer before sending it, or gives up and asks for a human.

The useful habit is a loop: collect those moments, have someone decide what the right answer should have been, add that example to the test collection, fix the AI, and check the fix passes before releasing it.

Don't take every thumbs-down literally, though. Sometimes people dislike a correct answer — like being told a refund isn't allowed.

The traffic app analogy: a navigation app gets better because drivers report jams, closures and accidents as they drive. The app checks the reports, confirms the real ones, and updates the map for everyone — and learns to ignore the driver who reports every red light as "traffic".
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

ব্যবহারকারীর feedback হলো বাস্তব ব্যর্থতার সবচেয়ে সস্তা উৎস।

  • Explicit: thumbs up/down, রেটিং, মন্তব্য — স্পষ্ট কিন্তু সংখ্যায় কম, আর মূলত অসন্তুষ্ট ব্যবহারকারীরাই দেন।
  • Implicit: কপি, আবার চেষ্টা, পাঠানোর আগে উত্তর সম্পাদনা, মাঝপথে ছেড়ে যাওয়া, মানুষের কাছে escalation — সংখ্যায় বেশি, তবে ব্যাখ্যা করতে হয়।
  • Outcome: টিকিট সমাধান, কেনাকাটা সম্পন্ন — ব্যবসার মূল্যের সবচেয়ে কাছে, কিন্তু দেরিতে আসে।

চক্র: খারাপ signal triage queue-তে পাঠান → একজন বিশেষজ্ঞ লিখুন সঠিক উত্তর কী হওয়া উচিত ছিল → উদাহরণটি golden eval set-এ যোগ করুন → ঠিক করুন, আর eval পাস না করা পর্যন্ত release করবেন না [19][14]।

সতর্কতা: প্রতিটি thumbs-down আক্ষরিক অর্থে নেবেন না — অনেক সময় মানুষ সঠিক কিন্তু অপছন্দের উত্তরেও (যেমন refund নিষেধ) thumbs-down দেন।

ট্রাফিক অ্যাপের উপমা: নেভিগেশন অ্যাপ ভালো হয় কারণ চালকেরা চলার পথেই জ্যাম, রাস্তা বন্ধ বা দুর্ঘটনার খবর দেন। অ্যাপ সেগুলো যাচাই করে সবার মানচিত্র হালনাগাদ করে — আর শেখে, যে চালক প্রতিটি লাল বাতিকে "জ্যাম" বলেন, তাঁকে উপেক্ষা করতে।
