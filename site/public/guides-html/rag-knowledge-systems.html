Chunking strategies: fixed, semantic, structural, late chunking

Retrieval works on pieces of documents, not whole documents, so how you cut the text decides what the retriever can ever return. A chunk that is too coarse buries the answer in noise; one that is too fine strips away the context that made the sentence meaningful. This section covers four families: fixed-size (with overlap and recursive separators), structural (headers and sentences), semantic (embedding-driven breakpoints) and late chunking (split after the transformer), plus Anthropic's contextual retrieval, which repairs lost context by prepending an explanation to every chunk.[1][2]

Fixed-size and recursive splitting

The baseline is a window of chunk_size units with chunk_overlap units shared between neighbours so a fact straddling a boundary still lands whole in at least one chunk. In LangChain's RecursiveCharacterTextSplitter the size is measured by length_function, which defaults to Python len(), i.e. characters. The recursive variant tries separators in order ("\n\n", "\n", " ", "": paragraph, line, word, character) so coherent units stay together for as long as possible.[3]

Top: overlapping windows keep boundary text in two chunks. Bottom: the recursive splitter prefers paragraph breaks and only descends to words or characters when it must.
উপরে overlap সহ sliding window দেখানো হয়েছে, যাতে দুই chunk-এর সীমানার লেখা দুই জায়গাতেই থাকে। নিচে recursive splitter আগে paragraph, তারপর line, word এবং শেষে character দিয়ে কাটে, যতক্ষণ না টুকরো ছোট হয়।

Structural and sentence-aware splitting

Structure-aware splitters respect boundaries the author already drew. LlamaIndex's SentenceSplitter breaks at sentence boundaries (the docs example uses chunk_size=1024 plus a chunk_overlap), and MarkdownNodeParser parses raw markdown into nodes.[4] LangChain's MarkdownHeaderTextSplitter groups text by header level and attaches the headers as metadata (for example {'Header 1': ..., 'Header 2': ...}); headers are stripped from the text by default (strip_headers=False keeps them). Chain it with a recursive splitter so overlap applies inside a section and never crosses a header boundary.[5]

from langchain_text_splitters import (
    MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter)

md = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "Header 1"), ("##", "Header 2")],
    strip_headers=False)          # keep headings inside the chunk text
sections = md.split_text(markdown_text)  # each Document carries header metadata

rc = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)  # illustrative values
chunks = rc.split_documents(sections)   # overlap stays inside each section
Units matter: the LangChain default measures characters, not tokens, so a "1000" chunk is not 1000 tokens. The values above are illustrative; none of the sources I checked states a recommended chunk size or overlap percentage, so tune them against your own retrieval evals.

Semantic chunking

Instead of a fixed size, semantic chunking embeds sentences and cuts where adjacent-sentence similarity drops. LlamaIndex's SemanticSplitterNodeParser chooses breakpoints from embedding similarity; its docs example uses breakpoint_percentile_threshold=95 and buffer_size=1, and credits Greg Kamradt's "5 levels of embedding chunking".[4]

Semantic chunking cuts at the biggest topic shifts between adjacent sentences. The curve is illustrative only.
পাশাপাশি বাক্যের embedding similarity হঠাৎ কমে গেলে সেখানে breakpoint বসে এবং নতুন chunk শুরু হয়। বক্ররেখাটি শুধু ধারণা বোঝানোর জন্য আঁকা, বাস্তব ডেটা নয়।

Late chunking

Conventional pipelines chunk first and embed each chunk alone, so a chunk saying "the company" cannot know which company. Late chunking (Günther et al., 2024) runs a long-context embedding model over the whole text and splits "after the transformer model and just before mean pooling", so every chunk vector is pooled from token embeddings that already attended to the surrounding document. The authors state it needs no extra training, and fine-tuning can improve it further.[1] The limit is practical: it requires an embedding model whose context window can hold the document.

Only the position of the split changes: late chunking pools chunk vectors from token embeddings that were computed over the whole document.
Naive পদ্ধতিতে আগে কাটা হয়, তারপর প্রতিটি chunk আলাদাভাবে encode হয়। Late chunking-এ পুরো document একবারে encode করে, তারপর mean pooling-এর ঠিক আগে কাটা হয়, তাই প্রতিটি chunk vector আশপাশের context বহন করে।

Contextual retrieval (Anthropic)

A different repair: have an LLM write a short, chunk-specific explanation of where the chunk sits in its document, prepend it to the chunk, and use the result for both the embedding and the BM25 index. Anthropic reports the context is roughly 50 to 100 tokens per chunk and that one-time generation costs $1.02 per million document tokens. For knowledge bases under about 200,000 tokens (around 500 pages) the post says simpler approaches, such as putting everything in the prompt, are enough.[2]

Contextual retrieval: generated context is prepended before both embedding and BM25 indexing; reported failure rate falls from 5.7% to 1.9% once reranking is added.
প্রতিটি chunk-এর আগে LLM-এর লেখা ছোট context জুড়ে দিয়ে embedding ও BM25 দুটোই বানানো হয়। Anthropic-এর রিপোর্ট অনুযায়ী retrieval failure rate 5.7% থেকে কমে reranking-সহ 1.9% হয়।

✂️Layman's versionplain English, no jargon

What is chunking? Before a computer can search your documents, it has to cut them into bite-sized pieces. Each piece is what gets matched to a question.

Why does it matter? Cut badly and the answer gets split in half, or a piece says "it was approved" without saying what "it" is. Cut well and each piece makes sense on its own. Tricks like overlapping pieces, cutting at headings, or stapling a one-line note ("this is from the 2023 refund policy") to every piece all fight that problem.

When does it go wrong? Pieces that are too small lose their meaning; pieces that are too big bury the answer in clutter. And no single cutting rule is best for every kind of document, so you have to test on your own.

The scrapbook analogy: imagine cutting up a newspaper to make a scrapbook. Cut by exact inches and you slice sentences in half. Cut along the article borders and each clipping makes sense. Write the newspaper name and date on the back of every clipping, and even a tiny clipping can be understood later.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Chunking কী? RAG সিস্টেমে বড় document সরাসরি খোঁজা হয় না; আগে সেটাকে ছোট ছোট টুকরোয় (chunk) ভাগ করা হয়, তারপর প্রতিটি টুকরো আলাদাভাবে index হয়। কাটার পদ্ধতির ওপরই নির্ভর করে retriever কী খুঁজে পাবে।

  • Fixed-size + overlap: chunk_size ও chunk_overlap দিয়ে কাটা হয়। LangChain-এর RecursiveCharacterTextSplitter-এ মাপ ডিফল্টভাবে character-এ (Python len()), token-এ নয়। Overlap থাকলে সীমানায় পড়া তথ্য অন্তত একটি chunk-এ পুরো থাকে।
  • Recursive: আগে paragraph ("\n\n"), না হলে line, তারপর word, শেষে character দিয়ে কাটে, যাতে অর্থপূর্ণ অংশ যতটা সম্ভব একসাথে থাকে।
  • Structural: MarkdownHeaderTextSplitter header অনুযায়ী ভাগ করে header-কে metadata হিসেবে রাখে; LlamaIndex-এর SentenceSplitter বাক্যের সীমানায় কাটে।
  • Semantic: পাশাপাশি বাক্যের embedding similarity বেশি কমে গেলে সেখানে কাটা হয় (SemanticSplitterNodeParser); এতে অতিরিক্ত embedding খরচ আর threshold ঠিক করার ঝামেলা থাকে।
  • Late chunking: আগে পুরো document long-context model দিয়ে encode করা হয়, তারপর mean pooling-এর ঠিক আগে কাটা হয়। ফলে প্রতিটি chunk vector আশপাশের context জানে; আলাদা training লাগে না, তবে long-context embedding model দরকার।
  • Contextual retrieval: প্রতিটি chunk-এর সামনে LLM দিয়ে লেখা প্রায় 50-100 token-এর context জুড়ে embedding ও BM25 দুটোতেই ব্যবহার করা হয়। Anthropic জানিয়েছে failure rate 5.7% থেকে reranking-সহ 1.9%-এ নেমেছে; ২০০,০০০ token-এর কম knowledge base হলে সবটা prompt-এ দিয়ে দেওয়াই যথেষ্ট।

কখন কোনটা: সহজ লেখায় recursive দিয়ে শুরু করুন; markdown বা structured doc হলে header-ভিত্তিক; chunk একা পড়লে অর্থ হারায় এমন হলে contextual retrieval বা late chunking। কোনো সূত্রে আদর্শ chunk size বলা নেই, তাই নিজের eval দিয়ে ঠিক করুন।

ফাঁদ: token আর character গুলিয়ে ফেলা, header-এর সীমানা পেরিয়ে overlap হওয়া, আর বিক্রেতার নিজস্ব মূল্যায়নের সংখ্যাকে নিজের ডেটার ফল ধরে নেওয়া।

দৈনন্দিন উপমা: চায়ের দোকানে পুরোনো খবরের কাগজ থেকে কাটিং রাখার কথা ভাবুন। ইঞ্চি মেপে কাটলে বাক্য মাঝখানে কেটে যায়; খবরের সীমানা ধরে কাটলে প্রতিটি কাটিং পড়ার মতো থাকে। আর প্রতিটির পেছনে কাগজের নাম ও তারিখ লিখে রাখলে অনেক পরেও বোঝা যায় এটা কোথাকার।

Vector databases: Qdrant, Pinecone, Weaviate, pgvector, Chroma, Milvus

A vector database stores embeddings and answers "which stored vectors are closest to this one?" without comparing against every row. Exact search over millions of vectors is too slow, so these systems build an approximate nearest neighbour (ANN) index, most often the HNSW graph.[6] Six popular options differ less in the core idea than in deployment model, index choices, hybrid-search support and how they isolate tenants. The feature table below is built only from vendor documentation I fetched; the "when to choose" guidance is my own synthesis and is labelled that way.

ANN basics: flat, IVF and HNSW

Flat search is a linear scan: exact, low memory, sensible for small collections (Weaviate suggests it for small per-tenant data).[7] IVF partitions vectors into lists and searches only some of them; in pgvector that is lists at build time and ivfflat.probes (default 1) at query time.[8] HNSW (Malkov and Yashunin) builds multi-layer proximity graphs, similar in spirit to a skip list, with search cost that scales logarithmically.[6]

HNSW search: start at a sparse top layer, take long hops to get near the target, then refine on denser layers down to layer 0.
HNSW-তে উপরের স্তর ফাঁকা, তাই লম্বা লাফে দ্রুত লক্ষ্যের কাছে পৌঁছানো যায়। তারপর প্রতিটি নিচের স্তরে আরও ঘন নোডের মধ্যে খুঁজে layer 0-তে সবচেয়ে কাছের vector পাওয়া যায়।
Three ways to find neighbours: scan everything (flat), scan only the nearest few lists (IVF), or walk a proximity graph (HNSW).
Flat পদ্ধতিতে সব vector-এর সাথে তুলনা হয়, IVF-এ শুধু query-র কাছের কয়েকটি list দেখা হয়, আর HNSW-তে graph ধরে হেঁটে নিকটতম প্রতিবেশী খোঁজা হয়। লাল বিন্দু হলো query।

Distance metrics

pgvector exposes <-> (L2), <#> (negative inner product), <=> (cosine), <+> (L1), <~> (Hamming) and <%> (Jaccard).[8] Milvus lists L2 and IP for float vectors, Jaccard and Hamming for binary vectors, and IP or BM25 for sparse vectors.[9] Weaviate's HFresh index supports only cosine and l2-squared.[7] Match the metric to the one your embedding model was trained for; for unit-length vectors cosine and dot product rank identically.

L2 measures the straight-line gap, cosine measures only the angle, and the dot product mixes angle with vector length.
L2 দুই বিন্দুর সরলরেখার দূরত্ব মাপে, cosine শুধু কোণ মাপে, আর dot product কোণ ও দৈর্ঘ্য দুটোই ধরে। unit-length vector হলে তিনটিই একই ranking দেয়।

🗄️Layman's versionplain English, no jargon

What is a vector database? It is a filing system for meaning. Each document becomes a long list of numbers, and the database finds the lists that look most like the one you ask about.

Why does it matter? Checking every single document for every question would be far too slow. So these systems build a shortcut map that gets you to the right neighbourhood fast, at the cost of occasionally missing the very best match. Different products package this map differently: some are services you rent, some you run yourself, one lives inside an ordinary database.

When does it go wrong? If you add filters like "only this customer's files", a shortcut map that ignores filters can return too few results. And a product that is perfect for a prototype may be awkward at huge scale.

The city map analogy: finding the nearest cafe by walking every street is exact but slow. A map with highways, main roads and side streets lets you zoom in fast. You might miss a tiny cafe on a back lane, but you arrive in seconds.

Vector database কী? Embedding মডেল প্রতিটি টেক্সটকে সংখ্যার একটি vector বানায়। Vector database এই vector জমা রাখে এবং query-র সবচেয়ে কাছের vector গুলো দ্রুত খুঁজে দেয়। সব vector-এর সাথে তুলনা করা ধীর, তাই ANN (approximate nearest neighbour) index ব্যবহার হয়।

  • Flat: সবকিছু একে একে মেলানো; নির্ভুল, কম memory, ছোট collection-এর জন্য উপযুক্ত।
  • IVF: vector-কে lists-এ ভাগ করে query-র সময় শুধু কয়েকটি list দেখা (pgvector-এ ivfflat.probes, ডিফল্ট 1)।
  • HNSW: বহুস্তরীয় proximity graph; উপরের স্তরে লম্বা লাফ, নিচে সূক্ষ্ম খোঁজ; খোঁজার খরচ লগারিদমিক হারে বাড়ে। pgvector-এ ডিফল্ট m = 16, ef_construction = 64, hnsw.ef_search = 40।
  • Distance metric: L2 সরলরেখার দূরত্ব, cosine শুধু কোণ, dot product কোণ ও দৈর্ঘ্য। pgvector-এ <->, <=>, <#>। unit-length vector হলে cosine ও dot product একই ranking দেয়।

Hybrid search (BM25 + vector) & reciprocal rank fusion

Keyword search (BM25) and embedding search fail in opposite ways: BM25 needs the query's exact words to appear, while dense vectors can blur rare identifiers, names and codes. Hybrid search runs both and merges the results. The most common merge is reciprocal rank fusion (RRF), which ignores raw scores and combines only each document's rank in each list.[16] The catch is that the two retrievers' scores live on different scales, which is exactly the problem rank-based fusion sidesteps.

The two retrievers and the parallel pipeline

BM25 comes from the Probabilistic Relevance Framework (grounded in 1970s-80s work); BM25F extends it to document fields such as metadata.[17] It scores exact term matches via an inverted index. Learned sparse models such as SPLADE keep that exact-match, inverted-index efficiency and interpretability but add learned term expansion to handle vocabulary mismatch.[18] A dense retriever embeds the query and finds nearest vectors with an ANN index. Weaviate states that its hybrid search runs the vector and BM25 searches in parallel and then fuses them.[13]

Hybrid search: one query goes to a keyword index and a vector index in parallel, and a fusion step merges the two ranked lists.
একই query একসাথে BM25 (keyword) ও dense vector search-এ যায়। দুটি আলাদা ranked list পাওয়া যায়, তারপর RRF শুধু rank দেখে সেগুলোকে মিলিয়ে একটি fused top-k বানায়।

Reciprocal rank fusion, worked by hand

Cormack, Clarke and Buettcher define the score as the sum, over every ranking that contains the document, of 1 / (k + r(d)), where r(d) is the document's rank. The paper states that "k = 60 was fixed during a pilot investigation and not altered during subsequent validation."[16] Elasticsearch uses score += 1.0 / (k + rank) with rank starting at 1, rank_constant defaulting to 60, and rank_window_size defaulting to the size parameter.[19] OpenSearch added RRF in 2.19 (12 Feb 2025) with a default rank constant of 60.[20] The ranks in the diagram are invented for the arithmetic.

Worked RRF example: doc A leads BM25 but sits at rank 5 in the dense list, so documents ranked well by both retrievers (B, C) overtake it.
এখানে doc A BM25-তে প্রথম কিন্তু dense তালিকায় পঞ্চম, তাই fused স্কোরে B ও C তার চেয়ে এগিয়ে যায়। দুই তালিকাতেই ভালো rank পাওয়া document-ই RRF-এ জেতে। ranks কাল্পনিক, অঙ্কটি নিখুঁত।
Vendors disagree on k: the paper fixed k = 60, and Elasticsearch and OpenSearch default to 60. Qdrant's docs, however, state that RRF's k is "set to 2 by default". Weaviate's rankedFusion uses 1/(RANK+60).[21][13] The same two lists can therefore fuse differently across engines; check the default before comparing results, and set k explicitly where the API allows it.

Rank-based versus score-based fusion

Weaviate's default hybrid method is relativeScoreFusion (default since v1.24), which normalises each search's scores to 0-1 (min-max style) and weights them with alpha (0 is keyword only, 1 is vector only, server default 0.75). It notes there is no max-distance equivalent for BM25 because BM25 scores are unbounded. rankedFusion, the default through v1.23, is the rank-based alternative.[13] Qdrant's Query API supports RRF and DBSF (distribution-based score fusion), added weighted RRF in v1.17.0, and advises RRF as the default when you have no evaluation set.[21]

বাঁয়ে score-ভিত্তিক fusion: score normalise করে alpha দিয়ে ওজন দেওয়া হয়। ডানে RRF: k = 60 হলে rank-10 এর ওজন rank-1-এর 87%, কিন্তু k = 2 হলে মাত্র 25%, অর্থাৎ ছোট k উপরের rank-কে অনেক বেশি গুরুত্ব দেয়।

In code

def rrf(rankings, k=60):
    """rankings: list of ranked doc-id lists, best first. Returns fused ids."""
    scores = {}
    for ranking in rankings:
        for rank, doc in enumerate(ranking, start=1):   # ranks start at 1
            scores[doc] = scores.get(doc, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

🔀Layman's versionplain English, no jargon

What is hybrid search? You ask the same question to two different helpers. One looks for the exact words you typed. The other looks for the meaning, even if the words differ. Then you combine their answers into one list.

Why does it matter? The word-matcher is great at product codes and names but misses rephrased ideas. The meaning-matcher is great at ideas but can fumble exact codes. Together they cover each other's blind spots. To combine, you do not compare their grades, because they grade on different scales. You only look at who each helper put first, second, third, and give points for good positions.

When does it go wrong? If one helper is clearly bad for your data, mixing it in drags results down. And different tools use different point rules, so the same two lists can come out in a different order.

The two-judges analogy: two judges rank talent show contestants, one scoring out of 10 and another out of 1,000. Adding their scores would be silly. Instead you ask who each put first, second and third, and reward contestants that both judges liked, even if neither ranked them number one.

Hybrid search কী? BM25 হলো keyword-ভিত্তিক search: query-র শব্দগুলো document-এ হুবহু আছে কি না তা inverted index দিয়ে মেলায়। Dense vector search অর্থের মিল খোঁজে। দুটোর শক্তি আলাদা, তাই একসাথে চালিয়ে ফল মেলানোকে hybrid search বলে। SPLADE-এর মতো learned sparse মডেল exact-match দক্ষতা রেখে শব্দ সম্প্রসারণও (term expansion) যোগ করে।

RRF কীভাবে কাজ করে: প্রতিটি ranked list-এ document-এর অবস্থান r ধরে স্কোর হয় 1 / (k + r), সব list-এর স্কোর যোগ করা হয়। raw score ব্যবহার হয় না, কারণ BM25 স্কোর unbounded আর vector স্কোর আলাদা স্কেলের।

  • Worked উদাহরণ (k = 60): doc B দুই তালিকাতেই rank 2, তাই 1/62 + 1/62 = 0.032258। doc A BM25-তে প্রথম (1/61) কিন্তু dense-এ পঞ্চম (1/65), মোট 0.031778, তাই A তৃতীয় হয়।
  • k-এর প্রভাব: k = 60-এ rank 10 পায় rank 1-এর প্রায় 87%; k = 2-এ মাত্র 25%। ছোট k উপরের rank-কে বেশি গুরুত্ব দেয়।
  • ভিন্নতা: paper, Elasticsearch ও OpenSearch-এ ডিফল্ট 60, কিন্তু Qdrant docs-এ লেখা আছে ডিফল্ট 2। তাই ইঞ্জিন বদলালে ফলও বদলাতে পারে।

Score-ভিত্তিক বিকল্প: Weaviate-এর ডিফল্ট relativeScoreFusion স্কোর 0-1 করে normalise করে alpha দিয়ে ওজন দেয় (0 = শুধু keyword, 1 = শুধু vector, ডিফল্ট 0.75)। rankedFusion হলো rank-ভিত্তিক বিকল্প। Qdrant RRF ও DBSF দেয়, আর eval set না থাকলে RRF দিয়ে শুরু করতে বলে। Pinecone তিনটি hybrid প্যাটার্ন দেখায় এবং মনে করিয়ে দেয়: RRF একটি fusion পদ্ধতি, hybrid search-এর সমার্থক নয়।

ফাঁদ: একটি retriever নিজের ডেটায় খারাপ হলে মেশালে ফল নামতে পারে; k বা alpha না দেখে ইঞ্জিনের ডিফল্ট ধরে নেওয়া; আর কোনো সূত্রে ইঞ্জিনভিত্তিক benchmark যাচাই করা হয়নি, তাই নিজের eval-এ মেপে নিন।

দৈনন্দিন উপমা: ক্রিকেটে দুজন বিশ্লেষক সেরা ব্যাটসম্যানের তালিকা করলেন, একজন রান দিয়ে, অন্যজন স্ট্রাইক রেট দিয়ে। দুই মাপের সংখ্যা যোগ করা অর্থহীন। বরং কে কার তালিকায় কত নম্বরে আছে সেটা ধরে পয়েন্ট দিন; যে খেলোয়াড় দুই তালিকাতেই ওপরে, সে-ই সামগ্রিক সেরা।

Query rewriting, expansion & HyDE

User queries are short, ambiguous and phrased differently from the documents that answer them. Query transformation puts a step before retrieval that rewrites, broadens, multiplies or even "answers" the query so the retriever has a better string (or vector) to match. Established variants include HyDE[23], step-back prompting[24], Query2doc[25], RAG-Fusion[26] and Rewrite-Retrieve-Read[27]. Each trades one extra LLM call (latency and cost) for a better chance that the right chunk appears in the candidate set.

HyDE: retrieve with a hypothetical answer

HyDE (Hypothetical Document Embeddings) asks an instruction-following LM to write a document that answers the query. The text "captures relevance patterns but is unreal and may contain false details"; an unsupervised contrastive encoder (Contriever) embeds it, and the resulting vector is used for nearest-neighbour search over the real corpus. The authors describe the encoder as a lossy compressor that filters out the hallucinated details, and report gains over the Contriever baseline across web search, QA and fact verification, all without relevance labels.[23]

HyDE: the query is replaced by a generated pseudo-answer; embedding it discards most invented specifics and keeps the "shape" of a relevant document.
HyDE-তে query-র বদলে LLM-এর লেখা একটি কাল্পনিক উত্তর embed করা হয়। encoder সেই লেখা থেকে ভুল খুঁটিনাটি ঝেড়ে ফেলে শুধু প্রাসঙ্গিকতার ধরনটা রাখে, তারপর সেই vector দিয়ে আসল documents খোঁজা হয়।

Step-back, rewriting and expansion

  • Rewrite-Retrieve-Read inserts a rewriting step before retrieval. The rewriter can be a prompted LLM or a small trainable T5 tuned with reinforcement learning, and the reader can stay a frozen black-box LLM. It was tested on HotpotQA, AmbigNQ, PopQA and MMLU.[27]
  • Step-back prompting has two stages: abstraction (derive a higher-level concept or question) and reasoning. With PaLM-2L the authors report +7% on MMLU physics, +11% on chemistry, +27% on TimeQA and +7% on MuSiQue. It is a reasoning method that also covers retrieval-augmented use (TimeQA), not a retrieval trick alone.[24]
  • Query2doc few-shot prompts an LLM for a pseudo-document and concatenates it with the query; for BM25 the original query is repeated several times to balance the weights. Reported: 3-15% BM25 gains on in-domain sets, only 0.4-4% for dense retrievers, and larger LLMs help more.[25]
  • RAG-Fusion generates several query variants, retrieves for each, and fuses the lists with Reciprocal Rank Fusion before the LLM answers.[26]
Query transformations fan one query out into several retrieval strings. You can use one technique or combine several, then fuse the resulting lists.
একটি query থেকে rewrite, step-back, multi-query ও HyDE-এর মতো একাধিক সার্চ স্ট্রিং তৈরি হয়। প্রতিটির জন্য আলাদা retrieval চলে, তারপর ফলাফলের তালিকাগুলো fuse করা হয়।

Multi-query fusion with RRF, worked through

RAG-Fusion scores each document by summing 1/(k + rank) across the lists produced by the query variants.[26] The original paper defining RRF fixed k = 60 in a pilot and did not alter it afterwards[16], and Elasticsearch defaults rank_constant to 60[19]. Vendors differ, though: Qdrant's docs state RRF's k is "set to 2 by default"[21], so check your engine's default before comparing rankings.

Worked RRF: ranks from two query-variant lists are turned into 1/(60 + rank) contributions and summed; agreement across lists decides the order.
দুটি query variant-এর ranking থেকে প্রতিটি document-এর 1/(60 + rank) যোগ করা হয়েছে। Doc B দুই তালিকাতেই ওপরের দিকে থাকায় একটিতে এক নম্বরে থাকা Doc A-কে সামান্য ব্যবধানে হারায়।

def rrf(lists, k=60):

def retrieve(question, n_variants=3, top_k=20):
    variants = llm(f"Write {n_variants} search queries for: {question}").splitlines()
    fake_doc = llm(f"Write a short passage answering: {question}")   # HyDE
    lists = [bm25_search(q, top_k) for q in [question, *variants]]
    lists.append(dense_search(embed(fake_doc), top_k))
    return rrf(lists)[:top_k]

✍️Layman's versionplain English, no jargon

What is it? Before searching your documents, the AI first rewrites your question, or even guesses what a good answer might look like, and searches with that instead.

Why does it matter? People type short, vague questions, while documents are written in full, formal sentences. A better-worded search finds the right page more often. Asking several versions of the question and combining the results catches pages a single wording would miss.

When does it go wrong? If the rewrite changes what you meant, or the guessed answer is confidently wrong, you can end up searching for the wrong thing. It also adds a small wait before the search even starts.

The librarian analogy: you ask "that book about the guy who sailed alone?" A good librarian rephrases it ("solo circumnavigation memoirs"), tries a couple of wordings, and imagines what the blurb of the right book would say. Then she checks the shelves with all of those in hand.

ব্যবহারকারীর প্রশ্ন সাধারণত ছোট ও অস্পষ্ট হয়, অথচ উত্তর থাকে বিস্তারিত নথিতে। তাই retrieval-এর আগে query transformation ধাপ যোগ করা হয়: প্রশ্নটি নতুন করে লেখা, প্রসারিত করা বা একাধিক রূপে ভাঙা হয়, যাতে retriever মেলানোর জন্য ভালো কিছু পায়।

  • HyDE: LLM প্রশ্নের একটি কাল্পনিক উত্তর লেখে। সেটি ভুল তথ্যও ধরতে পারে। encoder (যেমন Contriever) সেই লেখা embed করার সময় ভুল খুঁটিনাটি ছেঁটে প্রাসঙ্গিকতার ধরনটা রাখে, তারপর সেই vector দিয়ে আসল document খোঁজা হয়।
  • Step-back: আগে একটি বড় ও সাধারণ প্রশ্ন করা (abstraction), তারপর যুক্তি দিয়ে উত্তর দেওয়া। এটি মূলত reasoning পদ্ধতি, retrieval-এও কাজে লাগে।
  • Query2doc: LLM-এর বানানো pseudo-document মূল query-র সাথে জুড়ে দেওয়া হয়। BM25-এর ক্ষেত্রে মূল query কয়েকবার পুনরাবৃত্তি করে ওজন ঠিক রাখা হয়। পেপার অনুযায়ী BM25-এ লাভ বেশি, dense retriever-এ কম।
  • RAG-Fusion ও multi-query: কয়েকটি query variant দিয়ে আলাদা আলাদা খোঁজা হয়, তারপর RRF দিয়ে তালিকাগুলো মেলানো হয়।
  • Rewrite-Retrieve-Read: retrieval-এর আগে একটি rewriter বসে; এটি prompt করা LLM বা RL দিয়ে প্রশিক্ষিত ছোট T5 হতে পারে।

কখন কোনটি: BM25-ভিত্তিক সার্চে Query2doc, প্রশ্ন অস্পষ্ট হলে rewrite বা multi-query, ধারণাগত প্রশ্নে step-back, label ছাড়া dense retrieval-এ HyDE। প্রতিটি পদ্ধতিতে একটি বাড়তি LLM কল লাগে, তাই latency ও খরচ বাড়ে।

সতর্কতা: তৈরি করা variant মূল উদ্দেশ্য থেকে সরে যেতে পারে; HyDE-এর কাল্পনিক লেখায় ভুল তথ্য থাকতে পারে। মূল query-টি সবসময় তালিকায় রাখুন এবং নিজের ডেটায় মেপে দেখুন। বিভিন্ন vendor-এর RRF-এর k আলাদা (পেপারে 60, Qdrant-এর docs-এ 2)।

দৈনন্দিন উপমা: চায়ের দোকানে কেউ বলল "ওই যে লম্বা মতো লোকটা, যে গতকাল এসেছিল।" দোকানদার নিজে একটু ঘুরিয়ে ভাবে: কার কথা হতে পারে, নাম কী, কোন পাড়ার। কয়েকজন পরিচিতকে একই কথা আলাদাভাবে জিজ্ঞেস করে, তারপর সবার উত্তর মিলিয়ে সঠিক মানুষটিকে খুঁজে পায়।

Multi-hop retrieval & agentic retrieval

Some questions cannot be answered from one retrieval: the second search depends on what the first one found. Multi-hop benchmarks such as HotpotQA (113k Wikipedia question-answer pairs that require reasoning over multiple documents, with sentence-level supporting facts)[28] exist to test exactly this. Agentic retrieval lets the model itself decide whether to retrieve, what to search for, whether the results are good enough, and when to stop. The price is more LLM calls, more latency and a harder system to debug.

Interleaving retrieval and reasoning (IRCoT, ReAct)

IRCoT alternates retrieval with chain-of-thought steps: the CoT so far guides what to retrieve next, and the retrieved passages improve the following CoT step. The paper reports retrieval gains of 11-21 points and QA gains of up to 15 F1 across HotpotQA, 2WikiMultihopQA, MuSiQue and IIRC, working from 0.2B to 175B models, and up to 50% fewer factual errors in the CoT.[29] ReAct interleaves reasoning traces with actions such as Wikipedia lookups; it reduced hallucination in QA and fact verification and gave +34% / +10% absolute success on ALFWorld / WebShop.[30]

IRCoT-style loop: each reasoning sentence becomes the query for the next retrieval, until the model has enough evidence to answer.
IRCoT-তে প্রতিটি যুক্তির বাক্য পরের retrieval-এর query হয়ে যায়। যথেষ্ট প্রমাণ না পাওয়া পর্যন্ত retrieve করা আর যুক্তি দেওয়ার এই চক্র চলতে থাকে, তারপর চূড়ান্ত উত্তর আসে।
# IRCoT-style loop (sketch). retrieve() and llm() are placeholders.
def ircot(question, max_steps=5, k=4):
    evidence, cot = [], []
    query = question
    for _ in range(max_steps):
        evidence += retrieve(query, k)                    # 1. retrieve with the current query
        step = llm(question, evidence, cot)               # 2. write ONE next reasoning sentence
        cot.append(step)
        if "answer is" in step:                         # 3. stop when the model commits
            return step, evidence
        query = step                                    # 4. last sentence drives the next search
    return llm(question, evidence, cot), evidence

Self-reflection and routing (Self-RAG, CRAG, Adaptive-RAG)

  • Self-RAG: the LM retrieves on demand and critiques both the passages and its own output using special "reflection tokens". The 7B and 13B models are reported to outperform ChatGPT and retrieval-augmented Llama2-chat on open-domain QA, reasoning and fact verification, with better citation accuracy.[31]
  • CRAG (Corrective RAG): a lightweight retrieval evaluator returns a confidence; if the static corpus retrieval is inadequate, it falls back to large-scale web search, and a decompose-then-recompose step filters noise. It is plug-and-play over an existing RAG pipeline.[32]
  • Adaptive-RAG: a smaller LM classifier predicts query complexity and routes among no retrieval, single-step retrieval and iterative retrieval, improving efficiency and accuracy against adaptive baselines (NAACL 2024).[33]
Two control patterns: Adaptive-RAG spends retrieval effort according to predicted query complexity; CRAG checks retrieval quality and repairs it with web search when the corpus falls short.
বাঁ দিকে Adaptive-RAG প্রশ্নের জটিলতা অনুযায়ী retrieval ছাড়া, এক ধাপ বা বহু ধাপের পথ বেছে নেয়। ডান দিকে CRAG retrieval-এর মান যাচাই করে, অপর্যাপ্ত হলে web search-এ যায়।

Agentic retrieval and its cost

Anthropic distinguishes workflows (LLMs and tools orchestrated through predefined code paths) from agents (the LLM directs its own process and tool use), and recommends starting simple because a single optimized LLM call with retrieval is often enough; it also stresses investing in tool definitions.[34] OpenAI's file_search tool in the Responses API is a hosted retrieval tool the model chooses to invoke, doing semantic and keyword search over vector stores, with max_num_results and metadata filters; its docs do not detail internal query rewriting or ranking.[35]

In Anthropic's multi-agent research system a lead agent spawns parallel subagents that search iteratively. They report agents using about 4x the tokens of chat and multi-agent systems about 15x, token usage explaining 80% of performance variance on a browsing evaluation, and an Opus 4 lead with Sonnet 4 subagents beating single-agent Opus 4 by 90.2% on their internal evaluation.[36]

Orchestrator-worker agentic search and its cost: parallel subagents explore more, but token use climbs roughly 4x for an agent and 15x for a multi-agent system relative to chat.
একটি lead agent কয়েকটি subagent-কে সমান্তরালে খুঁজতে পাঠায়। Anthropic-এর রিপোর্ট অনুযায়ী chat-এর তুলনায় agent প্রায় 4 গুণ এবং multi-agent প্রায় 15 গুণ token খরচ করে।

🕵️Layman's versionplain English, no jargon

What is it? Some questions need a chain of lookups: first find who directed a film, then find where that person was born. The AI learns to search, read, think, and search again, instead of searching once.

Why does it matter? One search cannot answer a question whose second half depends on the first answer. Letting the AI decide when to search again, when to skip searching, or when to try the wider internet makes answers more complete.

When does it go wrong? Every extra round costs time and money. A confused AI can keep searching in circles, so you need a limit. Often a single good search is enough, and the extra machinery just slows things down.

The detective analogy: a detective does not solve a case with one question. A first witness gives a name, the name leads to a second witness, and so on. A good detective also knows when to stop asking. A team of detectives works faster, but you pay for all of them.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Multi-hop প্রশ্ন মানে এমন প্রশ্ন যার উত্তর পেতে একাধিক document জুড়ে ধাপে ধাপে যেতে হয়; দ্বিতীয় খোঁজ নির্ভর করে প্রথম ফলাফলের ওপর। বেঞ্চমার্ক হিসেবে HotpotQA বহুল ব্যবহৃত: এতে ১১৩ হাজার Wikipedia প্রশ্নোত্তর আছে এবং বাক্যস্তরের supporting facts দেওয়া। Agentic retrieval-এ মডেল নিজেই ঠিক করে retrieve করবে কি না, কী খুঁজবে, ফল যথেষ্ট কি না।

  • IRCoT: chain-of-thought-এর প্রতিটি বাক্য পরের খোঁজের query হয়; পেপারে retrieval-এ ১১-২১ পয়েন্ট ও QA-তে সর্বোচ্চ ১৫ F1 উন্নতির কথা আছে।
  • ReAct: reasoning ও action (যেমন Wikipedia lookup) মিশিয়ে চলে, ফলে hallucination কমে।
  • Self-RAG: মডেল reflection tokens দিয়ে নিজেই ঠিক করে কখন retrieve করবে এবং নিজের উত্তর যাচাই করে।
  • CRAG: একটি evaluator retrieval-এর আস্থা মাপে; অপর্যাপ্ত হলে web search-এ ফিরে যায়।
  • Adaptive-RAG: ছোট classifier প্রশ্নের জটিলতা দেখে retrieval-ছাড়া, এক-ধাপ বা বহু-ধাপের পথ বেছে দেয়।

ট্রেড-অফ: Anthropic-এর রিপোর্টে agent প্রায় 4x ও multi-agent প্রায় 15x token খরচ করে। তাই সহজ প্রশ্নে এক ধাপের retrieval দিয়ে শুরু করুন, শুধু যেসব প্রশ্ন তাতে ব্যর্থ হয় সেখানে loop বা agent যোগ করুন।

সতর্কতা: loop-এ সর্বোচ্চ ধাপ ও থামার শর্ত না থাকলে মডেল ঘুরপাক খেতে পারে; classifier ভুল করলে প্রশ্ন ভুল পথে যায়; কত খরচ হচ্ছে তা প্রতি উত্তরে মাপুন।

দৈনন্দিন উপমা: ঢাকায় অচেনা ঠিকানা খুঁজতে গিয়ে আপনি মোড়ের দোকানদারকে জিজ্ঞেস করেন, সে বলে "ওই গলির রিকশাওয়ালাকে জিজ্ঞেস করো", তার কাছ থেকে আরেকজনের খোঁজ মেলে। প্রতিটি উত্তর পরের প্রশ্ন ঠিক করে দেয়। বেশি লোককে একসাথে পাঠালে তাড়াতাড়ি হয়, তবে রিকশাভাড়াও বেশি লাগে।

GraphRAG & knowledge-graph augmentation

Vector search returns chunks that look like the query. It struggles with "global" questions such as "what are the main themes in this dataset?", which no single chunk answers. Microsoft's GraphRAG reframes this as query-focused summarization: an LLM builds an entity knowledge graph, pre-generates summaries for communities of related entities, and merges partial answers from those summaries at query time.[37] Lighter variants (LightRAG[38], HippoRAG[39]) and graph-database tooling (Neo4j[40]) target the same gap with different cost profiles.

Microsoft GraphRAG: index, then local or global search

The documented indexing pipeline segments documents into TextUnits, extracts entities, relationships and claims, runs Leiden hierarchical clustering, and summarizes each community. Query modes include Global search (reasoning over community summaries), Local search (expanding from matched entities to their neighbours) and DRIFT (local search enriched with community context). The docs recommend prompt tuning.[41] The original paper tested on corpora of about 1M tokens and reported gains in answer comprehensiveness and diversity over standard RAG.[37]

GraphRAG indexing: the documented pipeline turns raw text into a graph, clusters it with Leiden, and has an LLM summarize every community. The LLM-heavy steps dominate cost.
GraphRAG indexing-এ text ছোট ছোট TextUnit হয়, LLM entity ও সম্পর্ক বের করে graph বানায়, Leiden দিয়ে community ভাগ হয় এবং প্রতিটির summary লেখা হয়। LLM-নির্ভর ধাপগুলোতেই বেশি খরচ।
Same graph, two query paths: local search walks outward from specific entities; global search answers from pre-written community summaries and merges the partial answers.
একই graph-এ দুই ধরনের খোঁজ: local search নির্দিষ্ট entity থেকে প্রতিবেশীদের দিকে যায়; global search আগে থেকে লেখা community summary থেকে আংশিক উত্তর তৈরি করে তা মিলিয়ে একটি উত্তর দেয়।

Lighter alternatives: LightRAG, HippoRAG, Neo4j

  • LightRAG builds graph structures into both indexing and retrieval, with dual-level (low-level and high-level) retrieval, combines graph and vector retrieval, supports incremental updates, and is open source.[38]
  • HippoRAG is hippocampus-inspired: an LLM, a knowledge graph and Personalized PageRank. It reports up to 20% better multi-hop QA, and single-step retrieval comparable to or better than iterative retrieval while 10-30x cheaper and 6-13x faster.[39]
  • Neo4j's neo4j-graphrag Python package is Neo4j's official GraphRAG library (successor to neo4j-genai): a knowledge-graph builder, retrievers (VectorRetriever and others), and a GraphRAG class. It needs Neo4j 5.18.1 or later and supports LLM providers including OpenAI, Anthropic, Cohere, Mistral, Vertex AI and Ollama, plus external vector stores such as Weaviate, Pinecone and Qdrant.[40]
# neo4j-graphrag: vector retrieval wrapped by a RAG class (sketch; check the docs for exact setup)
from neo4j import GraphDatabase
from neo4j_graphrag.retrievers import VectorRetriever
from neo4j_graphrag.generation import GraphRAG

driver = GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "password"))
retriever = VectorRetriever(driver, index_name="chunk_embeddings", embedder=my_embedder)
rag = GraphRAG(retriever=retriever, llm=my_llm)       # my_embedder / my_llm: provider wrappers
answer = rag.search(query_text="Which suppliers connect to both plants?")

The following is my synthesis from the sources above, not a measured result. Global, whole-corpus sensemaking questions and multi-hop questions about connected entities are where the graph papers report their gains[37][39]. The cost is LLM extraction and summarization at index time, which Microsoft itself warns can be expensive[42]. LightRAG and HippoRAG emphasize incremental updates and cheaper retrieval respectively[38][39]. For simple point lookups, a plain vector or hybrid pipeline is the natural default.

Synthesis, not a benchmark: match the retrieval structure to the question type, and expect index-time cost to rise as you add graph extraction and summarization.

What is it? Instead of only keeping a pile of text snippets, the AI also draws a map of who and what is connected to whom: people, companies, places, and how they relate. It can then read the map to answer questions.

Why does it matter? Ordinary search finds the page that looks like your question. It cannot easily answer "what are the big themes across all 5,000 reports?" because no single page says that. A map, grouped into neighbourhoods that each have a short summary, can.

When does it go wrong? Building the map means the AI reads everything and takes notes, which is slow and expensive. If it misses or confuses names, the map is wrong. For simple "what does page 12 say?" questions, the map is overkill.

The city map analogy: a list of street names tells you where one street is. A city map with neighbourhood labels tells you how the districts connect and what each one is known for. Drawing that map costs a lot of surveying, so do it only when you need the big picture.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

সাধারণ vector search এমন chunk আনে যা প্রশ্নের সাথে মেলে। কিন্তু "এই পুরো ডেটাসেটের প্রধান থিম কী?"-র মতো global প্রশ্নের উত্তর কোনো একটি chunk-এ থাকে না। Microsoft GraphRAG এটিকে query-focused summarization হিসেবে দেখে: LLM entity-র একটি knowledge graph বানায়, সম্পর্কিত entity-র community-গুলোর summary আগেই তৈরি করে রাখে, আর প্রশ্নের সময় সেই summary থেকে আংশিক উত্তর নিয়ে একত্র করে।

  • Indexing: document থেকে TextUnits, তারপর entity/relationship/claim extraction, Leiden hierarchical clustering এবং community summarization।
  • Query mode: Global search (community summary), Local search (entity থেকে প্রতিবেশীতে সম্প্রসারণ), DRIFT (local সাথে community context)।
  • LightRAG: graph ও vector মেশায়, dual-level retrieval করে, incremental update সমর্থন করে।
  • HippoRAG: LLM, knowledge graph ও Personalized PageRank; পেপারে multi-hop QA-তে সর্বোচ্চ ২০% উন্নতি এবং iterative retrieval-এর চেয়ে ১০-৩০ গুণ সস্তা ও ৬-১৩ গুণ দ্রুত বলা হয়েছে।
  • Neo4j: neo4j-graphrag প্যাকেজে KG builder, retriever ও GraphRAG ক্লাস আছে; Neo4j 5.18.1 বা পরবর্তী সংস্করণ লাগে।

কখন কোনটি (সংশ্লেষণ): একক তথ্যের প্রশ্নে vector বা hybrid RAG যথেষ্ট; সংযুক্ত entity-র multi-hop প্রশ্নে local বা HippoRAG-ধাঁচ; পুরো corpus-এর থিমে community summary। খরচের বড় অংশ index-এর সময়ের LLM extraction ও summarization, যা Microsoft নিজেই ব্যয়বহুল বলেছে, তাই ছোট অংশ দিয়ে শুরু করুন।

সতর্কতা: extraction-এ entity মিস বা গুলিয়ে গেলে পুরো graph ভুল হয়; document বদলালে summary পুরোনো হয়ে যায়।

দৈনন্দিন উপমা: একটি বাজারে কোন দোকান কোথায় তা জানতে সূচিপত্র যথেষ্ট। কিন্তু "এই বাজারে কোন পাড়ায় কী বিখ্যাত?" জানতে চাইলে পাড়াভিত্তিক মানচিত্র আর প্রতিটি পাড়ার সংক্ষিপ্ত পরিচয় লাগে। মানচিত্র আঁকতে অনেক ঘোরাঘুরি করতে হয়, তাই ছোট এলাকা দিয়ে শুরু করাই ভালো।

Reranking: Cohere, BGE, Voyage

First-stage retrieval (BM25, dense vectors, or both) is built to be fast over a huge corpus, so it scores each document without ever looking at the query and document together. A reranker is a second-stage model that does look at them together: it takes the short candidate list and re-orders it by a more accurate relevance score. Sentence-Transformers documents this as the recommended pattern: a bi-encoder retrieves top-k candidates, then a cross-encoder re-ranks them.[43] Hosted options include Cohere Rerank and Voyage rerankers; open weights include BAAI's BGE rerankers.[44][45][46]

Three ways to score a (query, document) pair

Where the query and document meet: never until the final cosine (bi-encoder), inside every attention layer (cross-encoder), or at token level via MaxSim after independent encoding (ColBERT).
তিন ধরনের মডেলে query ও document কোথায় মিলিত হয় তা দেখানো হয়েছে: bi-encoder-এ একদম শেষে cosine-এ, cross-encoder-এ পুরো attention-এর ভেতরে একসাথে, আর ColBERT-এ আলাদা encode করে token স্তরে MaxSim দিয়ে।

Bi-encoder vs cross-encoder vs late interaction

Per the Sentence-Transformers docs, a bi-encoder embeds each text independently and compares vectors with cosine similarity, while a cross-encoder processes the pair jointly and outputs a score; it produces no reusable embedding, and it is more accurate but slower.[43] The same docs give a concrete cost example: clustering 10,000 sentences with a cross-encoder needs about 50 million pairwise comparisons, roughly 65 hours.[43] BGE describes its reranker the same way: it takes the question and document as input and directly outputs a similarity, not an embedding, and a full system is a first-stage retriever followed by the reranker.[47]

ColBERT sits in between. Query and document are encoded independently by BERT, so document representations can be computed offline, and the score is MaxSim: for each query token take the maximum cosine against the document's token vectors, then sum.[48] The paper reports about 170x faster and 14,000x fewer FLOPs per query than BERT rerankers at competitive quality on MS MARCO and TREC CAR, and shows it used either as a reranker over BM25 top-1000 or end-to-end with FAISS.[48]

MaxSim on a toy grid: every query token keeps only its best-matching document token, and the per-token maxima are summed into the document score.
MaxSim-এর একটি ছোট উদাহরণ: প্রতিটি query token শুধু document-এর সবচেয়ে মিলে যাওয়া token-টির মান রাখে, তারপর সেই সর্বোচ্চ মানগুলো যোগ করে document-এর score হয়। সংখ্যাগুলো উদাহরণের জন্য বানানো।

The two-stage funnel

Two-stage funnel: a cheap first stage maximises recall over the whole corpus, then a reranker spends its per-pair cost only on the N survivors before the top-k go to the LLM.
দুই ধাপের funnel: প্রথম ধাপ সস্তা উপায়ে পুরো corpus থেকে প্রার্থী আনে (recall), দ্বিতীয় ধাপে reranker শুধু সেই N-টি প্রার্থীর ওপর বেশি খরচ করে নিখুঁতভাবে সাজায় (precision), এবং সেরা top-k LLM-এর কাছে যায়।

The sizing of N and k is an engineering choice you tune against your own evaluation set. The vendor and paper limits above are hard ceilings; the commonly quoted "retrieve 50 to 100, keep 5 to 10" is practitioner folklore that none of the pages cited here state, so treat it as a starting point, not a rule. Because cross-encoder cost is linear in N, doubling N roughly doubles reranking latency and cost (this follows from one forward pass per pair).

Pitfalls. Scores from different rerankers are not on a common scale, so pick any score threshold per model and per corpus. Long documents get truncated or cut by token limits (for example Cohere's max_tokens_per_doc, Voyage's truncation), so rerank chunks, not whole files. A reranker can only re-order what stage 1 returned: if the right passage is not in the top-N, no reranker can recover it.
Research frontier: ColBERT showed that you can keep cross-encoder-like token-level matching while precomputing document representations: about 170x faster and 14,000x fewer FLOPs per query than BERT rerankers, at competitive quality on MS MARCO and TREC CAR.[48] Qdrant exposes the same idea operationally: prefetch cheap dense candidates, then rescore the top candidates with a multivector (ColBERT-style) model.[21] Limits: late interaction stores one vector per token, which costs index space, and the speed figures are from the paper's own setup, not your hardware.

🏅Layman's versionplain English, no jargon

What is it? A reranker is a careful second look. A quick search first pulls out a pile of documents that might answer your question, then the reranker reads your question next to each one and sorts the pile from best to worst.

Why does it matter? The quick search is fast because it never reads your question and a document side by side. That makes it good at not missing things, but sloppy at putting the best one first. Since the AI only has room for a few passages, getting the best ones on top is what decides whether the answer is good.

When does it go wrong? It is slower and costs money for every document you ask it to read, so you can only afford to show it a short pile. And if the right document never made it into the pile, the second look cannot rescue it.

The talent-show analogy: the first round is a quick audition where judges glance at hundreds of acts and pick a few dozen. The final round has the judges watch each remaining act properly, one at a time, and rank them. You cannot hold the long final for everyone, and you cannot crown someone who was cut in the first round.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Reranker কী? প্রথম ধাপের retrieval (BM25 বা dense vector) দ্রুত অনেক document আনে, কিন্তু সেরাটিকে সবার ওপরে বসাতে পারে না। Reranker হলো দ্বিতীয় ধাপের মডেল, যা ওই ছোট candidate তালিকাটি আরও নিখুঁত relevance score দিয়ে নতুন করে সাজায়। Sentence-Transformers-এর পরামর্শও তাই: bi-encoder দিয়ে top-k আনো, তারপর cross-encoder দিয়ে re-rank করো।

তিন ধরনের মডেল:

  • Bi-encoder: query ও document আলাদাভাবে vector হয়, শেষে cosine মাপা হয়। document vector আগে থেকে তৈরি থাকে, তাই দ্রুত।
  • Cross-encoder: query ও document একসাথে এক transformer-এ ঢোকে এবং সরাসরি একটি score দেয়। reusable embedding তৈরি হয় না; বেশি নিখুঁত কিন্তু ধীর। Sentence-Transformers-এর উদাহরণে ১০,০০০ বাক্য cluster করতে প্রায় ৫ কোটি তুলনা (প্রায় ৬৫ ঘণ্টা) লাগে।
  • ColBERT (late interaction): আলাদা encode হয়, কিন্তু token স্তরে MaxSim হিসাব হয়: প্রতিটি query token-এর জন্য document-এর সবচেয়ে মিলে যাওয়া token-এর cosine নিয়ে সেগুলো যোগ করা হয়।

API ও সীমা: Cohere-তে model, query, documents লাগে (সর্বোচ্চ ১,০০০ document সুপারিশকৃত), top_n ঐচ্ছিক, আর max_tokens_per_doc-এর default ৪,০৯৬। Voyage-এর endpoint /v1/rerank, document সর্বোচ্চ ১,০০০টি এবং মোট ৬ লাখ token, top_k ও truncation প্যারামিটার আছে। BGE-র bge-reranker-v2-m3 নিজের মেশিনে চালানো যায়; sigmoid দিয়ে score [0, 1]-এ আনা যায়, আর use_fp16 গতি বাড়ায়।

কখন কী: সাধারণ নিয়ম হলো পুরো corpus-এ সস্তা retrieval, তারপর অল্প সংখ্যক candidate-এ reranker। "৫০–১০০টি আনো, ৫–১০টি রাখো" কথাটি প্রচলিত অভ্যাস মাত্র, কোনো vendor-এর নথিতে এটি লেখা নেই। নিজের evaluation set দিয়ে N ও k ঠিক করো।

সতর্কতা: প্রথম ধাপে যে document আসেনি, reranker তা ফেরাতে পারে না। আলাদা reranker-এর score একই স্কেলে নয়, তাই threshold মডেল ধরে ঠিক করো। লম্বা document কাটা পড়তে পারে, তাই পুরো ফাইলের বদলে chunk rerank করো।

দৈনন্দিন উপমা: চায়ের দোকানে বা বইমেলায় আপনি প্রথমে স্টলের নাম দেখে দ্রুত বিশটি স্টল বেছে নিলেন। তারপর সেই বিশটিতে ঢুকে প্রতিটি বই হাতে নিয়ে মিলিয়ে দেখলেন কোনটি সত্যিই আপনার দরকারের। প্রথম বাছাই ছিল দ্রুত, দ্বিতীয়টি ধীর কিন্তু নিখুঁত; আর যে স্টল প্রথমেই বাদ পড়েছে, সেখানে আর ফেরা হয় না।

Metadata filtering & structured retrieval

Real questions mix meaning with constraints: "refund policy for enterprise customers in 2025" or "science-fiction movies after 2000 with rating above 8". Vector similarity alone cannot enforce year > 2000, so production retrieval attaches metadata to each chunk and filters on it, and for questions about counts or totals it hands the job to a database. The hard part is that a filter interacts badly with approximate nearest-neighbour (ANN) indexes, and each vector database handles that differently.[50][51]

Pre-filter, post-filter, and filtering inside the graph

Three strategies for combining an ANN search with a metadata filter and how each one fails or costs extra.
ANN search-এর সাথে metadata filter মেলানোর তিনটি পদ্ধতি: আগে filter করলে graph-এর link ভেঙে accuracy কমে, পরে filter করলে k-এর চেয়ে কম (এমনকি শূন্য) ফল আসতে পারে, আর graph চলার সময় filter দেখলে k-টি ঠিক ফল মেলে কিন্তু বেশি node ঘুরতে হয়।

Qdrant's filtering guide states the trade-off plainly: at scale, pre-filtering "breaks too many links in the HNSW graph, causing lower accuracy", while post-filtering with a low-cardinality filter means you often end up discarding a large portion of the results.[50] Its answer is filterable HNSW, which adds links between the leftover points, plus a payload index that lets it switch from HNSW to a payload-index search when the filter's cardinality is low.[50] A newer Qdrant post describes in-place filtering during HNSW traversal, filterable HNSW with extra index-time edges, and ACORN as a query-time repair, with a query planner choosing the path from estimated selectivity.[52]

Why a strict filter hurts HNSW: matching points are only reachable through filtered-out ones. Extra links between matches, or query-time expansion, restore connectivity.
কড়া filter দিলে HNSW graph-এ মিলে যাওয়া node-গুলো শুধু বাদ পড়া node-এর মধ্য দিয়ে পৌঁছানো যায়, তাই খোঁজ আটকে যায়। মিলে যাওয়া node-দের মধ্যে বাড়তি link (filterable HNSW) বা query-time expansion (ACORN) যোগ করলে graph আবার সংযুক্ত হয়। ছবিটি সরলীকৃত স্কেচ।

Self-querying: let the LLM write the filter

Users type natural language, not filter JSON. A self-querying retriever has an LLM parse the request into a semantic query plus a structured metadata filter, then runs both against embeddings and metadata; Elastic's example is "science fiction movies released after 2000 with rating above 8".[55] The LLM must be told the available fields, their types, and the allowed operators, and its output should be validated against that schema before it reaches the database.

# 1) LLM turns text into {query, filter}  (llm_json = your structured-output call)
parsed = llm_json(
    "Fields: genre(str), year(int), rating(float). "
    "Return JSON {query, filter} for: sci-fi movies after 2000 rated above 8"
)
# parsed = {"query": "science fiction",
#           "filter": {"$and": [{"genre": {"$eq": "sci-fi"}},
#                               {"year": {"$gt": 2000}}, {"rating": {"$gt": 8}}]}}

# 2a) Pinecone: filter goes straight into the query
res = index.query(vector=embed(parsed["query"]), top_k=5,
                  filter=parsed["filter"], include_metadata=True)

# 2b) Elasticsearch: put the filter INSIDE knn so k matching docs return
body = {"knn": {
    "field": "embedding", "query_vector": embed(parsed["query"]),
    "k": 5, "num_candidates": 50,
    "filter": {"range": {"year": {"gt": 2000}}},
}}

প্রশ্নের ধরন দেখে পথ বেছে নেওয়ার গাছ: গণনা বা যোগফলের মতো নিখুঁত প্রশ্ন যায় text-to-SQL-এ, অস্পষ্ট অর্থের প্রশ্ন vector search-এ, অর্থ ও শর্ত মেশানো প্রশ্ন self-query filtered search-এ, আর মিশ্র প্রশ্নে দুটোই চলে। এই গাছটি ডিজাইনের সারসংক্ষেপ, কোনো উৎস থেকে নেওয়া মানদণ্ড নয়।

Spider's 2018 figure of 9.7% for the best model is a historical baseline showing how hard cross-domain SQL generation was then, not a statement about current models.[56] In practice, give the model the schema, validate generated SQL (read-only credentials, allow-listed tables, row limits) and log every query.

Research frontier: The ACORN paper (arXiv 2403.04871) frames the problem: pre-filtering scans the filtered set exhaustively and scales poorly, post-filtering has to expand the search when the predicate is uncorrelated with vector similarity. ACORN modifies HNSW to traverse the predicate subgraph, and claims 2 to 1,000 times higher throughput at fixed recall.[57] Elasticsearch and Weaviate have since exposed ACORN-style handling in their docs.[53][51] Limits: the throughput range is the paper's own claim across its workloads, and how well any engine copes still depends on filter selectivity and correlation with the query.
গবেষণার সারকথা: ACORN HNSW-কে এমনভাবে বদলায় যাতে filter-এ মিলে যাওয়া অংশের graph ধরে চলা যায়; paper-এর দাবি একই recall-এ ২ থেকে ১,০০০ গুণ বেশি throughput, তবে ফল নির্ভর করে filter কতটা কড়া তার ওপর।
🗂️Layman's versionplain English, no jargon

What is it? Every piece of text in a knowledge base can carry labels, like year, department or customer type. Metadata filtering means "only look at the ones with the right labels", so you search for meaning inside a smaller, correct set.

Why does it matter? Meaning-based search is fuzzy. It happily returns a 2019 policy when you asked about 2025. Labels give you hard rules, and for questions like "how many orders last month" you skip searching text altogether and ask a database.

When does it go wrong? If you filter after searching, a strict rule can wipe out almost everything and leave you with two results or none. If you filter before, the search can lose its way. Good systems are built to avoid both, and you should still check how many results came back.

The shopping-site analogy: typing "comfortable running shoes" is the fuzzy part, and ticking "size 9, under $80" is the filter. A bad site finds the 10 most comfortable shoes in the world and then hides the ones that are not size 9, leaving you nothing. A good one only looks at size-9 shoes to begin with.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

মূল ধারণা: প্রতিটি chunk-এর সাথে metadata (যেমন year, department, customer_type) রাখা হয়। শুধু vector similarity দিয়ে "২০০০ সালের পরে" বা "rating ৮-এর বেশি"-র মতো কঠিন শর্ত মানানো যায় না, তাই similarity search-এর সাথে metadata filter জুড়ে দেওয়া হয়।

তিনটি পদ্ধতি:

  • Pre-filter: আগে মিলে যাওয়া point রেখে বাকি graph বাদ দেওয়া। Qdrant বলছে, বড় স্কেলে এতে HNSW graph-এর অনেক link ভেঙে accuracy কমে।
  • Post-filter: আগে ANN চালিয়ে পরে filter। কড়া filter হলে অনেক ফল বাদ পড়ে, ফলে k-এর চেয়ে কম বা শূন্য ফল আসতে পারে।
  • In-graph filter: graph চলার সময়ই filter দেখা (allow-list)। k-টি মিলে যাওয়া ফল পাওয়া যায়, কিন্তু বেশি node ঘুরতে হয়। Qdrant-এর filterable HNSW মিলে যাওয়া point-দের মধ্যে বাড়তি link বসায়, আর ACORN query-time-এ সংযোগ মেরামত করে।

Engine-ভেদে আচরণ: Weaviate inverted index থেকে allow-list বানিয়ে HNSW-কে দেয় (v1.34+ থেকে ACORN default) এবং খুব কড়া filter-এ brute force-এ নামে। Elasticsearch-এ knn clause-এর ভেতরে filter দিলে k-টি মিলে যাওয়া ফল আসে, বাইরে দিলে post-filter হয়ে কম আসতে পারে। Pinecone-এ $eq, $gt, $in, $and, $or ইত্যাদি operator আছে; $in/$nin-এ সর্বোচ্চ ১০,০০০ মান।

Self-query ও text-to-SQL: self-query-তে LLM প্রাকৃতিক ভাষার প্রশ্ন ভেঙে একটি semantic query ও একটি structured filter বানায়। গণনা, যোগফল বা join-এর মতো প্রশ্ন similarity-র নয়, সেগুলো text-to-SQL-এ যায়; Spider benchmark-এ ২০০টি database ও ১০,১৮১টি প্রশ্ন আছে। প্রশ্নের ধরন দেখে পথ ঠিক করতে router ব্যবহার করা হয়।

সতর্কতা: ফল কয়টি এল তা সবসময় দেখুন, শূন্য ফলে LLM ফাঁকা থেকে উত্তর বানাতে পারে। যে field-এ filter দেবেন সেটির index রাখুন। LLM-এর বানানো SQL বা filter যাচাই করে read-only অধিকারে চালান।

দৈনন্দিন উপমা: বাজারে গিয়ে আপনি বললেন "ভালো ইলিশ চাই, এক কেজির নিচে নয়"। বোকা দোকানি পুরো বাজারের সেরা দশটি মাছ আলাদা করে তারপর দেখে একটাও এক কেজির নয়, আপনি খালি হাতে ফিরলেন (post-filter)। চালাক দোকানি শুরুতেই এক কেজির ওপরের ইলিশের ঝুড়ি থেকে সেরাটি বাছে (filter সহ search)। আর "আজ কয়টা ইলিশ বিক্রি হলো" জানতে চাইলে মাছ না দেখে খাতা খুলতে হয়, সেটাই text-to-SQL।

Document parsing pipelines: Unstructured, LlamaParse, Docling

A RAG system is only as good as the text it indexes, and most enterprise knowledge sits in PDFs, scans, slide decks and spreadsheets, not clean strings. A parsing pipeline turns those files into structured elements (headings, paragraphs, tables, figures) and then into Markdown or JSON that a chunker can split sensibly. Three widely used options are Docling (IBM Research, MIT-licensed)[58], the Unstructured open-source partitioner[59] and LlamaParse from LlamaIndex[60].

The canonical pipeline

A parser detects page layout, recovers text (with OCR for scans) and table structure, emits structured Markdown or JSON, and only then is the result chunked.
PDF থেকে প্রথমে layout বোঝা হয়, তারপর OCR ও table structure বের করা হয়, শেষে structured Markdown/JSON হয়ে chunk-এ ভাগ হয়। এই ধাপ দুর্বল হলে পরের সব ধাপের মান নেমে যায়।

📄Layman's versionplain English, no jargon

What is it? Before an AI can answer questions from your documents, something has to read them first. A parser is that reader: it looks at each page and works out which part is a title, which is a paragraph and which is a table.

Why does it matter? If the reader garbles the page, the AI only ever sees the garbled version. Everything after that, searching and answering, builds on those mistakes.

When does it go wrong? Photos of paper, pages with two columns, and tables full of numbers are the usual troublemakers. A simple reader might skip a scanned page entirely or mix up the order of the columns.

The note-taker analogy: imagine a student who must copy a textbook into tidy notes for a friend. If the student copies a two-column page straight across the lines, the notes make no sense, and the friend studies nonsense with total confidence.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

RAG সিস্টেমে সবার আগে নথি পড়তে হয়। বেশিরভাগ প্রতিষ্ঠানের জ্ঞান থাকে PDF, scan, slide ও spreadsheet-এ, সাজানো টেক্সটে নয়। Parsing pipeline এই ফাইলগুলোকে heading, paragraph, table, figure-এর মতো structured element-এ ভেঙে Markdown বা JSON বানায়, তারপর সেটা chunk করা হয়।

পাইপলাইনের ধাপ: PDF → layout analysis (কোথায় কী আছে ও পড়ার ক্রম) → OCR ও table structure → structured Markdown/JSON → chunks।

  • Docling: IBM Research-এর MIT-licensed টুল। layout-এর জন্য DocLayNet, table-এর জন্য TableFormer। PDF, DOCX, PPTX, XLSX, HTML ইত্যাদি পড়ে, DoclingDocument থেকে Markdown/HTML/JSON export করে, local বা on-prem চলে।
  • Unstructured: চারটি strategy: auto (ডিফল্ট), fast (pdfminer, text layer লাগে), hi_res (layout model), ocr_only (scan-এর জন্য)। ফলাফল Title, NarrativeText, Table ইত্যাদি typed element।
  • LlamaParse: layout-aware OCR, cell structure ধরে রাখা table extraction, chart parsing, প্রাকৃতিক ভাষায় instruction, এবং Fast থেকে Agentic Plus পর্যন্ত tier।

কখন কোনটা: শুধু text থাকা সরল PDF-এ fast যথেষ্ট; table দরকার হলে hi_res বা Docling; scan হলে OCR আবশ্যক। নিজের নথির নমুনায় তিনটিই পরীক্ষা করে নেওয়াই নিরাপদ।

সতর্কতা: text layer ছাড়া scan-এ fast ব্যর্থ হয়; multi-column পাতায় hi_res কষ্ট করে; আর শুধু text extraction ছবি, layout, table ও font হারায়। তাই OCR fallback রাখুন এবং আউটপুট চোখে দেখে নিন।

দৈনন্দিন উপমা: পুরোনো খাতার হিসাব কম্পিউটারে তুলতে দোকানের কর্মচারীকে দিলেন। সে যদি দুই কলামের পাতা লাইন ধরে আড়াআড়ি টুকে ফেলে, তাহলে হিসাব গুলিয়ে যাবে। তাই কাজ শুরুর আগে দেখে নিতে হয় সে কলাম ঠিকমতো আলাদা করছে কি না।

Multimodal RAG: images, tables, charts

Text-only RAG goes blind the moment the answer lives in a chart, a scanned table or a slide. Multimodal RAG keeps those objects searchable. There are three broad designs: turn everything into text, embed images directly into a shared vector space, or retrieve page images with late interaction and let a vision-capable model read them.[63][62]

Three architectures

The three options described by LangChain: embed raw images with a multimodal embedder, embed LLM-written summaries, or embed summaries while keeping a pointer to the raw object for the answer step.
তিনটি পদ্ধতি: (১) CLIP-ধরনের embedder দিয়ে সরাসরি ছবি embed করা, (২) ছবি বা table-এর LLM summary টেক্সট হিসেবে embed করা, (৩) summary দিয়ে খোঁজা কিন্তু উত্তর দেওয়ার সময় মূল ছবি multimodal LLM-কে দেওয়া।

LangChain's write-up lists these as: (1) multimodal embeddings such as CLIP, passing raw images to a multimodal LLM; (2) LLM summaries of images and tables embedded as text; (3) summaries embedded with a reference to the raw image, which is handed to a multimodal LLM at synthesis time. Option 3 relies on a multi-vector retriever, which decouples the retrieval key from the document used for synthesis.[63]

# Option 3 in plain Python: summary is the key, raw object is the value
docstore = {}          # id -> raw table / image (kept as-is)
index = []             # (vector, id) pairs built from summaries
for obj_id, raw in parsed_objects:
    summary = summarize_with_llm(raw)       # placeholder: your LLM call
    docstore[obj_id] = raw
    index.append((embed_text(summary), obj_id))   # placeholder: your embedder

hits = nearest(index, embed_text(question), k=3)
context = [docstore[obj_id] for obj_id in hits]   # raw objects go to a multimodal LLM

Tables and unified frameworks

Tables are the hardest object: a plain-text flattening loses row and column relationships. Three practical routes follow from the architectures above: parse the table into Markdown or HTML (previous section), summarise it for retrieval while keeping the raw table for the answer step (option 3), or retrieve the page image (ColPali). RAG-Anything takes a broader view: a unified framework over text, images, tables and equations with dual-graph construction (cross-modal plus textual) and cross-modal hybrid retrieval; code is open source at HKUDS/RAG-Anything.[68]

Summaries can hide the detail you need. In options 2 and 3 the retriever only sees what the summariser wrote. If the summary omits a number in a chart, no query can find it. Prefer option 3 so the generator still sees the original, and evaluate retrieval on questions that depend on specific cell values (my synthesis, not a sourced finding).
Research frontier: ColPali (Faysse et al.) builds the ViDoRe benchmark and shows that embedding page images as multi-vector representations with late interaction can replace the parse-then-embed pipeline for visually rich documents.[62] RAG-Anything (Guo et al., 2025) instead unifies modalities through a dual-graph design and cross-modal hybrid retrieval.[68] Limits: multi-vector page embeddings store many vectors per page (index size is a cost to measure), and the reported gains are on the authors' benchmark, so validate on your own documents.
গবেষণার সারকথা: ColPali পাতার ছবি থেকেই multi-vector embedding বানায়, text extraction লাগে না। RAG-Anything text, ছবি, table ও equation এক কাঠামোয় আনে।
🖼️Layman's versionplain English, no jargon

What is it? Normal document search only understands words. Multimodal search also understands pictures, charts and tables, so you can ask about a graph and get the page that contains it.

Why does it matter? A lot of important facts live in figures: sales charts, diagrams, price tables. If the system ignores them, it simply cannot answer those questions.

When does it go wrong? If you describe a chart in words and the description leaves out a number, search will never find that number. Searching by page picture avoids that, but needs more storage.

The photo album analogy: you can label every photo with a caption and search the captions, or you can search the photos by looking at them. Captions are cheap but only as good as the writer; looking at the photo takes more effort but misses nothing the caption left out.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

সাধারণ RAG শুধু টেক্সট বোঝে। কিন্তু অনেক তথ্য থাকে chart, ছবি আর table-এ। Multimodal RAG সেই জিনিসগুলোকেও searchable করে। মূলত তিনটি স্থাপত্য আছে।

  • Multimodal embedding: CLIP-ধরনের মডেল ছবি ও টেক্সটকে একই vector space-এ আনে, তারপর raw ছবি multimodal LLM-কে দেওয়া হয়। CLIP ৪০ কোটি image-text জোড়ায় শেখানো। Voyage একই backbone-এ mixed input নেয়, যাতে mixed search-এ একই ধরনের item-এর সাথে বেশি মিলে যাওয়ার সমস্যা কমে।
  • Summary-to-text: LLM ছবি বা table-এর বিবরণ লেখে, সেই লেখা embed করা হয়। সহজ, কিন্তু summary-তে যা বাদ পড়ে তা আর খুঁজে পাওয়া যায় না।
  • Summary + raw reference: summary দিয়ে খোঁজা হয় (multi-vector retriever), কিন্তু উত্তর বানানোর সময় মূল ছবি বা table LLM-কে দেওয়া হয়।
  • Page-image retrieval (ColPali / ViDoRe): পাতার ছবি থেকে সরাসরি multi-vector embedding, late interaction দিয়ে মেলানো; text extraction বাদ।

Table: সরল টেক্সটে চ্যাপ্টা করলে সারি-কলামের সম্পর্ক হারায়। তাই Markdown/HTML-এ parse করুন, বা summary-র সাথে raw table রাখুন, বা পাতার ছবি দিয়ে খুঁজুন। RAG-Anything text, ছবি, table ও equation এক framework-এ আনে, dual-graph ও cross-modal hybrid retrieval দিয়ে।

কখন কোনটা: সরল ক্ষেত্রে summary যথেষ্ট; সূক্ষ্ম তথ্য (chart-এর সংখ্যা) দরকার হলে raw রেফারেন্স রাখুন বা page-image retrieval দেখুন। মনে রাখুন, multi-vector-এ প্রতি পাতায় অনেক vector, তাই storage খরচ বাড়ে।

দৈনন্দিন উপমা: পাড়ার লাইব্রেরিতে বইয়ের তালিকায় শুধু নাম লেখা থাকলে ভেতরের নকশা খোঁজা যায় না। লাইব্রেরিয়ান যদি প্রতিটি বইয়ের ছবির পাতা নিজে উল্টে দেখে বলেন, তবেই নকশাওয়ালা বইটি ঠিক মেলে।
