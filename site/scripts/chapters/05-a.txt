@lede If you can't measure an LLM feature, every change is a guess. Evaluation engineering turns "it feels better" into numbers you can gate releases on: golden datasets and regression tests, LLM-as-judge done carefully, RAG-specific metrics, agent evals that check both outcome and trajectory, synthetic test data, the main frameworks, online evals on live traffic, and red teaming.
@minutes 26

=== Offline evals: golden datasets, regression tests
@sub A golden dataset is a versioned set of inputs with known-good expectations. Run it on every change to prompts, models, tools or retrieval, and block releases that regress.
@icon ✅

## What goes into a golden set
- **Real traffic first.** Sample production inputs (with consent and redaction) across your main use cases; synthetic data fills the gaps later.
- **Expectations, not just answers.** Each case states what "correct" means: an exact value, required facts, forbidden content, a rubric, or a check on the final state.
- **Coverage tags.** Label cases by intent, difficulty, language and risk so you can see *where* a change helps or hurts.
- **Known failures.** Every bug found in production joins the set (chapter 04's feedback loop).

Start small — 50 to 200 well-chosen cases beat 5,000 unexamined ones — and grow from real failures. Hamel Husain's essay argues that most of the value comes from this unglamorous loop of looking at data and writing targeted tests [@hamel-evals].

## Many metrics, not one
HELM argued for evaluating models on many scenarios with several metrics each — accuracy, calibration, robustness, fairness, efficiency — because a single number hides trade-offs [@helm]. The same holds for your product: track task success alongside cost, latency, refusal rate and safety checks.

## Regression tests in CI
```python
# tests/test_support_golden.py — runs in CI on every prompt/model/tool change
import json
import pytest
from app.agent import answer
from evals.checks import contains_all, no_pii, judge_passes

CASES = [json.loads(line) for line in open("evals/support_golden.jsonl")]

@pytest.mark.parametrize("case", CASES, ids=[c["id"] for c in CASES])
def test_golden(case):
    out = answer(case["input"], user=case["user"])
    assert contains_all(out.text, case["must_include"])
    assert no_pii(out.text)
    if case.get("rubric"):
        assert judge_passes(case["input"], out.text, case["rubric"])
```

Treat the suite like any test suite: deterministic checks wherever possible, judge-based checks only where needed, and a pass-rate threshold (with per-category minimums) as the release gate.

| Check type | Example | Cost | Reliability |
|---|---|---|---|
| Exact or regex | order id format, valid JSON schema | almost free | high |
| Reference match | the answer contains the required facts | almost free | medium |
| State check | the right row changed in the test database | low | high |
| LLM judge | tone, helpfulness, rubric criteria | model calls | needs calibration |
| Human review | ambiguous or high-stakes cases | expensive | highest |

> warn **Variance is real.** LLM outputs vary from run to run. Run flaky cases several times, report pass rates with confidence intervals on small sets, and don't celebrate a one-point move on fifty cases.

@layman
**A golden dataset is your AI's standing checklist.** It's a fixed set of real situations, each with a clear note of what a good response must include and must never include. Every time anyone changes the instructions, the model or the tools, the AI is run through the whole list again.

**If results get worse, the change doesn't ship.** And every real mistake customers report becomes a new item on the list, so it gets better at catching problems over time.

**Small and well-chosen beats huge and unexamined:** a hundred carefully picked situations are worth more than thousands nobody has looked at.

>> **The pre-flight checklist analogy:** before every flight, pilots run the same checklist, however experienced they are and however small the change to the aircraft. One missed item and the plane stays on the ground. When an incident reveals a new risk, a line is added to the checklist for every future flight.

@bangla
**Golden dataset** হলো বাস্তব input ও প্রত্যাশিত আচরণের একটি version-যুক্ত সংগ্রহ। প্রতিবার prompt, মডেল, টুল বা retrieval বদলালে এটি চালান; মান কমলে release বন্ধ।
- আগে বাস্তব traffic থেকে নমুনা নিন, পরে synthetic দিয়ে ফাঁক পূরণ করুন।
- প্রতিটি case-এ "সঠিক" মানে কী তা লিখুন: নির্দিষ্ট মান, আবশ্যিক তথ্য, নিষিদ্ধ বিষয়, rubric বা চূড়ান্ত state।
- উদ্দেশ্য, কাঠিন্য, ভাষা ও ঝুঁকি অনুযায়ী tag দিন।
- ছোট থেকে শুরু করুন (৫০–২০০টি ভালোভাবে বাছাই করা case), বাস্তব ব্যর্থতা দিয়ে বাড়ান [@hamel-evals]।

একটি সংখ্যা নয়, কয়েকটি মেট্রিক দেখুন — নির্ভুলতার পাশাপাশি খরচ, latency, প্রত্যাখ্যানের হার ও নিরাপত্তা [@helm]। LLM-এর output প্রতিবার একটু ভিন্ন হয়, তাই অস্থির case কয়েকবার চালান এবং ছোট dataset-এ এক পয়েন্টের পরিবর্তনকে বড় করে দেখবেন না।

>> **উড্ডয়নের আগের চেকলিস্টের উপমা:** অভিজ্ঞতা যত বেশিই হোক, প্রতিটি ফ্লাইটের আগে পাইলট একই চেকলিস্ট মেলান; একটি ঘর বাদ গেলে বিমান ওড়ে না। কোনো ঘটনায় নতুন ঝুঁকি ধরা পড়লে ভবিষ্যতের সব ফ্লাইটের চেকলিস্টে নতুন লাইন যোগ হয়।

=== LLM-as-judge: pairwise comparison, rubric-based scoring
@sub Many qualities — helpfulness, tone, adherence to a policy — can't be checked with a regex. A strong model can grade them, but only if you design against its known biases and check it against human labels.
@icon ⚖️

## It works — with caveats
The MT-Bench study found that strong LLM judges such as GPT-4 matched both controlled and crowdsourced human preferences with over 80% agreement, the same level of agreement humans reach with each other [@mtbench]. The same paper documents the biases to design against: **position bias** (favouring one answer slot), **verbosity bias** (favouring longer answers) and **self-enhancement bias** (favouring its own outputs) [@mtbench]. Wang et al. showed that simply swapping the order of two candidates can flip a judge's verdict [@notfair].

## Pairwise versus rubric scoring
| Mode | How it works | Strength | Weakness |
|---|---|---|---|
| Pairwise | "Which answer is better, A or B?" | relative judgements are easier and more consistent | needs two candidates; grows quadratically with variants |
| Rubric (pointwise) | score 1–5 on defined criteria, with reasons | absolute tracking over time | scores drift; scales are fuzzy |
| Reference-based | compare against a gold answer | grounded and stable | needs a gold answer for every case |

G-Eval showed that asking the judge to reason through the evaluation criteria before filling in a score improves agreement with people — a Spearman correlation of 0.514 with human ratings on summarisation, using GPT-4 as the backbone [@geval].

## A debiased pairwise judge
```python
JUDGE = """You are grading two answers to the same customer question.
Criteria: correct per the policy excerpt, complete, concise, polite.
Reason through each criterion, then output exactly one of: A, B, TIE.

Question: {q}
Policy excerpt: {policy}
Answer A: {a}
Answer B: {b}"""

def pairwise(q, policy, x, y, judge):
    first = judge(JUDGE.format(q=q, policy=policy, a=x, b=y))    # x shown first
    second = judge(JUDGE.format(q=q, policy=policy, a=y, b=x))   # order swapped
    if first == "A" and second == "B":
        return "x"
    if first == "B" and second == "A":
        return "y"
    return "tie"          # verdict flipped with order: not a confident win
```

## Calibrate against people — and keep calibrating
Before trusting a judge, have people label a sample and measure agreement with the judge (raw agreement plus Cohen's kappa). Shankar et al. found that evaluation criteria themselves drift as people grade more outputs — you discover what you care about by looking — so judge prompts and human labels need to evolve together [@evalgen]. A panel of several smaller, diverse judge models can also be cheaper and less biased than one large judge [@juries]. Public human-preference leaderboards such as Chatbot Arena apply the same pairwise idea at scale [@arena].

> warn **Don't let a model grade itself.** Use a different model family as the judge where you can, and never judge with the exact prompt being evaluated.

@layman
**Some answers can't be marked by a simple rule.** Is this reply polite? Did it follow the policy? Is it actually helpful? For those, you can ask a second, strong AI to act as the marker.

**AI markers have known quirks:** they tend to prefer whichever answer they read first, prefer longer answers, and go easy on answers that sound like their own writing. Good setups show the two answers in both orders, ask for reasons before the verdict, and compare the marker's decisions with real people's on a sample.

**Only once the AI marker agrees with people often enough do you let it mark at scale** — and you keep spot-checking it.

>> **The figure skating panel analogy:** skating competitions use several judges, a written scoring guide and rules that cancel out individual bias — extreme marks can be dropped, and a judge who keeps favouring one country gets reviewed. An AI judge needs the same safeguards.

@bangla
**LLM-as-judge**: যেসব গুণ regex দিয়ে মাপা যায় না (সহায়কতা, ভদ্রতা, policy মানা), সেগুলো একটি শক্তিশালী মডেল দিয়ে মূল্যায়ন করানো।

MT-Bench গবেষণায় শক্তিশালী LLM judge মানুষের পছন্দের সাথে ৮০%-এর বেশি মিলেছে — মানুষে-মানুষে মিলের সমান [@mtbench]। কিন্তু পক্ষপাত আছে: নির্দিষ্ট অবস্থানের উত্তরকে প্রাধান্য (position bias), লম্বা উত্তরকে প্রাধান্য (verbosity bias), আর নিজের লেখার মতো উত্তরকে প্রাধান্য (self-enhancement) [@mtbench][@notfair]।
- **Pairwise:** "A না B, কোনটি ভালো?" — দুই ক্রমে দেখিয়ে মিলিয়ে নিন।
- **Rubric:** নির্দিষ্ট মানদণ্ডে ১–৫ স্কোর, আগে কারণ লিখিয়ে নিন; এতে মানুষের সাথে মিল বাড়ে [@geval]।
- মানুষের label-এর সাথে মিল (agreement, Cohen's kappa) মেপে তবেই বিশ্বাস করুন; মানদণ্ডও সময়ের সাথে বদলায় [@evalgen]।
- কয়েকটি ছোট ও বৈচিত্র্যময় মডেলের প্যানেল একটি বড় judge-এর চেয়ে সস্তা ও কম পক্ষপাতদুষ্ট হতে পারে [@juries]।

>> **ফিগার স্কেটিং বিচারক প্যানেলের উপমা:** স্কেটিং প্রতিযোগিতায় কয়েকজন বিচারক, লিখিত নম্বর-নির্দেশিকা আর পক্ষপাত কাটানোর নিয়ম থাকে — চরম নম্বর বাদ দেওয়া যায়, আর যে বিচারক বারবার একটি দেশকে বেশি নম্বর দেন, তাঁকে পর্যালোচনা করা হয়। AI judge-এরও একই রকম সুরক্ষা দরকার।

=== RAG metrics: faithfulness, answer relevance, context precision/recall (Ragas)
@sub A RAG answer can fail in the retriever (wrong or missing context) or in the generator (ignoring or contradicting the context). Separate metrics for each stage tell you which half to fix.
@icon 📰

## The core metrics
Ragas popularised a set of largely reference-free metrics for RAG pipelines [@ragas]; its documentation describes the current implementations and variants [@ragas-docs].

| Metric | Question it answers | Stage it diagnoses | Needs a reference answer? |
|---|---|---|---|
| Faithfulness | are the answer's claims supported by the retrieved context? | generation | no |
| Answer relevance | does the answer address the question asked? | generation | no |
| Context precision | are the retrieved chunks mostly relevant, and ranked high? | retrieval ranking | sometimes |
| Context recall | was everything needed to answer actually retrieved? | retrieval coverage | yes |

## How they are computed
Faithfulness is typically computed by splitting the answer into individual claims and asking a judge model whether each one is supported by the context; the score is the supported fraction. Answer relevance can be estimated by generating questions from the answer and comparing them with the original question. ARES takes a different route: it fine-tunes lightweight judges on synthetic data and uses a small set of human labels with prediction-powered inference to put confidence intervals around the scores [@ares].

## Add classic retrieval metrics
LLM-based metrics are slower and noisier than counting. Where you have labelled relevant documents per query, also track recall@k, MRR and nDCG for the retriever on its own — cheap, deterministic, and ideal for tuning chunking and reranking (see the RAG guide in this series).

> warn **High faithfulness doesn't mean a correct answer.** An answer can faithfully repeat a wrong or outdated chunk. Pair faithfulness with context recall and with spot checks against ground truth.

@layman
**An AI that answers from documents can go wrong in two places.** It might fetch the wrong pages, or it might fetch the right pages and then ignore or twist them.

**So you check each step separately.** Did it pull the right pages, and all the ones it needed? Does every claim in the answer actually appear in those pages? And did it answer the question that was actually asked?

**Knowing which step failed tells you what to fix:** the searching, or the writing.

>> **The newspaper fact-checker analogy:** a fact-checker asks whether the reporter gathered the right sources, whether every sentence in the article is backed by those sources, and whether the piece answers the editor's actual question. A beautifully written story built on the wrong sources still fails.

@bangla
RAG উত্তর দুই জায়গায় ব্যর্থ হতে পারে: retriever ভুল বা অসম্পূর্ণ context আনতে পারে, অথবা generator context উপেক্ষা বা বিকৃত করতে পারে। Ragas-এর মেট্রিকগুলো প্রতিটি ধাপ আলাদা করে মাপে [@ragas]:
- **Faithfulness**: উত্তরের প্রতিটি দাবি কি আনা context-এ আছে?
- **Answer relevance**: উত্তর কি আসল প্রশ্নের জবাব দিচ্ছে?
- **Context precision**: আনা অংশগুলো কি বেশিরভাগই প্রাসঙ্গিক এবং উপরের দিকে আছে?
- **Context recall**: উত্তরের জন্য দরকারি সব তথ্য কি আনা হয়েছে?

ARES হালকা judge মডেল ও অল্প মানুষের label দিয়ে স্কোরের confidence interval দেয় [@ares]। পাশাপাশি recall@k, MRR, nDCG-এর মতো সস্তা retrieval মেট্রিকও রাখুন। মনে রাখবেন, উচ্চ faithfulness মানেই সঠিক উত্তর নয় — উত্তর ভুল বা পুরোনো তথ্যও বিশ্বস্তভাবে পুনরাবৃত্তি করতে পারে।

>> **সংবাদপত্রের তথ্য-যাচাইকারীর উপমা:** তথ্য-যাচাইকারী দেখেন সাংবাদিক ঠিক সূত্র জোগাড় করেছেন কি না, প্রতিবেদনের প্রতিটি বাক্য সেই সূত্রে আছে কি না, আর সম্পাদকের আসল প্রশ্নের উত্তর দেওয়া হয়েছে কি না। ভুল সূত্রের ওপর লেখা সুন্দর প্রতিবেদনও ব্যর্থ।

=== Agent evals: task success rate, trajectory analysis, tool-call accuracy
@sub An agent's final answer can be right for the wrong reasons, or wrong after mostly good steps. Evaluate the outcome, the path and each tool call — and run tasks several times, because reliability matters as much as capability.
@icon 🚗

## Outcome: did the task succeed?
The most robust check compares the **end state**, not the transcript: was the right database row changed, was the correct booking made, do the tests pass? τ-bench evaluates agents this way in simulated retail and airline domains, comparing the final database state with the goal [@taubench]; SWE-bench checks whether a generated patch makes the repository's tests pass [@swebench].

## Reliability: pass^k, not just pass@1
τ-bench introduced pass^k — the probability that an agent succeeds on **all** k independent trials of the same task. Even strong function-calling agents such as gpt-4o succeeded on under 50% of tasks, and pass^8 fell below 25% in the retail domain [@taubench]. For a customer-facing agent, inconsistency is a failure in itself.

```python
def pass_hat_k(results_per_task: dict[str, list[bool]], k: int) -> float:
    """Share of tasks where the agent succeeded on every one of k trials."""
    tasks = [runs[:k] for runs in results_per_task.values() if len(runs) >= k]
    return sum(all(runs) for runs in tasks) / len(tasks)
```

## Trajectory and tool calls
| What to check | Example assertion |
|---|---|
| Tool selection | used `orders_search` before `orders_refund` |
| Argument correctness | refund amount equals the order total, never more |
| No forbidden actions | never called `account_delete` |
| Efficiency | finished within 8 steps; no repeated identical calls |
| Recovery | after a 429 error, waited and retried instead of giving up |
| Policy | asked for confirmation before any write above a threshold |

The Berkeley Function Calling Leaderboard measures single-call accuracy — choosing the right function and filling its arguments correctly — and is a useful reference point for tool-call accuracy [@bfcl].

## Public benchmarks as context, not targets
AgentBench evaluates models as agents across several interactive environments [@agentbench], GAIA poses general-assistant questions that are simple for people but hard for models [@gaia], WebArena uses realistic self-hosted websites [@webarena], and OSWorld uses real computer environments [@osworld]. They help with model selection; only your own task suite tells you whether *your* agent works.

> info **Grade trajectories with code first.** Most trajectory checks are simple assertions over the trace (chapter 04). Save LLM judges for genuine judgement calls such as "was the clarifying question reasonable?".

@layman
**Testing an AI agent is like testing a driver, not a calculator.** You check that it actually reached the destination — the order was really refunded, the meeting really booked — not just that it said so.

**You also watch how it got there:** did it use the right tools in a sensible order, avoid anything forbidden, ask permission before big actions, and recover when something went wrong?

**And you run each task several times.** An agent that succeeds two times out of three isn't ready to deal with customers.

>> **The driving test analogy:** the examiner cares that you reach the end of the route, but also whether you checked mirrors, signalled, kept to the speed limit and handled the unexpected cyclist. Passing once by luck isn't enough — a licence means you can do it reliably.

@bangla
Agent-এর চূড়ান্ত উত্তর ভুল কারণে সঠিক হতে পারে, আবার ভালো ধাপের পরেও ভুল হতে পারে। তাই তিনটি স্তরে মূল্যায়ন করুন:
- **Outcome**: transcript নয়, চূড়ান্ত **state** মিলিয়ে দেখুন — ঠিক row বদলেছে কি না, test পাস করে কি না [@taubench][@swebench]।
- **Reliability**: τ-bench-এর pass^k — একই কাজ k বার চালালে সবকটিতে সফল হওয়ার সম্ভাবনা। gpt-4o-এর মতো শক্তিশালী agent-ও ৫০%-এর কম কাজে সফল হয়েছে, আর retail-এ pass^8 ছিল ২৫%-এর নিচে [@taubench]।
- **Trajectory ও tool call**: ঠিক টুল, ঠিক argument, কোনো নিষিদ্ধ কাজ নয়, অপ্রয়োজনীয় পুনরাবৃত্তি নয়, ব্যর্থতার পর সামলে ওঠা; single-call নির্ভুলতার জন্য BFCL একটি ভালো মানদণ্ড [@bfcl]।

AgentBench, GAIA, WebArena, OSWorld-এর মতো public benchmark মডেল বাছাইয়ে সাহায্য করে; কিন্তু আপনার agent কাজ করে কি না, তা বলে শুধু আপনার নিজের task suite।

>> **ড্রাইভিং পরীক্ষার উপমা:** পরীক্ষক দেখেন আপনি গন্তব্যে পৌঁছালেন কি না, সাথে আয়না দেখলেন কি না, সংকেত দিলেন কি না, গতিসীমা মানলেন কি না। একবার ভাগ্যক্রমে পাস করা যথেষ্ট নয় — লাইসেন্স মানে নির্ভরযোগ্যভাবে পারা।
