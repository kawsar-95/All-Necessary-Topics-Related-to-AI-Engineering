LLMOps & observability

Traditional DevOps answers "did the request return 200?" LLM apps need richer questions: did the model return the right answer, at the right cost, in the right tone, with no leakage? The discipline of answering those is LLMOps, and it has its own toolchain.

Tracing

An LLM trace is a tree of spans: the user request, the system prompt assembly, the LLM call, every tool invocation, the result. The four leading tracing tools in 2025:

ToolStrength
LangfuseOpen-source, OpenTelemetry-native, self-hostable
LangSmithPolished UI, deep LangChain integration
HeliconeDrop-in proxy that captures everything with one env-var change
Arize PhoenixEvaluation-first, embeddings-aware drift detection
BraintrustEval + trace in one workspace
A single agent run as a traced tree: parent (POST), LLM calls (in violet), tool calls (in green/yellow), approval gate, plus a cost and latency footer.
একটি এজেন্ট রান traced tree হিসেবে: parent POST, LLM calls (বেগুনি), tool calls (সবুজ/হলুদ), approval gate, এবং খরচ ও latency ফুটার।

Token, cost, and latency tracking

Every request must record: input tokens, output tokens, model, cost (computed from vendor's pricing), latency (TTFT, total), and cache hit. Tag with user_id, feature, experiment. This data is the substrate for every other LLMOps question — "is feature X losing money?", "is the new model slower?"

Prompt and agent versioning

Prompts are code. Treat them like code: store in git, version them, review them via PR, deploy via CI. Each prompt version gets a stable ID; every trace carries the prompt ID. When something breaks, you can answer "what prompt version were users on?" instantly.

A/B testing prompts and models in production

Route traffic between two prompt versions (or two models) by user_id hash. Measure: cost, latency, evals run on the output, user feedback. Stop the experiment when one variant wins on the metric you chose (and you didn't peak on it after one bad afternoon).

Replay and debugging

When a user complains, you should be able to pull the trace, see every prompt and every model reply, identify the failure, and replay the exact request against a different model or prompt to verify the fix. Langfuse, Helicone, and LangSmith all give you a replay button.

Drift detection (silent behaviour changes)

When OpenAI swaps GPT-4 for GPT-4-0613 or Anthropic bumps the weights of a "same-named" model, your outputs drift in ways your offline evals won't catch. The fix: run a small fraction of production traffic (1–5%) through both the old and new model, compare evals, alert on delta. Arize Phoenix and Braintrust automate this.

Feedback loops

Capture thumbs-up / thumbs-down (or richer signals) and feed the failures into your eval dataset. After three months you'll have a thousand real failures that's worth more than ten thousand synthetic ones.

🔭Layman's versionplain English, no jargon

LLMOps is "DevOps for AI apps." In a normal web app, you know if it crashed because you see a red error in your dashboard. In an AI app, the call might return 200 OK and the model might still be giving wrong answers, expensive answers, or biased answers. So you need new tools that watch for those things.

Tracing = a flight recorder for every request. When a user says "your AI gave me a weird answer yesterday," you should be able to pull up the exact request, see every prompt, every model call, every tool it used, the cost, and the latency — in one view. The big tracing tools (Langfuse, LangSmith, Helicone, Arize Phoenix) all do this.

Token and latency tracking is your new "errors dashboard. Every call should write down how many tokens it used, how much it cost, how fast it was, and whether the cache worked. Tag every call with who made it, what feature was running, and which experiment it was part of. Now you can answer "which feature is burning the budget?" instantly.

Prompt versioning = prompts are code. Stop editing prompts in the admin panel. Put them in git, give them version IDs, deploy them through CI. When something breaks, you can say "users on version 7 reported this," not "uh, I changed the prompt last Tuesday."

A/B testing = "let's see which version people like more." Send 50% of users to prompt A, 50% to prompt B. Measure cost, speed, thumbs-up rate. The winner becomes the default.

Drift detection = "did the AI quietly get worse?" AI vendors upgrade models without telling you, and the new version might be subtly worse on your specific workload. The fix: send 5% of traffic through the new model, compare the answers, alert if quality dropped.

Feedback loops = "learn from complaints." When users click thumbs-down, save that exact trace into your eval set. Three months from now you'll have hundreds of real-world failures to test against, worth more than thousands of synthetic ones.

The black-box flight recorder analogy: every LLM call should leave a black-box flight recorder behind. The recorder should write down the prompt, the model's reply, the cost, the latency, which user, which feature, which experiment — so when something goes wrong (or silently degrades), you can replay the exact moment and figure out why.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

LLMOps হলো "DevOps for AI apps"। সাধারণ ওয়েব অ্যাপে আপনি জানেন এটি ক্র্যাশ করেছে কারণ ড্যাশবোর্ডে লাল ত্রুটি দেখেন। AI অ্যাপে কল 200 OK ফেরত দিতে পারে, অথচ মডেল ভুল, ব্যয়বহুল বা পক্ষপাতদুষ্ট উত্তর দিতে পারে। তাই এই বিষয়গুলো দেখার নতুন সরঞ্জাম দরকার।

Tracing = প্রতিটি request-এর জন্য flight recorder: ব্যবহারকারী বললে "আপনার AI গতকাল আমাকে অদ্ভুত উত্তর দিয়েছে," আপনি সেই নির্দিষ্ট request টেনে এনে প্রতিটি prompt, প্রতিটি model call, প্রতিটি ব্যবহৃত tool, খরচ ও latency এক দৃশ্যে দেখতে পারবেন। প্রধান tracing tools: Langfuse (open-source, OpenTelemetry-native, self-hostable), LangSmith (LangChain ইন্টিগ্রেশন), Helicone (একটি env-var দিয়ে সব ক্যাপচার), Arize Phoenix (evaluation-first), Braintrust (eval + trace এক জায়গায়)।

Token, cost ও latency tracking: প্রতিটি request রেকর্ড করুক: input tokens, output tokens, model, cost (vendor-এর pricing থেকে হিসাব), latency (TTFT, total), ও cache hit। user_id, feature, experiment দিয়ে tag করুন। এই ডেটাই প্রতিটি অন্য LLMOps প্রশ্নের ভিত্তি।

Prompt ও agent versioning: prompt হলো কোড। কোডের মতোই git-এ রাখুন, ভার্সন করুন, PR-এ review করুন, CI দিয়ে deploy করুন। প্রতিটি prompt version-এর একটি স্থিত ID থাকবে; প্রতিটি trace সেই prompt ID বহন করবে।

A/B testing prompts ও models: user_id hash দিয়ে দুটি prompt version (বা দুটি model)-এর মধ্যে traffic রাউট করুন। Cost, latency, output-এ চালানো eval, ব্যবহারকারীর প্রতিক্রিয়া মাপুন। নির্বাচিত মেট্রিকে একটি ভ্যারিয়েন্ট জিতলে পরীক্ষা বন্ধ করুন।

Replay ও debugging: ব্যবহারকারী অভিযোগ করলে trace টেনে এনে প্রতিটি prompt ও প্রতিটি model reply দেখুন, ব্যর্থতা চিহ্নিত করুন, এবং সেই exact request ভিন্ন model বা prompt-এ replay করে fix যাচাই করুন।

Drift detection (silent behaviour changes): OpenAI GPT-4-কে GPT-4-0613 দিয়ে প্রতিস্থাপন করলে বা Anthropic "same-named" মডেলের weights আপডেট করলে, আপনার output-গুলো আপনার offline eval ধরতে পারবে না এমনভাবে drift করে। সমাধান: production traffic-এর একটি ছোট অংশ (১–৫%) একই সাথে পুরোনো ও নতুন মডেলের মধ্য দিয়ে চালান, eval তুলনা করুন, delta-তে সতর্কতা দিন। Arize Phoenix ও Braintrust এটি স্বয়ংক্রিয় করে।

Feedback loops: thumbs-up / thumbs-down (বা সমৃদ্ধ সংকেত) ক্যাপচার করুন এবং ব্যর্থতাগুলো আপনার eval dataset-এ ফিড করুন। তিন মাস পর আপনার কাছে এক হাজার বাস্তব ব্যর্থতা থাকবে, যা দশ হাজার synthetic-এর চেয়ে বেশি মূল্যবান।

Black-box flight recorder উপমা: প্রতিটি LLM কল একটি black-box flight recorder রেখে আসা উচিত। Recorder prompt, model reply, খরচ, latency, কোন ব্যবহারকারী, কোন feature, কোন experiment — সব লিখে রাখুক, যাতে কিছু ভুল হলে (বা নীরবে খারাপ হলে) আপনি সেই মুহূর্তটি replay করে বুঝতে পারেন কেন।
