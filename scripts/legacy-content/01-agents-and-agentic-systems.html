Agents & agentic systems

An agent is an LLM running in a control loop: it observes the world, decides what to do, calls tools, observes the results, and repeats until the goal is reached. This chapter covers the four canonical agent loops, single- vs multi-agent orchestration, state machines and workflow graphs, agent memory, human-in-the-loop checkpoints, subagents, error recovery, durable long-running execution, and browser / computer-use agents.

01

What an agent actually is

A working definition, the boundary between "agent" and "workflow," and the minimum set of components any production agent must have.

The minimal agent

Strip away the marketing and every agent is the same shape: a loop that takes the current state, asks an LLM what to do next, executes the answer (a tool call, a structured response, or a final answer), and feeds the result back in. Where agents diverge from each other is how the loop is structured, what the state contains, and how failure is handled.

# The minimal agent in 12 lines
def agent_loop(goal, llm, tools, max_steps=20):
    history = [{"role": "user", "content": goal}]
    for step in range(max_steps):
        response = llm.complete(history, tools=tools)
        if response.finish_reason == "stop":
            return response.text
        result = tools.invoke(response.tool_call)
        history.append({"role": "tool", "content": str(result)})
    raise AgentTimeout("loop did not terminate")

Agent vs workflow

A workflow is a deterministic graph of LLM calls and tool calls: every step is authored, every branch is explicit. An agent is a workflow where at least one node's behaviour is decided at runtime by the LLM itself. The line is blurry in practice — most production systems are "agentic workflows" that combine both.

Rule of thumb: if a human could write a flowchart of the system's behaviour from the prompt alone, it's a workflow. If the LLM picks the next node at runtime, it's an agent. Most shipped systems are a mix — deterministic scaffolding around a few agentic decisions.

What every production agent needs

  • A bounded loop with a hard step cap and a wall-clock timeout. Unbounded loops are how agents burn $10k overnight.
  • A tool surface that's narrow, well-typed, and namespaced (so the model can't accidentally call a destructive tool without going through a guardrail).
  • A scratchpad — some persistent state across turns that survives the LLM's context window. Either the model writes to a file, the framework keeps it, or you stuff it into the next prompt.
  • An exit predicate: at minimum, "I think I have enough; here is the answer." Without one the agent will keep acting forever.
  • Observability: every step recorded with prompt, tool call, result, cost, and latency. Without it you cannot debug.
🤖Layman's versionplain English, no jargon

An agent is an AI that doesn't stop until the job is done. A normal chatbot: you ask, it answers, done. An agent: you ask "find me a hotel under $150 in Tokyo next week," and it goes off, browses the web, checks three sites, compares them, and comes back in five minutes with a recommendation. You didn't tell it which sites. It figured that out.

The "loop" is just doing the same five steps over and over:

1. Look at what's in front of me (what tools do I have? what have I learned so far?).
2. Decide what to do next (use a tool, ask the user, or stop).
3. Do it (call the tool, send the message).
4. Look at the result.
5. Repeat from step 1 until done (or until you've been looping too long).

The five things every production agent must have: a cap on how many times it can loop, a small list of allowed tools, a place to keep notes that survive the model's short memory, a way to say "I'm done," and a way to record what it did so you can debug it later. Skip any one and you have a hobby project, not a product.

The personal-assistant analogy: an agent is like hiring a human PA. The PA doesn't know your preferences yet (it builds them over time). When you ask "handle my dentist appointment," the PA calls the dentist, asks for times, checks your calendar, calls back to confirm, and texts you the details. If the dentist's line is busy, the PA tries again in 5 minutes. If you said "cancel if it costs more than $200," the PA pauses and asks before booking. If the PA's phone dies, it picks up where it left off when it charges. That's an agent.

02

The four canonical agent loops

Every agent loop you'll meet in production is a variation of one of these four patterns. Pick by the shape of your task, not by hype.

The four canonical agent loops. Each trades off reasoning depth, token cost, latency, and recovery behaviour. Production systems usually compose them.
চারটি ক্যানোনিক্যাল agent লুপ: ReAct, Plan-and-Execute, Reflexion, এবং ReWOO।

ReAct — Reason + Act (interleaved)

Introduced by Yao et al. in 2022,[1] ReAct is the simplest agent loop: the model writes a Thought, picks an Action, observes the result, repeats. The thought is in the model's private scratchpad and never shown to the user; only the final answer is. ReAct is the default loop in LangChain's AgentExecutor and most early agent frameworks.

# ReAct scratchpad format (text version)
Thought: I need to find the population of Tokyo in 2024.
Action:   search(query="Tokyo population 2024 official")
Observation: As of January 2024, the estimated population...
Thought: Now I can answer.
Action:   Finish("Tokyo's population is ~13.96 million.")
Why ReAct dominates: the interleaved reasoning makes traces human-readable. When something goes wrong, you can read the scratchpad and see why the model picked the action it did. That single property is why ReAct is still the default for most agent debugging.

Plan-and-Execute

Plan-and-Execute separates planning from execution: a planner (usually a strong LLM) produces a sequence of steps, then a worker (often a smaller model or a deterministic tool) carries out each step. The worker can be ReAct itself, a single-shot LLM call, or a pure function. If a step fails, the planner re-runs only that step (cheap) rather than the whole loop.[2]

Reflexion — verbal self-criticism

Reflexion adds a second pass: after a ReAct attempt, the model is asked to reflect on what went wrong, and that reflection is appended to the memory for the next attempt.[3] In benchmarks (HumanEval, AlfWorld) Reflexion beats vanilla ReAct by 10–20% absolute.

ReWOO — Reasoning Without Observation

ReWOO's insight: in many retrieval-heavy tasks, the model doesn't need to see the result of tool #1 to plan tool #2. It plans the entire tool graph upfront, the worker executes everything in parallel, then the solver reads the evidence and answers.[4] ReWOO uses 4–6× fewer tokens than ReAct on retrieval benchmarks.

Which loop to pick

LoopToken costLatencyDebug-abilityWhen to use
ReActHigh (LLM per step)MediumExcellentDefault for short, tool-heavy tasks; debugging
Plan-and-ExecuteMedium (replan only)MediumGoodKnown-shape workflows; mixed executors per step

🔁Layman's versionplain English, no jargon

There are four common "personalities" for agents:

• ReAct = the improv actor. Thinks out loud, acts, reacts.
• Plan-and-Execute = the project manager. Writes a to-do list, then ticks items off.
• Reflexion = the perfectionist. Does the work, checks itself, tries again.
• ReWOO = the efficient assistant. Plans every call upfront, no chat.

How to pick: default to ReAct. If your task is "go look up 5 things in parallel and write a summary," switch to ReWOO. If your task is "do these 6 steps in order, but be ready to replan if step 3 fails," use Plan-and-Execute.

The four-college analogy: ReAct is the liberal-arts student. Plan-and-Execute is the engineering student. Reflexion is the grad student. ReWOO is the consultant who preps the entire deck before the meeting.

Single-agent vs multi-agent orchestration

The most expensive mistake in agent engineering is reaching for a multi-agent setup when a well-tuned single agent would do.

What a single agent gives you

A single agent is one LLM in one control loop with one tool surface. Every decision flows through one prompt, one model call, one trace. Debugging is "read the trace."

What a multi-agent setup gives you

Multi-agent systems have an orchestrator that delegates to specialised workers — researcher, writer, critic, coder — each with its own prompt, its own tool surface, and (often) its own model.[5]

DimensionSingle-agentMulti-agent
DebuggingOne trace to read end-to-endN traces to correlate
Token costLower2–5× higher
Capability ceilingLimited by one prompt's coherenceHigher (separation of concerns)
Failure isolationWhole loop fails togetherOne agent's failure can be retried independently
When to use≤5 tools, one domainDistinct roles, high stakes
Anti-pattern: spinning up a multi-agent system because it sounds advanced. Anthropic's own engineering blog reports that well-tuned single-agent prompts often match multi-agent quality at a fraction of the cost.[5]

Communication patterns between agents

  • Shared scratchpad (blackboard): all agents read/write to a shared file or in-memory dict.
  • Message passing: orchestrator sends typed messages to workers.
  • Tool calls: the orchestrator is the only "agent"; workers are exposed as tools.
# Anthropic Research pattern (simplified)
async def research(query):
    sub_queries = await orchestrator.plan(query)
    findings = await asyncio.gather(*[
        researcher.search(sq) for sq in sub_queries
    ])
    review = await critic.review(query, findings)
    return await orchestrator.synthesise(query, findings, review)
👥Layman's versionplain English, no jargon

"One smart assistant" vs "a team of specialists."

Why teams cost more: every time the manager hands work to a specialist, you have to send them the full context. The specialist has to re-read it. That's the 2–5× cost.

When to use a team: when one person really cannot do it all well.

The mistake to avoid: building a team because teams sound smart, when one well-tuned generalist would do.

The restaurant analogy: single-agent is a one-person food truck. Multi-agent is a restaurant with multiple specialists.

State machines and workflow graphs

For non-trivial agents, replace the implicit loop with an explicit graph of nodes (LLM calls, tool calls, human approvals) connected by edges (conditional transitions). This is how production systems stay debuggable.

Why an explicit graph

An implicit loop is fast to write and impossible to debug. After 30 tool calls, you can't tell which path the model took. An explicit graph makes the topology visible: every node has a name, every edge has a condition, every transition is recorded.

LangGraph

LangGraph (LangChain's graph framework) is the most popular Python/TypeScript option.[6] It models the agent as a state graph: nodes are functions, edges are conditional, the state is a TypedDict that flows through. Cycles are first-class (an agent can loop back to an earlier node), and checkpointer lets you resume from any past state.

# LangGraph minimal agent
from langgraph.graph import StateGraph, END
from typing import TypedDict

class State(TypedDict):
    messages: list
    step: int

def call_llm(state: State) -> State:
    response = llm.invoke(state["messages"])
    return {"messages": state["messages"] + [response], "step": state["step"] + 1}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tool"
    return END

graph = StateGraph(State)
graph.add_node("llm", call_llm)
graph.add_conditional_edges("llm", should_continue, {"tool": "llm", END: END})
graph.set_entry_point("llm")
app = graph.compile()

Temporal, Restate, Mastra, Inngest

For long-running agents (minutes to hours), the graph needs to be durable — survive crashes, retries, and human-in-the-loop pauses. Temporal and Restate are workflow engines from the microservices world adapted to agents.[7] Mastra is TypeScript-first with built-in workflow engine, memory, and tool definitions. Inngest is event-driven serverless workflows with pay-per-step pricing.

🗺️Layman's versionplain English, no jargon

Don't write agents as a single loop; draw a map of the steps.

When an agent does "search → summarise → check → maybe search again → write answer," you could write that as one loop with if-statements. Or you could draw a flowchart with named boxes and arrows. The flowchart version is what graph frameworks do for you.

For long agents (hours/days): you need a workflow engine that survives crashes. That's Temporal or Restate.

Picking one: if you're already in Python + LangChain, use LangGraph. If you need long-running + humans in the loop, use Temporal. If you want everything in TypeScript with batteries included, try Mastra. If you wake on webhooks and want to pay per step, use Inngest.

The flowchart vs paragraph analogy: writing an agent as a loop is like writing directions as a paragraph. Drawing it as a graph is like giving someone a map.

Agent memory: scratchpad, semantic, procedural

Three memory types show up again and again in the agent literature.[8]

Scratchpad (working memory)

The scratchpad is the model's private notes for the current run. When the run ends, the scratchpad is discarded.

Semantic memory (long-term facts)

Semantic memory stores facts the agent has learned about the user, the project, the world. The classic implementation is a vector store indexed by meaning, plus a structured row store for exact matches.

Procedural memory (skills)

Procedural memory is the agent's playbook: "how to do X." Stored as versioned prompt templates or Markdown checklists.

Other memory types

TypeWhat it storesWhere it lives
ScratchpadCurrent-run notesContext window or temp file
SemanticFacts about the worldVector store + row DB
ProceduralHow-tosVersioned prompt templates
EpisodicPast runs and their outcomesEvent log + vector store
IdentityWho the agent isSystem prompt (immutable)

Where memory breaks

  • Too much memory: the agent over-relies on stale facts.
  • Too little memory: the agent re-derives the same conclusion on every turn.
  • Conflicting memory: two facts disagree.
🧠Layman's versionplain English, no jargon

Agents have three kinds of memory, just like humans.

• Scratchpad = the napkin you're scribbling on right now.
• Semantic memory = facts you remember.
• Procedural memory = how-tos.

The hard part of memory is decay. Stale facts cause confidently wrong answers.

When memory breaks: too much = clings to old facts. Too little = re-derives. Conflicting = flip-flops.

The-colleague analogy: a new hire's scratchpad is the sticky note. Their semantic memory is the facts you told them. Their procedural memory is the standard operating procedures. A good manager keeps all three fresh.

06

Human-in-the-loop checkpoints

Most production agents need at least one approval step.

The risk ladder

  1. Read-only: search, fetch, query. Auto-approve.
  2. Local-write: edit a file the agent owns. Auto-approve with a soft cap.
  3. External-write: send an email, post to Slack. Approve per call.
  4. Money: refund, charge, payout. Approve per call, plus a daily cap.
  5. Destructive: delete a record. Two-person rule.

The checkpoint primitive

Every durable framework exposes a "wait for human" primitive. In LangGraph it's interrupt; in Temporal it's wait_for_signal; in Restate it's await call().ack().

# LangGraph interrupt + resume
def send_email(state):
    approval = interrupt({
        "to": state["recipient"],
        "subject": state["subject"],
        "body": state["draft"],
    })
    if not approval["approved"]:
        return {"messages": ["User rejected email send."]}
    email_client.send(approval)
    return {"messages": ["Email sent."]}
The hard part is the UI, not the protocol. Most teams underestimate how much work the approval surface is. The framework gives you a clean "interrupt" primitive, but you still have to build the inbox, the diff view, the approve/reject buttons, the audit log, the SLA, the mobile notifications. Budget at least 30% of agent project time for the human-facing surface.

Asynchronous approvals

When the human can't respond synchronously:

  • Soft timeout + default reject: if no response in 24 hours, the workflow terminates.
  • Soft timeout + default approve with rollback: if no response, the action proceeds but is logged and reversible.
  • Hard timeout + escalate: at 24 hours, route to a backup approver.
✋Layman's versionplain English, no jargon

Some actions are too dangerous to do without asking.

The "risk ladder": as actions get more dangerous, more humans need to be in the loop.

The hard part is the UI, not the protocol.

When the human is offline: cancel after 24h, proceed anyway but log it, or escalate to a backup approver.

The new-intern analogy: a new intern can answer the phone without asking. They can take a message. They can draft an email — but show it to you before sending. They can refund a customer under $50 — but you pre-approve the policy. They can fire a customer — only with you in the room.

Subagents and delegation patterns

When a single agent's task list grows too large for one context window, the natural move is to delegate.

What a subagent is

A subagent is an agent launched by another agent. It has its own system prompt, its own tool surface, its own loop, and its own termination. It returns a final result to the parent — not intermediate state.

Manager–worker, not fork/join

The mental model is "manager → worker," not "fork/join." The parent does not poll the subagent. The parent does not stream the subagent's progress. The parent waits for the subagent to finish, then receives a single, structured result. The benefit: the parent's context window stays clean.

Claude Code's Task tool

Anthropic's Claude Code ships a Task tool that the model can invoke to spawn a subagent. The subagent runs in its own loop, with its own tools, and returns a summary. The parent never sees the intermediate steps — only the summary. This is the cleanest implementation of the pattern in 2025.

OpenAI's agents-sdk and CrewAI

OpenAI's openai-agents-sdk exposes Runner.run(agent, input) returning a final RunResult. CrewAI models multi-agent systems as crews (the team), agents (the roles), tasks (the work), and a process (sequential, hierarchical, or consensual).

When to use a subagent

  • The subtask is well-defined and self-contained.
  • The subtask needs different tools than the parent has.
  • The subtask's intermediate steps would pollute the parent's context.
  • You want the subtask to be retried independently of the parent.
  • You want to bill the subtask to a different cost centre.

A subagent is a temporary worker you hire to do one job. You give them a brief, a list of tools they can use, and a deadline. They go do the work and come back with an answer. You never see what they did in the middle — just the final report.

Mental model: the parent is the manager. The subagent is a contractor.

Bonus: you can use a different (cheaper) model for the subagent.

The contractor analogy: a CEO doesn't personally do market research. They hire a research firm, give them a brief, get a report.

Manager-worker, fork/join নয়।

কখন subagent ব্যবহার করবেন: উপ-কাজ সু-সংজ্ঞায়িত, ভিন্ন tools দরকার, parent-এর context দূষিত করবে, স্বাধীনভাবে retry করতে চান।

ঠিকাদারের উপমা: একজন CEO ব্যক্তিগতভাবে market research করেন না। তারা একটি research firm নিয়োগ করেন।
08

Error recovery, retries, and self-correction

Three escalating layers: retry the same call, fall back to a different one, or reflect on the failure and revise. Always bound retries.

Layer 1: retry

Transient failures (rate limit, network blip, server overloaded) are best handled with a short retry. Exponential backoff is the default: 1s, 2s, 4s, 8s, with jitter to avoid thundering-herd. Cap at 3–5 attempts; beyond that, the failure is not transient.

# Exponential backoff with jitter
import random, time
def retry_with_backoff(fn, max_attempts=5, base=1.0):
    for attempt in range(max_attempts):
        try:
            return fn()
        except (RateLimitError, TimeoutError):
            if attempt == max_attempts - 1: raise
            sleep = base * (2 ** attempt) + random.uniform(0, base)
            time.sleep(sleep)

Layer 2: fallback

When the failure is not transient (the API is permanently down, the JSON schema is rejected because the model can't follow it, the function raised a domain-specific error), retrying the same call is pointless. Fall back to a different tool or model: use a smaller model with a simpler schema, use a different vendor, or skip the tool and let the model answer from its own knowledge.

Layer 3: reflect

When the failure was caused by a reasoning error (the model called the right tool with the wrong arguments, or made a logical mistake), neither retry nor fallback fixes the root cause. Feed the failure back into the model and ask it to revise.[3] Reflexion is the formal version of this.

Always bound retries

Unbounded retry is a footgun. A poisoned input that always returns the same transient-looking error will burn your entire budget in a tight retry loop. Always set a hard cap on retries, a wall-clock timeout, and a circuit breaker that opens after N consecutive failures of the same type.

Circuit breakers

A circuit breaker protects against a downstream service that's failing in a way that looks transient but isn't. After 5 consecutive failures of the same kind, the breaker opens: all calls for the next 60 seconds fail fast with a "service unavailable" error, no retries. After 60 seconds, the breaker half-opens: one test call. If it succeeds, the breaker closes. If it fails, the timer resets.

🛟Layman's versionplain English, no jargon

Three layers of failure handling:

• Retry: try the same thing again.
• Fallback: try a different thing.
• Reflect: feed the error back to the AI.

The dangerous footgun: an unbounded retry will burn your entire budget. Always cap retries.

The circuit breaker pattern: after 5 consecutive failures, all calls for the next 60 seconds fail instantly.

The-customer-service analogy: when a customer's call drops, you call them back. If it drops a third time, you send an email instead.

ব্যর্থতা মোকাবেলার তিনটি স্তর: Retry, Fallback, Reflect।

বিপজ্জনক footgun: একই ত্রুটি বারবার আসতে থাকলে, একটি unbounded retry একটি টাইট loop-এ আপনার সম্পূর্ণ budget পুড়িয়ে ফেলবে।

Circuit breaker pattern: 5 টি ধারাবাহিক ব্যর্থতার পর, পরবর্তী 60 সেকেন্ডের জন্য সমস্ত call তাৎক্ষণিকভাবে ব্যর্থ হয়।

কাস্টমার সার্ভিসের উপমা: যখন একজন গ্রাহকের কল ড্রপ হয়, আপনি তাদের কল করেন। এটি তৃতীয়বার ড্রপ হলে, আপনি পরিবর্তে একটি ইমেল পাঠান।
09

Long-running agents and durable execution

Agents that take minutes or hours face three problems a normal Python loop can't solve: crashes lose state, rate limits force waits, and human approvals force pauses. Durable execution engines solve all three.

Why "just save state" isn't enough

The naive solution is to checkpoint the agent's state to disk every step. But "the agent's state" is more than the message log: it's the in-flight tool calls, the partial writes to external services, the human approval state, the retry counters. Saving the messages and losing the rest gives you a corrupt resume.

Durable execution, defined

A durable execution engine records every step's intent and result to a durable store (a database, a journal, a queue). On crash, the next process loads the snapshot and resumes from the next un-run step. The engine handles retries, rate limits, and human-in-the-loop pauses natively. The application code is a series of workflow steps; the engine is the runtime that survives crashes.[7]

A durable workflow: each step's intent and result is journaled. A crash mid-flight resumes from the next un-run step, not from the beginning.
একটি টেকসই workflow: প্রতিটি ধাপের intent ও result জার্নাল করা হয়। মাঝ-উড়ানে ক্র্যাশ হলে, পরবর্তী un-run ধাপ থেকে resume হয়।

When you need it

  • The agent runs for more than ~30 seconds (anything that might survive a deploy).
  • Humans are in the loop and might take hours or days to respond.
  • The agent makes irreversible side effects (sending money, deleting records) that you want to be able to retry without duplicating.
  • The agent's work spans multiple services and you want to resume from the failed service.

Long agents need a "save and resume" engine.

The fix: durable execution. Treat the agent as a series of steps. After each step, write progress to a database. If the server crashes, the next process loads that log and resumes at the failed step.

When you need it: the agent runs for more than 30 seconds; humans are in the loop and might take days to respond; the agent makes irreversible side effects.

Pick a tool: Temporal or Restate for traditional, multi-day workflows. Inngest for event-driven. AWS Step Functions if you're all-in on AWS.

The-multi-day-recipe analogy: baking a wedding cake is a 4-step process. If your kitchen floods after step 2, you don't restart from day 1 — you read the recipe's checklist and resume at day 3.

দীর্ঘ agent-দের "save এবং resume" engine দরকার।

সমাধান: durable execution। agent-কে একটি সিরিজ ধাপ হিসেবে দেখুন। প্রতিটি ধাপের পর, একটি database-এ progress লিখুন।

চারটি durable engine: Temporal, Restate, Inngest, AWS Step Functions / DBOS।

10

Browser and computer-use agents

The newest agent category uses a model that can see a screenshot and act with mouse/keyboard primitives. OpenAI's Operator and Anthropic's "computer use" are the marquee examples. They trade precision for generality.

How computer use works

The model receives a screenshot of the desktop (or a specific window) and a list of available actions: mouse_move, left_click, right_click, type, key, screenshot. It picks an action, the runtime executes it, captures a new screenshot, and feeds both back. The loop continues until the model emits a done action.[9]

# Anthropic computer-use minimal loop (pseudocode)
while not done:
    screenshot = capture()
    response = client.messages.create(
        model="claude-sonnet-4-5",
        tools=["computer"],
        messages=[{"role": "user",
                   "content": [screenshot, goal]}],
    )
    for block in response.content:
        if block.type == "tool_use":
            execute(block.input)
    if response.stop_reason in ("end_turn", "max_tokens"):
        break

Where computer use wins

  • No API exists. The site or app has no programmatic interface; the only way in is the GUI.
  • The API is hostile. The vendor's API is rate-limited, expensive, or has bad docs; the GUI is faster.
  • One-off tasks. You need to do this once, not at scale, so the cost-per-task of computer use is acceptable.
  • Cross-app workflows. The task crosses SaaS boundaries (read from Gmail, post to Slack) and no integration exists.

Where computer use loses

  • Cost. Computer-use calls are 5–30× the cost of an API call (vision tokens for every screenshot).
  • Latency. A click is instant; a screenshot → LLM → action cycle is 1–5 seconds. A 20-step task takes a minute.
  • Reliability. A shifted button, a popup, a captcha — any of these kills the run.
  • Security. The agent has unrestricted mouse/keyboard. Pair with a sandboxed VM, a per-task browser profile, and a tight human-in-the-loop on destructive actions.

Browser agents vs computer use

Browser agents (ChatGPT's "Browse with Bing," Perplexity, Arc Max) are a constrained subset of computer use: the model can only see and act inside a single browser tab, not the whole desktop. They use the same screenshot → action loop but with a smaller surface area, which is why they're more reliable. If you can frame the task in a browser, prefer a browser agent over a full computer-use agent.

The reliability pattern

Production computer-use agents use three reliability patterns: (1) the model emits a structured plan up front ("I will click the blue button, then fill the form, then submit"), which makes mid-run debugging easier; (2) each step is checkpointed, so a crash resumes from the last successful step; (3) the agent runs in an isolated VM or browser profile, so a misclick can't reach the host system.

🖥️Layman's versionplain English, no jargon

Browser agents and computer-use agents are the "wild west" of AI.

Where they win: no API exists for the site; the API is hostile; one-off tasks where speed doesn't matter; cross-app workflows with no integration.

Where they lose: cost (5–30× more than an API call), latency (1–5 seconds per click vs instant), reliability (a shifted button kills the run), security.

Browser agents vs full computer use: browser agents are constrained to a single browser tab. Smaller surface = more reliable.

The reliability pattern: the model emits a plan up front, each step is checkpointed, and the agent runs in an isolated VM.

The-remote-intern analogy: a remote intern who can only see your screen and use a mouse. Slow, but they can do anything you can do.
