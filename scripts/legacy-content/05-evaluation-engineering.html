Evaluation engineering

If you can't measure it, you can't improve it. Evaluation engineering is the discipline of turning "the model feels worse today" into numbers, then turning the numbers into a CI signal that gates every prompt or model change.

Offline evals: golden datasets, regression tests

A golden dataset is a fixed set of (input, expected_output) pairs the model is run against on every change. Build it once, grow it from real failures, never let it decay. Run it in CI; block the release if accuracy drops below threshold.

LLM-as-judge

Many qualities ("does this answer sound helpful?", "is this code idiomatic?") can't be checked with regex. The trick is to use a strong LLM as a judge, with one of two modes:

  • Pairwise comparison: show the judge A and B, ask which is better. Beats absolute scoring, because relative judgements are easier than absolute ones.
  • Rubric-based scoring: define 4–6 criteria, ask the judge to rate each 0–5 with reasoning. Aggregate weighted score.

Best practice: use a different (often stronger) model as the judge than the one being evaluated; rotate judge prompts; periodically sanity-check the judge against human labels.[18]

RAG metrics: faithfulness, answer relevance, context precision/recall

The Ragas framework standardised four metrics that every RAG system should track:[19]

MetricQuestion
FaithfulnessDoes the answer stick to the retrieved chunks, or does it hallucinate?
Answer relevanceDoes the answer address the user's question?
Context precisionAre the retrieved chunks mostly relevant (not noise)?
Context recallWere all the chunks needed to answer actually retrieved?

Agent evals: task success, trajectory, tool-call accuracy

For agents, "the right answer" is necessary but not sufficient — you also need to check how it got there. Track:

  • Task success rate (final outcome correct?)
  • Trajectory match (did the agent take a reasonable path — same tools, similar number of steps?)
  • Tool-call accuracy (did each individual tool call have the right arguments?)
  • Step efficiency (how many steps vs. minimum needed?)

Synthetic data generation for evals

When your golden set is too small, use an LLM to synthesise plausible (input, expected_output) pairs from your docs and seed examples. Always include a contamination check — make sure synthetic questions aren't paraphrases of training data, otherwise you're testing memorisation, not capability.

Online evals on production traffic

Sample 1–5% of live requests, run cheap judges (heuristics, regex, small LLM), record the eval score alongside the trace. This catches real failures your offline set misses — distribution shifts, prompt-template copy-paste errors, fresh prompt injections.

Red teaming and adversarial testing

Build a set of attacks: prompt injection, jailbreaks, PII elicitation, hallucination bait. Run them monthly. Track the failure rate; treat any new failure as a bug to fix in the system prompt or guardrail.

📏Layman's versionplain English, no jargon

"How do I know the AI is actually good?" That's the question evaluation engineering answers. Without evals, you're guessing. With evals, you have numbers — and numbers let you make decisions.

Golden datasets = a fixed exam you give the AI every week. You write 200 questions the AI should know — "what's our refund policy?", "summarise this contract in 3 bullets", "convert this SQL to Pandas." Every time you change a prompt or upgrade a model, you run the exam. If the score drops, you don't ship the change. Real-world failures (the ones users actually report) get added to the exam, growing it over time.

LLM-as-judge = "let an AI grade another AI's homework." For things like "does this answer sound helpful?" you can't write a regex. So you have a second, usually stronger, AI score the first AI's answers. Two styles: (1) pairwise — show A and B side by side, ask which is better, (2) rubric — define 5 criteria, ask for 0–5 on each with reasoning. The pairwise style works better because relative judgements are easier than absolute ones.

RAG metrics = "is the AI cheating or actually using the documents?" Four numbers to track:

• Faithfulness: does the answer stick to what the documents say, or does the AI make stuff up?
• Answer relevance: does the answer address the user's question?
• Context precision: are the documents the AI pulled up mostly relevant?
• Context recall: did the AI pull up all the documents it needed, or did it miss a crucial one?

Agent evals = "did it work, and did it work well?" For agents, the final answer matters, but so does the path. Track: did it succeed? Did it use the right tools with the right parameters? Did it take 3 steps when a smart agent could do it in 2? Did it loop uselessly?

Synthetic data = "let the AI make its own homework." If your exam only has 50 items, use another LLM to write 1,000 more. But check that the synthetic questions aren't paraphrases of the training data — otherwise you're testing whether the AI memorised, not whether it understands.

Online evals = "grade a random 1% of real users in production." Even the best offline exam misses stuff. Sample real traffic, run cheap judges on it, save the scores. Now you catch things your offline exam never thought to test for.

Red teaming = "hire someone to try to break it." Every month, try to break your AI: try to inject prompts, try to extract training data, try to make it give medical advice, try to make it reveal other users' info. Each successful attack is a bug. Track them; ship fixes.

The school-exam analogy: think of your AI as a student. The golden dataset is the final exam you give it every week. LLM-as-judge is having a senior teacher grade essays (which can't be auto-graded). Agent evals check both whether the student got the right answer and whether they used the right method. Online evals are like pop quizzes — you surprise the student with real-world questions and see if they keep up. Red teaming is like hiring a mean teacher specifically to try to trick the student into mistakes.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

"AI আসলে কতটা ভালো, তা কীভাবে জানব?" এই প্রশ্নের উত্তর দেয় evaluation engineering। Eval ছাড়া আপনি অনুমান করছেন; eval-এর সাথে আপনার কাছে সংখ্যা আছে — এবং সংখ্যা সিদ্ধান্ত নিতে দেয়।

Golden dataset = প্রতি সপ্তাহে AI-কে দেওয়া একটি নির্দিষ্ট পরীক্ষা। ২০০টি প্রশ্ন লিখুন যা AI-এর জানা উচিত — "আমাদের refund policy কী?", "এই চুক্তিটি ৩টি bullet-এ সারমর্ম কর", "এই SQL-টি Pandas-এ রূপান্তর কর"। প্রতিটি prompt পরিবর্তন বা model upgrade-এর সময় পরীক্ষা চালান। স্কোর কমলে পরিবর্তন ship করবেন না। বাস্তব ব্যর্থতা (ব্যবহারকারীরা যেগুলো আসলে রিপোর্ট করে) পরীক্ষায় যোগ হয়, সময়ের সাথে এটি বাড়ে।

LLM-as-judge = "এক AI অন্য AI-এর হোমওয়ার্ক গ্রেড করে।" "এই উত্তর কি সহায়ক শোনায়?" এমন কিছুর জন্য regex লেখা যায় না। তাই দ্বিতীয়, সাধারণত শক্তিশালী, AI প্রথম AI-এর উত্তর স্কোর করে। দুটি ধরন: (১) pairwise — A ও B পাশাপাশি দেখিয়ে জিজ্ঞেস করুন কোনটি ভালো, (২) rubric — ৫টি মানদণ্ড সংজ্ঞায়িত করুন, প্রতিটিতে যুক্তিসহ ০–৫ চান। Pairwise ভালো কাজ করে কারণ আপেক্ষিক বিচার পরম বিচারের চেয়ে সহজ।

RAG metrics = "AI কি প্রতারণা করছে নাকি আসলেই ডকুমেন্ট ব্যবহার করছে?" চারটি সংখ্যা:

  • Faithfulness: উত্তর কি ডকুমেন্টে যা আছে তার সাথে সামঞ্জস্যপূর্ণ, নাকি AI বানিয়ে বলছে?
  • Answer relevance: উত্তর কি ব্যবহারকারীর প্রশ্নের সাথে সম্পর্কিত?
  • Context precision: AI যে ডকুমেন্টগুলো টেনে এনেছে সেগুলো কি বেশিরভাগই প্রাসঙ্গিক?
  • Context recall: AI কি উত্তর দেওয়ার জন্য প্রয়োজনীয় সব ডকুমেন্ট টেনে এনেছে, নাকি একটি গুরুত্বপূর্ণ ডকুমেন্ট মিস করেছে?

Agent evals = "এটা কাজ করেছে কি, এবং ভালোভাবে করেছে কি?" এজেন্টের জন্য চূড়ান্ত উত্তর গুরুত্বপূর্ণ, কিন্তু path-টাও। ট্র্যাক করুন: সফল হয়েছে? সঠিক টুল সঠিক parameter-সহ ব্যবহার করেছে? ২ ধাপে করা যায় এমন কাজে ৩ ধাপ নিয়েছে? অকারণে লুপ করেছে?

Synthetic data = "AI-কে তার নিজের হোমওয়ার্ক তৈরি করতে দিন।" আপনার পরীক্ষায় মাত্র ৫০টি আইটেম থাকলে, অন্য LLM দিয়ে আরও ১,০০০টি লিখুন। কিন্তু যাচাই করুন যে synthetic প্রশ্নগুলো training data-র অনুবাদ নয় — নতুননা আপনি AI মুখস্থ করেছে কিনা তা পরীক্ষা করছেন, বুঝেছে কিনা তা নয়।

Frameworks: Promptfoo (CLI-first, YAML configs, CI-friendly, provider-agnostic), DeepEval (pytest-style, বিল্ট-ইন metric প্রচুর — G-Eval, hallucination, bias), Inspect (UK AISI, research-y task, safety eval-এর জন্য শক্তিশালী), Braintrust (eval UI + trace + dataset management), OpenAI Evals / Anthropic Eval templates (vendor-প্রস্তুত baseline)।

Online evals on production traffic: live request-এর ১–৫% sample করুন, সস্ত judge (regex, ছোট LLM) চালান, eval স্কোর trace-এর সাথে রেকর্ড করুন। এটি আপনার offline set মিস করা বাস্তব ব্যর্থতা ধরে — distribution shift, prompt-template copy-paste error, fresh prompt injection।

Red teaming ও adversarial testing: আক্রমণের একটি সেট তৈরি করুন: prompt injection, jailbreak, PII elicitation, hallucination bait। মাসে একবার চালান। ব্যর্থতার হার ট্র্যাক করুন; যেকোনো নতুন ব্যর্থতা system prompt বা guardrail-এ ঠিক করার বাগ।

স্কুল পরীক্ষার উপমা: AI-কে একজন শিক্ষার্থী হিসেবে ভাবুন। Golden dataset হলো প্রতি সপ্তাহে দেওয়া চূড়ান্ত পরীক্ষা। LLM-as-judge হলো একজন সিনিয়র শিক্ষককে দিয়ে রচনা গ্রেডন (যা অটো-গ্রেড করা যায় না)। Agent evals যাচাই করে শিক্ষার্থী সঠিক উত্তর দিয়েছে কিনা এবং সঠিক পদ্ধতি ব্যবহার করেছে কিনা। Online evals pop quiz-এর মতো — বাস্তব-বিশ্বের প্রশ্ন দিয়ে শিক্ষার্থীকে অবাক করে দেখান সে টিকে থাকে কিনা। Red teaming হলো শিক্ষার্থীকে ভুলে ফেলার জন্য একজন mean teacher নিয়োগ করা।
