AI application architecture

An LLM call is just one HTTP request. Building a product around it requires the same plumbing any modern app needs, plus a few new primitives: streaming, resumability, multi-tenancy, fallbacks, feature flags, and an API surface designed for partial results.

Streaming over SSE / WebSockets / HTTP chunked

Users expect words to appear as the model writes them, not after a 3-second pause. Three transports:

  • SSE (Server-Sent Events): the simplest; works through any HTTP proxy; one-way (server→client).
  • WebSockets: bidirectional; needed for voice and collaborative UIs; heavier handshake.
  • HTTP chunked transfer: a fallback for proxies that strip SSE headers.
# OpenAI streaming
  for chunk in client.chat.completions.create(
        model="gpt-4o", stream=True,
        messages=messages):
    token = chunk.choices[0].delta.content or ""
    print(token, end="", file=sys.stdout)

Background jobs and queues for long agent runs

Anything over ~10 seconds should not block an HTTP request. Push it to a queue (BullMQ, Celery, Inngest, Cloud Tasks, Temporal) and return a job_id. Client polls or subscribes via SSE/WebSocket for updates. This is the single biggest UX win for "the agent took 4 minutes" tasks.

Idempotency and resumability

LLM calls fail. Networks drop. Users refresh. Always:

  • Generate an idempotency key per request; reject duplicates.
  • Store checkpoints of agent state so a resume replays only the failed steps.
  • Use durable execution (Temporal/Restate) for anything longer than a minute.

Multi-tenant prompt and key management

Per-tenant prompt overrides, per-tenant API keys, per-tenant rate limits, per-tenant tracing. The cleanest pattern: store all of these in a tenant_config row, fetch at the edge of every request, attach to the trace. Never hard-code a tenant's prompt in their codebase.

Fallback chains across providers

OpenAI 503s? Route to Anthropic. Anthropic 429s? Route to Together. With degraded prompts per provider ("you have no tool use; just answer"). LiteLLM and Portkey do this out of the box; a model gateway is essentially a fallback router plus cost tracking.

Feature flags for prompts and models

Treat every prompt and every model as a flag. Roll out "use GPT-5 for premium users only" to 1%, then 10%, then 100%. Roll back instantly when evals regress. LaunchDarkly, Statsig, PostHog, or a simple DB column — pick one and use it for prompts.

API design patterns for AI features

Five rules that distinguish an AI API from a normal REST API:[30]

  • Cancel mid-flight: the client should be able to abort the request and stop the bill.
  • Retry idempotently: same request + idempotency key → same response, no double billing.
  • Return partial results: stream tokens, return intermediate tool states, never make the client wait until completion.
  • Structured confidence: include a self-reported confidence, logprobs, or a "would I retry this?" field.
  • Cost/latency budget in the request: let the client say "spend up to $0.05 and 8s"; the server respects it.
🏗️Layman's versionplain English, no jargon

An LLM call is one HTTP request. A product is a thousand of those wrapped in plumbing.

Streaming = "show the words as they come." Users hate 3-second pauses before anything appears. Stream tokens to the browser as the AI writes them — the same way Twitter shows posts one at a time instead of all at once. SSE (server-sent events) is the simplest way; WebSockets if you need two-way chat.

Background jobs = "the long task runs in the background, you go on with your day." Anything taking more than ~10 seconds shouldn't make the user wait with a loading spinner. Push the task to a queue, return "your job is #4711, here's a link to check on it." This is how email batch processors, video uploaders, and now AI agents work.

Idempotency = "if you accidentally click twice, you only pay once." Every request gets a unique ID. If the same ID shows up again, the server says "I already answered that, here's the same result." Without it, retrying because of a timeout could double your cost.

Multi-tenant prompt management = "each customer has their own brain." If you're building for 100 customers, each customer's AI should be tuned to their voice, their policies, their data. Don't hard-code prompts in each customer's app. Store them centrally, fetch them per request, log which version ran.

Fallback chains = "if Vendor A is down, use Vendor B." OpenAI 503s? Anthropic is up? Send the next 100 requests to Anthropic. A "model gateway" is just a router that does this for you automatically, with cost tracking.

Feature flags for prompts = "I'll roll out the new brain to 1% of users first." Want to test a new prompt? Don't change it for everyone. Set a flag: "users with ID ending in 87 get the new prompt." Roll to 1%, measure, roll to 100%. Roll back instantly if it breaks.

API design rules for AI:

• Cancel mid-flight: let the user stop a request and stop the bill.
• Retry idempotently: same request ID → same result, no double work.
• Partial results: stream tokens, never make the client wait until "done."
• Confidence field: include "how sure am I?" in the response.
• Budget field: the client can say "spend up to $0.05 and 8s, no more."

The restaurant-kitchen analogy: building an AI app is like running a restaurant kitchen. Streaming is serving courses as they're ready instead of holding every plate until the whole table is done. Background jobs are prep work that runs before dinner service. Idempotency is "if the same order slips twice, we don't cook it twice." Fallback chains are "if the fish supplier is out, get it from the second supplier." Feature flags are "Monday only this table gets the new menu." API design is the rules the waiters agree on ("don't bring the bill before dessert," "always bring water first").
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

একটি LLM কল হলো একটি HTTP অনুরোধ। এর চারপাশে একটি পণ্য তৈরি করতে যেকোনো আধুনিক অ্যাপের প্রয়োজনীয় সাধারণ plumbing দরকার, সাথে কিছু নতুন primitive — streaming, resumability, multi-tenancy, fallbacks, feature flags, এবং partial results-এর জন্য ডিজাইন করা একটি API surface।

SSE / WebSockets / HTTP chunked দিয়ে streaming: ব্যবহারকারীরা ৩ সেকেন্ডের বিরতির পরে নয়, মডেল যেভাবে লেখে সেভাবে শব্দ দেখতে চায়। তিনটি transport: SSE (সবচেয়ে সহজ, যেকোনো HTTP proxy-র মধ্য দিয়ে কাজ করে, একমুখী), WebSockets (দ্বিমুখী; voice ও সহযোগী UI-এর জন্য দরকার), HTTP chunked transfer (SSE header strip করে proxy-র জন্য fallback)।

দীর্ঘ এজেন্ট রানের জন্য background jobs ও queues: ~১০ সেকেন্ডের বেশি যেকোনো কিছু HTTP request block করা উচিত নয়। একটি queue-তে (BullMQ, Celery, Inngest, Cloud Tasks, Temporal) push করুন এবং একটি job_id ফেরত দিন। ক্লায়েন্ট poll করে বা SSE/WebSocket দিয়ে update সাবস্ক্রাইব করে। "এজেন্ট ৪ মিনিট নিয়েছে" কাজের জন্য এটাই একমাত্র সবচেয়ে বড় UX জয়।

Idempotency ও resumability: LLM কল ব্যর্থ হয়। নেটওয়ার্ক ড্রপ হয়। ব্যবহারকারী refresh করে। সর্বদা: প্রতিটি request-এর জন্য একটি idempotency key তৈরি করুন; duplicate প্রত্যাখ্যান করুন। এজেন্ট state-এর checkpoint সংরক্ষণ করুন যাতে resume শুধু ব্যর্থ ধাপগুলো replay করে। এক মিনিটের বেশি যেকোনো কিছুর জন্য durable execution (Temporal/Restate) ব্যবহার করুন।

Multi-tenant prompt ও key management: প্রতি-tenant prompt override, প্রতি-tenant API key, প্রতি-tenant rate limit, প্রতি-tenant tracing। সবচেয়ে পরিষ্কার প্যান্টার্ন: এগুলো সব একটি tenant_config row-তে সংরক্ষণ করুন, প্রতিটি request-এর edge-এ fetch করুন, trace-এ যুক্ত করুন। কখনোই একটি tenant-এর prompt তাদের codebase-এ hard-code করবেন না।

Provider-জুড়ে fallback chains: OpenAI 503 দিলে? => Anthropic-এ route করুন। Anthropic 429 দিলে? => Together-এ route করুন। Degraded prompt সহ (প্রতি provider-এর জন্য "আপনার tool use নেই; শুধু উত্তর দিন")। LiteLLM ও Portkey এটি বাক্সের বাইরে করে; একটি model gateway মূলত একটি fallback router ও খরচ ট্র্যাকিং।

Prompt ও model-এর জন্য feature flags: প্রতিটি prompt ও প্রতিটি model-কে flag হিসেবে দেখুন। "শুধু premium ব্যবহারকারীদের জন্য GPT-5 ব্যবহার করুন" ১%, তারপর ১০%, তারপর ১০০%-এ roll out করুন। Eval regress করলে তাৎক্ষণিকভাবে roll back করুন। LaunchDarkly, Statsig, PostHog, বা একটি সাধারণ DB column — একটি বেছে নিন এবং prompt-এর জন্য এটি ব্যবহার করুন।

AI feature-এর জন্য API design patterns: পাঁচটি নিয়ম যা একটি AI API-কে সাধারণ REST API থেকে আলাদা করে:[30]

  • মাঝ-উড়ানে cancel: ক্লায়েন্ট request abort করতে এবং বিল বন্ধ করতে সক্ষম হওয়া উচিত।
  • Idempotently retry: একই request + idempotency key → একই response, কোনো দ্বিগুণ billing নয়।
  • Partial results ফেরত দিন: token stream করুন, মধ্যবর্তী tool state ফেরত দিন, ক্লায়েন্টকে কখনো সম্পূর্ণ হওয়া পর্যন্ত অপেক্ষা করাবেন না।
  • Structured confidence: একটি self-reported confidence, logprobs, বা "আমি কি এটি retry করব?" ক্ষেত্র অন্তর্ভুক্ত করুন।
  • Request-এ cost/latency budget: ক্লায়েন্টকে বলতে দিন "সর্বোচ্চ $0.05 ও 8s খরচ করুন"; server সেটি মানে।
রেস্তোরাঁ-রান্নাঘরের উপমা: AI অ্যাপ তৈরি করা একটি রেস্তোরাঁর রান্নাঘর চালানোর মতো। Streaming হলো সম্পূর্ণ টেবিল শেষ না হওয়া পর্যন্ত প্রতিটি প্লেট আটকে না রেখে প্রস্তুত হওয়ার সাথে সাথে course পরিবেশন করা। Background jobs হলো dinner service-এর আগে চলা prep কাজ। Idempotency হলো "একই order দুইবার slip হলে আমরা দুইবার রান্না করি না।" Fallback chains হলো "মাছ supplier-এর কাছে নেই, দ্বিতীয় supplier থেকে নাও।" Feature flags হলো "সোমবার শুধু এই টেবিল নতুন menu পায়।" API design হলো waiter-দের মধ্যে চুক্তি করা নিয়ম ("dessert-এর আগে bill আনবেন না", "সর্বদা আগে পানি আনুন")।
