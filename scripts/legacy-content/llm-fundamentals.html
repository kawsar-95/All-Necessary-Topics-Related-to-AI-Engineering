Tokens, tokenization & context cost

Everything a model does — attention, generation, cost — is denominated in tokens, not characters or words. If your prompt shrinks from 800 to 200 tokens, you just cut cost by 75% and latency by a meaningful fraction. This is the single biggest engineering lever you have.

What is a token?

A token is one element in the model's vocabulary. Modern LLMs don't read characters; they read the output of a subword tokenizer — most commonly Byte-Pair Encoding (BPE), which iteratively merges the most frequent adjacent pairs in a corpus until a target vocabulary size (often 32k–200k) is reached.[15] For multilingual and code workloads, SentencePiece is the dominant alternative — it operates directly on raw Unicode bytes or whitespace, treating language as a configuration parameter.[16]

BPE tokenization in practice: English byte-runs merge into common pieces; punctuation and whitespace often become standalone tokens.
এই diagram-এ দেখানো হয়েছে raw input টেক্সট কীভাবে BPE merges-এর মাধ্যমে subword pieces-এ ভাগ হয় এবং প্রতিটি piece একটি token ID পায়। উপর থেকে নিচে পড়ুন: মডেল কখনো characters দেখে না, শুধু এই integer IDs-ই embedding table-এ যায়।

Why this matters: the cost equation

APIs charge per token, not per character. A useful mnemonic: ~1 token ≈ 4 characters in English for most modern tokenizers, but this varies wildly by language — Chinese runs ~1 char ≈ 1.5 tokens, code ~1 token ≈ 3.5 chars, numbers are split digit-by-digit in early tokenizers but consolidated in newer ones.

# Counting tokens with tiktoken (OpenAI) or transformers
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
text = "Tokenization is the silent tax on every LLM call."
print(len(enc.encode(text)))   # → 11 tokens, not 8 words

# Concrete cost (input, gpt-4o-mini, Jul 2025 pricing)
tokens        = 11
price_per_m   = 0.15      # USD per 1M input tokens
cost_per_call = tokens / 1_000_000 * price_per_m   # → $0.00000165

Context windows — what they actually are

The context window is the maximum total tokens (input + output) the model can attend to in a single call. It has grown dramatically: GPT-3's 2K window in 2020 → 8K (GPT-3.5) → 128K (GPT-4o) → 1M+ (Gemini 1.5).[1][11]

Long context ≠ free performance. Even with 1M-token windows, retrieval-augmented generation, summarisation, or hierarchical attention beats dumping 800K tokens in. Needle-in-a-haystack benchmarks improve, but multi-hop reasoning across long contexts degrades sharply. Measure on your own workloads.

Think of a token like a "word piece." When you read this sentence, you see whole words. An LLM doesn't see words — it sees chunks. "Unbelievable" might be three chunks: un + believ + able. Common chunks like "the" or "ing" are single chunks. Weird stuff ("Doha", "kubernetes") gets chopped into more chunks.

Why does this matter to you? Because every API charge is per chunk, not per word. A 100-word email is roughly 130 chunks. A 100-word email stuffed with code and rare names might be 220 chunks. Same email, double the cost — just from language alone.

Context window = the model's short-term memory. You know how if a friend has been listening for 4 hours straight, they start forgetting things you said an hour ago? LLMs do the same thing, just more abruptly. "Context window" is the size of their working memory — usually 8K to 1M chunks. Bigger isn't always better: cramming 800K chunks in doesn't make the model 100× smarter, it just makes the bill bigger.

The kitchen analogy: tokens are like "ingredients on the counter." The context window is the counter size. A tiny counter (2K) means you can only cook small meals. A huge counter (1M) lets you cook for a wedding — but you still have to actually cook, and the bigger meal doesn't come out better just because you had room.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Token হলো LLM-এর ভোকাবুলারির একেকটি টুকরো। মডেল অক্ষর বা পুরো শব্দ পড়ে না; একটি subword tokenizer শব্দকে ভেঙে ছোট ছোট অংশে পরিণত করে, যার জনপ্রিয় পদ্ধতি BPE (Byte-Pair Encoding)। এটি corpus-এর সবচেয়ে ঘন ঘন পাশাপাশি আসা জোড়াগুলো বারবার মিলিয়ে নেয়, যতক্ষণ না নির্দিষ্ট vocabulary size (প্রায়ই 32k–200k) হয়। বহুভাষিক ও কোডের কাজে SentencePiece বেশি ব্যবহৃত হয়। মডেল শেষ পর্যন্ত শুধু token ID (পূর্ণসংখ্যা) দেখে, যা embedding table-এ যায়।

খরচের হিসাব হয় token দিয়ে, অক্ষর দিয়ে নয়। ইংরেজিতে মোটামুটি 1 token ≈ 4 অক্ষর, কিন্তু ভাষাভেদে এটি অনেক বদলায়: চীনা ভাষায় 1 অক্ষর ≈ 1.5 token, কোডে 1 token ≈ 3.5 অক্ষর। তাই prompt 800 থেকে 200 token-এ নামালে খরচ 75% কমে এবং latency-ও কমে। এটাই সবচেয়ে বড় engineering lever।

Context window হলো এক কলে মডেল সর্বোচ্চ কত token (input + output মিলিয়ে) দেখতে পারে। এটি GPT-3-এর 2K থেকে বেড়ে এখন 1M+ পর্যন্ত গেছে। খরচ ও গতির দিক থেকে: prefill (prompt প্রসেসিং) এর খরচ input token অনুযায়ী, আর decode (লেখা তৈরি) ধাপে ধাপে হয় এবং output token সাধারণত input-এর চেয়ে 3–5 গুণ দামি। Prompt caching বারবার আসা prefix-এর খরচ প্রায় 80–90% কমায়।

সতর্কতা: বড় context মানে নিখুঁত পারফরম্যান্স নয়। 800K token ঢেলে দেওয়ার চেয়ে RAG বা summarisation প্রায়ই ভালো, কারণ লম্বা context-এ multi-hop reasoning দ্রুত খারাপ হয়। নিজের workload-এ মেপে দেখুন।

দর্জির দোকানের উপমা: কাপড়ের থান (পুরো লেখা) দর্জি আগে ছোট ছোট টুকরোয় কেটে নেয় (token), আর মজুরি হয় টুকরোর সংখ্যা ধরে। Context window হলো দর্জির কাটিং টেবিলের মাপ: টেবিল যত বড়, একসাথে তত কাপড় ছড়িয়ে কাজ করা যায়। কিন্তু টেবিল বড় হলেই জামা সুন্দর হয় না; আর অকারণে বেশি কাপড় ছড়ালে খরচ ও সময় দুটোই বাড়ে।

Model families & trade-offs

The frontier in 2025 is dominated by five families, each with a distinct architectural and commercial philosophy. Picking "the best model" is a misframe — the right question is which trade-off matches your workload's centre of gravity.

Architectural distinctions that matter

Dense transformers

Every parameter is used on every token. Predictable compute, simple serving. Examples: Llama 3.1 8B, Mistral 7B.[2][4]

Mixture-of-Experts (MoE)

Routes each token to a subset of "expert" FFNs. Total params large but active params per token small → cheaper inference, larger memory. Mixtral 8×7B, DeepSeek-V3 (671B/37B active), Qwen3-235B-A22B.[5][6][28]

Multi-Head Latent Attention (MLA)

DeepSeek's innovation: compresses the KV cache into a low-rank latent, slashing memory for long contexts.[6]

Sliding-window / hybrid

Mistral 7B pioneered sliding-window attention for cheap inference. Gemini 1.5 mixes local + global attention for million-token contexts.[4][11]

🚗Layman's versionplain English, no jargon

Imagine cars on a road. Each "model family" is a different car brand — they all get you from A to B, but they have different personalities. Anthropic (Claude) is the careful Volvo: best at reading long, complicated documents and being safe. OpenAI (GPT) is the polished Tesla: the most famous, with a huge ecosystem of accessories. Google (Gemini) is the minivan: huge cargo space (it can hold millions of words at once) and built-in cameras. Meta (Llama) is the kit car: you get the blueprints for free and build it yourself in your garage. Mistral is the European hatchback — small, nimble, made in France.

And then there are the Chinese manufacturers. Alibaba's Qwen and DeepSeek are like Xiaomi and BYD: they came out of nowhere, the open-weights version is free, and benchmarks say they keep up with the expensive brands. In 2024–2025 they went from "who?" to "frontier-tier."

Why are some free? "Open-weight" means the company released the file containing the model's brain — anyone can download it. They still trained it on expensive computers, but once the file exists, copying it costs nothing. It's the difference between a chef who sells them dishes (closed) and a chef who publishes the recipe (open).

Which should you pick? If you're a regular user, just use the brand with the best app (probably ChatGPT or Claude). If you're building software: pick closed for the absolute best capability, pick open-weight to save money at scale or keep it inside your company.

The car analogy again: closed models = renting a luxury car monthly. Open-weight = buying the car (or a cheap one) outright. If you drive 100 miles a month, renting is cheap. If you drive 100,000, buying wins. The 2025 sweet spot for most companies: rent for hard problems, own for the easy stuff you do millions of times.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

"সেরা মডেল" বলে কিছু নেই, প্রশ্ন হলো আপনার workload-এর জন্য কোন trade-off মানানসই। প্রধান পরিবারগুলো: OpenAI (GPT-4o, o3, GPT-5) reasoning ও পরিণত ecosystem-এ ভালো; Anthropic (Claude 4) লম্বা context (200K), কোড-এজেন্ট ও দীর্ঘ ডকুমেন্ট বিশ্লেষণে ভালো; Google (Gemini 2.5) native multimodal ও 1–2M context-এ এগিয়ে; Meta (Llama 3.1) open weights ও শক্তিশালী ছোট মডেল; Mistral ইউরোপীয় data residency ও edge deployment-এর জন্য; Alibaba Qwen3 সস্তা self-host ও বহুভাষিক কাজে; DeepSeek (V3, R1) কম training খরচে শক্তিশালী open-weight reasoning-এ।

স্থাপত্যগত পার্থক্যও গুরুত্বপূর্ণ। Dense transformer-এ প্রতিটি token-এর জন্য সব parameter ব্যবহার হয়, তাই compute অনুমানযোগ্য ও serving সহজ। Mixture-of-Experts (MoE)-এ প্রতিটি token শুধু কিছু "expert" FFN-এ যায়: মোট parameter বিশাল কিন্তু active parameter কম, ফলে inference সস্তা হলেও memory বেশি লাগে (যেমন DeepSeek-V3: 671B মোট, 37B active)। MLA (Multi-Head Latent Attention) KV cache-কে ছোট করে লম্বা context-এর memory বাঁচায়। Sliding-window বা hybrid attention সস্তা inference ও বিশাল context-এ সাহায্য করে।

বাছাইয়ের নিয়ম: সর্বোচ্চ ক্ষমতা লাগলে closed মডেল, আর খরচ কমানো বা data নিজেদের কাছে রাখতে চাইলে open-weight।

পরিবহনের উপমা: প্রতিদিন অফিস করতে আপনি কখনো রিকশা, কখনো বাস, আবার জরুরি দরকারে উবার নেন। সব যানই গন্তব্যে পৌঁছে দেয়, কিন্তু দাম, আরাম ও গতি আলাদা। তেমনি সহজ কাজ ছোট সস্তা মডেলে, আর কঠিন কাজ ফ্রন্টিয়ার মডেলে চালানোই বুদ্ধিমানের কাজ।

Closed vs open-weight models

"Open" splits into two camps that engineers often confuse: open-weight (you can download and run the model) and open-source (you also have training code, data, and licence to modify and redistribute). Most "open" LLMs are open-weight.

Closed / proprietary

Hosted behind APIs. Examples: GPT-4o/o3/GPT-5, Claude 4, Gemini 2.5. Advantages: highest capability ceiling, fastest hardware optimisation, integrated safety stack, no infra to run. Costs: vendor lock-in, no auditability of weights, data leaves your perimeter, price changes are unilateral.[14][13]

Open-weight

Weights released under a licence (often Apache 2.0, Llama Community License, or MIT). Examples: Llama 3.1 (8B–405B),[3] Mistral 7B & Mixtral 8×7B,[4][5] Qwen2.5/Qwen3,[8][9] DeepSeek-V3 / R1.[6][7] Advantages: self-host on your hardware, fine-tune on private data, audit weights, no per-token fees, no data egress. Costs: you operate the infra (GPUs, networking, monitoring), capability ceiling ~3–9 months behind the frontier, safety is your problem.

When open-weight wins: predictable cost at scale, data residency / compliance requirements, need to fine-tune on proprietary data, latency-sensitive serving where inference co-locates with state.
When closed wins: tasks where you're 3–9 months behind the SOTA matters (frontier coding agents, reasoning), small query volume makes self-hosting uneconomical, you need multimodal audio/video (Gemini).

Hybrid patterns becoming standard

  • Distillation: DeepSeek-R1's distilled Qwen/Llama variants prove you can train strong small open models from a closed teacher's outputs.[7]
  • Routing: route easy queries to a local 8B, hard ones to a frontier API. Saves cost without measurable quality loss on common tasks.
  • Open-weights with closed APIs: Llama 3.1 405B is open, and you can also call it via Together, Groq, Fireworks for managed serving — keeping the option to migrate.
🔓Layman's versionplain English, no jargon

"Closed" vs "open-weight" is about who owns the brain.

Closed (GPT, Claude, Gemini): the AI lives on the company's servers. You talk to it through their app or API. Your data travels to them, they run the model, the answer travels back. You can never inspect the actual model — like renting a black-box appliance.

Open-weight (Llama, Qwen, DeepSeek, Mistral): the company released the file containing all the model's "knowledge" — billions of numbers that together form a brain. Anyone can download this file (it's huge — 8 to 700 gigabytes) and run it on their own computers. The recipe is public, even if the cookbook is not.

What's the catch? "Open-weight" is not the same as "open-source." You usually can't see how it was trained, what data, or modify it freely. You can run it, fine-tune it on your own data, and deploy it. But retraining from scratch? That costs millions of dollars in computers.

The 2025 reality: open-weight models got so good that for most business tasks, a free open-weight model running on rented GPUs is 80% as good as GPT-4 at 10% of the cost. Companies are quietly switching. The frontier closed models (Claude 4, GPT-5) still lead on hard reasoning, but the gap is small.

The cookbook analogy: closed = a chef who sells you meals but won't share recipes. Open-weight = a chef who wrote the recipe book; you can cook it yourself or pay someone to cook it for you. Open-source = a chef who shared the kitchen, the suppliers, AND the recipes — that's almost never available for LLMs.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

"Open" শব্দটি দুই অর্থে ব্যবহৃত হয় এবং ইঞ্জিনিয়াররা প্রায়ই গুলিয়ে ফেলেন। Open-weight মানে মডেলের weights ডাউনলোড করে নিজে চালানো যায়। Open-source মানে এর সাথে training code, data এবং পরিবর্তন ও পুনর্বিতরণের লাইসেন্সও পাওয়া যায়। বেশিরভাগ "open" LLM আসলে শুধু open-weight।

Closed/proprietary মডেল (GPT, Claude, Gemini) API-র পেছনে থাকে। সুবিধা: সর্বোচ্চ ক্ষমতা, দ্রুত hardware optimisation, তৈরি safety stack, নিজের infra চালাতে হয় না। অসুবিধা: vendor lock-in, weights যাচাই করা যায় না, data আপনার সীমানার বাইরে যায়, আর দাম তারা একতরফা বদলাতে পারে।

Open-weight (Llama, Mistral, Qwen, DeepSeek) মডেলে আপনি নিজের হার্ডওয়্যারে চালাতে পারেন, private data-য় fine-tune করতে পারেন, weights audit করতে পারেন, per-token ফি লাগে না এবং data বাইরে যায় না। বিনিময়ে GPU, networking ও monitoring আপনাকেই চালাতে হবে, ক্ষমতা ফ্রন্টিয়ার থেকে প্রায় 3–9 মাস পিছিয়ে, আর safety-র দায়ও আপনার।

  • Open-weight জেতে যখন scale-এ অনুমানযোগ্য খরচ, data residency/compliance, proprietary data-য় fine-tuning বা latency-সংবেদী serving দরকার।
  • Closed জেতে যখন ফ্রন্টিয়ার কোডিং/reasoning লাগে, query কম বলে self-host লাভজনক নয়, অথবা audio/video multimodal দরকার।
  • Hybrid প্যাটার্ন এখন সাধারণ: distillation, সহজ query ছোট লোকাল মডেলে ও কঠিনগুলো ফ্রন্টিয়ার API-তে পাঠানো (routing), এবং Together/Groq/Fireworks-এর মতো managed serving।
বাসা ভাড়া বনাম নিজের বাড়ির উপমা: Closed মডেল ভাড়া বাসার মতো: মালিক সব দেখভাল করে, কিন্তু ভাড়া বাড়ালে আপনার কিছু করার নেই, আর দেয়াল ভাঙার অনুমতি নেই। Open-weight হলো নিজের বাড়ি: ইচ্ছেমতো সাজাতে পারেন, কিন্তু মেরামত ও পাহারার ঝামেলা আপনার। আর Open-source হলো বাড়ির নকশা, ইট-সিমেন্টের হিসাব ও কারিগর সবকিছু পাওয়া, যা LLM-এর ক্ষেত্রে প্রায় দেখাই যায় না।
04

Sampling parameters

A model outputs a probability distribution over every token in its vocabulary. Sampling is how you turn that distribution into text. The same logits can produce robotic lists, creative prose, or factual hallucinations depending on five knobs.

The knobs

Visualising how temperature flattens or sharpens the distribution, and where truncation steps (top_k, top_p, min_p) cut the tail.
এখানে দেখা যায় raw logits কীভাবে softmax, temperature, top_k, top_p, min_p ও repetition penalties পেরিয়ে শেষে sample হয়। বাঁ থেকে ডানে পড়ুন: T কম হলে বণ্টন sharp (greedy), T বেশি হলে flat (noise), আর truncation ধাপগুলো কম-সম্ভাবনার tail কেটে দেয়।
ParameterWhat it doesWhen to tune it
temperature Divide logits by T before softmax. T<1 sharpens (more deterministic), T>1 flattens (more random). 0 = code, JSON, classification, math.
0.7–1.0 = chat.
1.0–2.0 = creative writing, brainstorming.
top_k Restrict sampling to the k highest-prob tokens. k=1 = greedy. k≈40–100 typical. Avoid k<10 with high temperature.
top_p (nucleus) Keep the smallest set of tokens whose cumulative probability ≥ p. 0.9–0.95 is the usual sweet spot. Often used with top_k.
min_p Drop tokens with prob < min_p × top_prob. Recent alternative to top_p. Scales better across model sizes than fixed top_p.
frequency_penalty Subtract α × (count of token) from logits each step. Discourages repetition. 0.1–1.0 typical.
presence_penalty Subtract α if token has appeared at all. Encourages topical diversity. 0–0.6 typical. 
# OpenAI-compatible sampling params (works across providers)
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    temperature=0.2,        # low for JSON extraction
    top_p=1.0,              # off when temperature low
    frequency_penalty=0.3,
    presence_penalty=0.0,
    max_tokens=512,
)
Don't combine top_k and top_p aggressively. Either pick top_k (fixed vocabulary cut) or top_p (probability mass cut). Using both with tight values double-strips the tail and can cause degeneration. Modern providers recommend temperature + top_p (or temperature + min_p), full stop.
🎲Layman's versionplain English, no jargon

Inside the AI, every word is a dice roll. When the model writes "The cat sat on the..." it has a list of probabilities: mat 40%, floor 25%, couch 15%, roof 8%, ... and thousands of weird options at fractions of a percent. The model has to choose one. How it chooses is "sampling."

Temperature is the dice's "creativity dial." Set it to 0 and the model always picks mat — boring, predictable, perfect for code or facts. Crank it up to 1.2 and it might pick roof, cathedral, or porcupine — fun, surprising, occasionally nonsense. Set it to 2 and it's babbling.

top_p and top_k are "filters." Imagine you only let the dice roll the top 50 candidates (top_k=50), or only the candidates whose probabilities add up to 90% (top_p=0.9). This stops it from picking the bizarre long-shots.

Penalties are memory aids. "frequency_penalty" means "stop saying the the the the the." "presence_penalty" means "you already mentioned dogs, try a new topic."

The cheat sheet: code/JSON/facts → temperature 0. Chat → 0.7. Creative writing → 1.0–1.3. Don't combine lots of filters — pick one and trust it.

The dinner party analogy: the model is a friend picking from the menu. Temperature 0 = "always order the safest thing." Temperature 1 = "pick whatever sounds good tonight." Temperature 2 = "order whatever's weirdest on the menu." top_p/top_k = "don't even look at the last 3 pages of the menu, nothing weird there is worth trying."
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

মডেল প্রতিটি ধাপে ভোকাবুলারির সব token-এর ওপর একটি সম্ভাবনা বণ্টন (probability distribution) তৈরি করে। Sampling হলো সেই বণ্টন থেকে একটি token বেছে নেওয়ার পদ্ধতি। একই logits থেকে এই knob-গুলোর কারণে কখনো রোবটিক তালিকা, কখনো সৃজনশীল লেখা বা hallucination বেরোতে পারে।

  • temperature: softmax-এর আগে logits-কে T দিয়ে ভাগ করে। T<1 হলে বণ্টন ধারালো (বেশি deterministic), T>1 হলে সমতল (বেশি random)। কোড, JSON, classification, math-এর জন্য 0; chat-এর জন্য 0.7–1.0; সৃজনশীল লেখা ও brainstorming-এর জন্য 1.0–2.0।
  • top_k: শুধু সবচেয়ে সম্ভাব্য k-টি token থেকে বাছে। k=1 মানে greedy; সাধারণত k≈40–100। বেশি temperature-এর সাথে k<10 এড়ানো ভালো।
  • top_p (nucleus): যে ক্ষুদ্রতম token-সেটের সম্মিলিত সম্ভাবনা ≥ p, শুধু সেটি রাখে। সাধারণত 0.9–0.95।
  • min_p: top token-এর সম্ভাবনার min_p গুণের চেয়ে কম সম্ভাবনার token বাদ দেয়; মডেলের আকার বদলালেও এটি ভালো কাজ করে।
  • frequency_penalty: token যতবার এসেছে তার সংখ্যা অনুযায়ী logit কমায়, ফলে পুনরাবৃত্তি কমে (সাধারণত 0.1–1.0)।
  • presence_penalty: token একবার এসে থাকলেই কমায়, ফলে বিষয়ের বৈচিত্র্য বাড়ে (সাধারণত 0–0.6)।

সাধারণ ভুল: top_k ও top_p একসাথে কড়াভাবে দিলে tail দুইবার ছাঁটা হয়ে লেখা অসংলগ্ন (degeneration) হতে পারে। আধুনিক প্রোভাইডাররা temperature + top_p (অথবা temperature + min_p) ব্যবহারের পরামর্শ দেন।

চায়ের দোকানের উপমা: আপনি চায়ের দোকানে গেছেন। Temperature 0 হলো রোজকার মতো সেই একই নিরাপদ চা অর্ডার করা। Temperature বাড়ালে আপনি নতুন কিছু চেখে দেখার ঝুঁকি নেন, আর খুব বেশি হলে যা-তা অর্ডার করে বসেন। top_p/top_k হলো আগেই ঠিক করা: মেনুর শেষের পাতার অদ্ভুত আইটেমগুলো দেখবই না।
05

Streaming vs non-streaming

Generation is sequential — tokens come one at a time. Streaming returns them as they're produced via Server-Sent Events or chunked HTTP, so the UI can render the first word while the rest is still being decoded. Non-streaming waits for the full response.

Streaming shifts perceived latency from "all-or-nothing" to "incremental". Same compute, much better UX.
এই diagram-এ non-streaming ও streaming response-এর সময়রেখা তুলনা করা হয়েছে। Non-streaming-এ পুরো text একসাথে আসে, আর streaming-এ prefill-এর পর t1, t2, t3, t4 করে tokens ক্রমে আসে; মোট সময় একই, শুধু TTFT কমে বলে অনুভূত latency কম লাগে।

Trade-offs

Use streaming when

  • Any user-facing chat / completion UI
  • Long generations where the user needs feedback that the model is "thinking"
  • Tools like Cursor, Claude.ai, ChatGPT — every product is streaming by default now

Skip streaming when

  • You're feeding output back into a pipeline (function-call result, structured extractor)
  • You need the full response for JSON parsing / validation
  • Batch jobs with no UX
# Streaming with the OpenAI SDK
stream = client.chat.completions.create(
    model="gpt-4o", messages=messages,
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content or ""
    print(delta, end="", flush=True)

# Anthropic equivalent
with client.messages.stream(model=model, messages=msgs, max_tokens=1024) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
💬Layman's versionplain English, no jargon

Without streaming, asking the AI a question is like waiting for a fax. You hit send, then wait in silence for 5–20 seconds, then the entire answer appears at once. With streaming, the answer appears word by word as the AI thinks of it — like a live chat bubble that fills in real time.

Is the AI faster? No, exactly the same. But it FEELS way faster. Reading the first word after 0.3 seconds (streaming) feels snappy. Waiting 8 seconds in silence for the whole answer (non-streaming) feels broken. Same total work, completely different vibe.

When should you turn streaming off? When the AI's answer isn't for humans to read directly. If you're piping the output into a database, or a code function, or a JSON parser, you want the whole answer validated before doing anything.

Every chat app you've used (ChatGPT, Claude, Gemini) streams by default. That's why the responses feel instant even though complex ones take 10+ seconds to compute.

The TV analogy: non-streaming = the network holds the whole show hostage and dumps it on your screen all at once. Streaming = watching it unfold live, second by second. Same show, totally different feeling.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

LLM একটি একটি করে token তৈরি করে, অর্থাৎ generation ক্রমিক। Streaming-এ token তৈরি হওয়ার সাথে সাথে Server-Sent Events বা chunked HTTP দিয়ে পাঠানো হয়, ফলে বাকি অংশ তৈরি হওয়ার আগেই UI-তে প্রথম শব্দ দেখা যায়। Non-streaming-এ পুরো উত্তর তৈরি হওয়া পর্যন্ত অপেক্ষা করতে হয়।

মূল কথা: compute একই, কিন্তু perceived latency "সব-অথবা-কিছুই-না" থেকে ক্রমবর্ধমান হয়ে যায়, ফলে UX অনেক ভালো লাগে।

  • Streaming ব্যবহার করুন: ব্যবহারকারীর সামনে থাকা chat/completion UI-তে, লম্বা generation-এ যেখানে ব্যবহারকারীর জানা দরকার মডেল কাজ করছে, এবং Cursor, Claude.ai, ChatGPT-র মতো প্রোডাক্টে।
  • Streaming বাদ দিন: যখন আউটপুট pipeline-এ ফিরে যাচ্ছে (function-call result, structured extractor), পুরো response লাগে JSON parsing/validation-এর জন্য, অথবা UX-বিহীন batch job।

OpenAI SDK-তে stream=True দিয়ে প্রতিটি chunk-এর delta পড়তে হয়; Anthropic-এ client.messages.stream(...) থেকে text_stream পড়া যায়।

ক্রিকেট ম্যাচের উপমা: Non-streaming হলো খেলা শেষ হওয়ার পর শুধু চূড়ান্ত স্কোর জানা। Streaming হলো বল বাই বল লাইভ কমেন্ট্রি শোনা। খেলার সময় একই, কিন্তু অপেক্ষাটা অনেক সহনীয় লাগে।
06

Structured outputs & JSON mode

Forcing free-form text into a typed schema unlocks LLMs as reliable components in larger pipelines. There are three progressively stricter approaches.

The three levels

JSON mode, schema-constrained decoding, and typed parsing — three guarantees, three reliability tiers.
এখানে structured output পাওয়ার তিনটি স্তর strictness বাড়ার ক্রমে দেখানো হয়েছে: JSON mode (~90% reliable), schema-constrained decoding (~99%, invalid tokens mask হয়) এবং typed parsing (Pydantic, Zod ইত্যাদি দিয়ে 100% by construction)। বাঁ থেকে ডানে গেলে নিশ্চয়তা বাড়ে।

Schema-constrained generation: how it actually works

The provider compiles the schema into a finite-state machine (or grammar) and, at each generation step, masks the logits of any token that would violate the schema. Output is guaranteed to be parseable by construction — no defensive try/except needed.[26]

# OpenAI Structured Outputs (Python)
from pydantic import BaseModel
from openai import OpenAI

class Person(BaseModel):
    name: str
    age: int
    role: str

client = OpenAI()
resp = client.beta.chat.completions.parse(
    model="gpt-4o-2024-08-09",
    messages=[{"role": "user", "content": "Extract: Ada Lovelace, 36, mathematician"}],
    response_format=Person,
)
person: Person = resp.choices[0].message.parsed
print(person.name, person.age)    # typed, valid by construction
Use structured outputs whenever you can. They turn LLM calls into well-typed function calls — no regex, no eval, no retry loops. The slight latency bump from FSM lookup is dwarfed by the saved post-validation.
📦Layman's versionplain English, no jargon

Imagine hiring a brilliant but very chatty assistant. You say "find me flights to London next Tuesday under $500" and they reply with a beautiful paragraph of text: "Certainly! I've looked up some lovely options, you might consider a British Airways departure at..." Now your software has to parse English to get the structured flight info. That's brittle and fails constantly.

Structured outputs fix this. Instead of free-form prose, the AI returns a perfectly-formatted package — like a shipping label. You said "give me {departure_city, arrival_city, date, price}" and you get exactly that, in JSON, every time. No parsing, no guessing, no surprise.

Three flavors:

• JSON mode — "respond with JSON" in the prompt. ~90% reliable, sometimes the shape drifts.
• Schema-constrained — you pass a strict shape; the AI physically cannot output anything that doesn't fit. ~99.9% reliable.
• Typed parsing — the schema-constrained output goes directly into a typed object in your code (Pydantic, Zod). 100% guaranteed.

Real impact: structured outputs turn "AI chat" into "AI as API." You can now build reliable software on top of LLMs because they return predictable data structures, not essays.

The form analogy: free-form AI is like calling a friend and asking for advice. Structured output is like giving them a form to fill out: "name, date, amount, address." The form always has the same fields in the same places — your software knows exactly where to look. Which would you rather process 10,000 of?
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

মডেলের মুক্ত-ভঙ্গির লেখাকে টাইপ-করা schema-তে বাধ্য করলে LLM বড় সিস্টেমের নির্ভরযোগ্য অংশ হয়ে ওঠে। এর তিনটি ক্রমশ কড়া স্তর আছে: JSON mode, schema-constrained decoding এবং typed parsing। প্রতিটি স্তরে নিশ্চয়তা ও নির্ভরযোগ্যতা বাড়ে।

Schema-constrained generation কীভাবে কাজ করে: প্রোভাইডার JSON schema-কে একটি finite-state machine (বা grammar)-এ রূপ দেয়, এবং প্রতিটি ধাপে যে token schema ভাঙবে তার logit mask করে দেয়। ফলে আউটপুট নির্মাণগতভাবেই parse-যোগ্য, আলাদা try/except দরকার হয় না।

Python-এ সাধারণত Pydantic মডেল (যেমন Person ক্লাসে name, age, role) বানিয়ে response_format=Person দিলে ফলাফল টাইপসহ parsed অবজেক্ট হিসেবে পাওয়া যায়। এতে regex, eval বা retry loop লাগে না।

সুতরাং সম্ভব হলেই structured outputs ব্যবহার করুন। FSM lookup-এর জন্য সামান্য latency বাড়ে, কিন্তু পরে validation-এর ঝামেলা বাঁচায় বলে সেটা সহজেই পুষিয়ে যায়।

সরকারি ফর্মের উপমা: কাউকে মুখে বললে সে নিজের মতো করে লম্বা গল্প শোনাবে। কিন্তু ব্যাংকের ফর্ম দিলে নাম, তারিখ, টাকার অঙ্ক নির্দিষ্ট ঘরেই লিখতে হয়। কেরানি তখন ঠিক জানে কোন তথ্য কোথায় পাবে। দশ হাজার ফর্ম প্রসেস করতে হলে কোনটা বেছে নেবেন?
07

Function calling & tool use

Function calling lets the model emit a structured request to invoke a tool (a function, an API, a database query) instead of free-form prose. The model doesn't execute — it decides what to call and with what arguments, and your code runs the tool and feeds the result back. This is the basis of every LLM agent.

The loop

Classic ReAct-style tool loop: model emits a tool-call JSON, your code runs it, the result is appended, repeat.
এই diagram-এ tool-calling loop দেখানো হয়েছে: User prompt ও tools schema থেকে LLM সিদ্ধান্ত নিয়ে JSON emit করে, আপনার code তা parse করে tool চালায়, আর Tool result context-এ যুক্ত হয়ে আবার LLM-এ যায়। LLM আরেকটি tool call করলে loop পুনরাবৃত্ত হয়, নইলে final answer আসে।

How it works under the hood

You supply a list of tools as JSON Schema (function name, parameters, description). The model is fine-tuned to emit a special tool_calls field instead of (or alongside) prose. Because the schema is constrained, the arguments are valid by construction. The leading paper is Toolformer (Meta, 2023),[18] with concurrent industry work on Gorilla (Berkeley, 2023) for massive API use,[17] and Anthropic's tool use docs.[27]

# Anthropic tool-use example
tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a location.",
    "input_schema": {
        "type": "object",
        "properties": {"location": {"type": "string"}},
        "required": ["location"]
    }
}]

msg = client.messages.create(
    model="claude-sonnet-4-5", tools=tools,
    messages=[{"role": "user", "content": "Weather in Dhaka?"}],
)
if msg.stop_reason == "tool_use":
    tool = msg.content[1]                    # tool-use block
    result = get_weather(**tool.input)          # your code
    # feed result back, model produces final answer
Tool design matters as much as model choice. Tool names and descriptions are inserted verbatim into the prompt. "Retrieve flights" is ambiguous; search_flights(origin, destination, depart_date, cabin_class) with documented parameters in the description yields dramatically higher correct-call rates. Iterate on tool descriptions the same way you iterate on prompts.

Modern patterns

  • Parallel tool calls: OpenAI's tool_choice: "auto" can emit multiple independent calls per turn — the model decides what can run concurrently.
  • Chain-of-Abstraction: the model writes placeholders for tool results, then fills them in after parallel execution — saves wall time on multi-step agents.[19]
  • Computer use: Sonnet 4.5 and similar can drive a desktop via screenshot + mouse/keyboard primitives — the "ultimate tool" with the agent acting as the API.

Tools turn an LLM from a brain in a jar into something that can actually do things. Without tools, the AI can only write essays. With tools, it can look up your calendar, query Wikipedia, run a database search, send an email, book a flight, or even drive your computer mouse.

How does it work? You tell the AI what tools are available, like giving a new assistant a keyring: get_weather(city), send_email(to, subject, body), search_database(query). The AI reads your question, decides which tool(s) to use, and writes a structured request like {"tool": "get_weather", "args": {"city": "Dhaka"}}. Your software runs that tool — the AI itself can't touch anything. Then it gets the result and writes the final answer.

This is the heart of every "AI agent." ChatGPT that browses the web for you? Tool. Cursor that edits your code? Tool. The AI that books your appointments? Tool.

The loop repeats: AI thinks → calls tool → reads result → calls next tool → ... → eventually writes the final reply. The smarter the AI, the more steps it can chain before getting confused.

The catch: the more tools you give, the harder the AI has to think about which one to use. Too many tools = bad choices. Good tool design (clear names, descriptions, parameter docs) matters as much as the model choice.

The sous chef analogy: the AI is a brilliant chef who can't leave the kitchen. You stock the kitchen with tools: a stove, a blender, a knife. The chef can use any of them to make dinner, but YOU had to buy them and put them there. If you stock the kitchen with 200 weird gadgets, the chef gets confused. Stock it with the 10 right tools and magic happens.

Multimodal inputs (vision, audio, PDFs)

Modern frontier models ingest more than text: images, audio, video frames, and PDF pages become tokens the transformer can attend to. The unifying trick: any modality is converted into a sequence of embedding vectors and concatenated with the text sequence.

The encoder-per-modality architecture

Each modality has a specialised encoder; a learned projection maps them into the LLM's token space, where a single transformer attends over all of them.
এখানে দেখা যায় image, audio waveform ও PDF / doc page প্রতিটি আলাদা encoder দিয়ে প্রক্রিয়া হয়। এরপর projection দিয়ে token sequence-এ রূপান্তরিত হয়ে text tokens-এর সাথে concat হয় এবং LLM core-এর joint attention সবগুলোকে একসাথে প্রক্রিয়া করে।

Modern AI isn't just text anymore. You can paste a photo of a handwritten note, a chart, an X-ray, a screenshot, a 200-page PDF, or even a 30-second voice clip — and the AI can read, describe, and reason about it like a human would.

• Images get chopped into patches; a vision model (like CLIP) describes each patch as numbers.

Embedding models & reranker models

Two specialised model types that, together with an LLM, form the standard retrieval-augmented generation (RAG) stack. Embeddings compress text into a vector such that semantically similar items land near each other. Rerankers score (query, document) pairs with cross-attention for higher precision.

The two-stage retrieval pipeline

Two-stage retrieval: cheap dense retrieval narrows millions to a few hundred, then an expensive reranker picks the best few.
এই diagram-এ দুই ধাপের retrieval দেখানো হয়েছে: ১০M docs-এর corpus থেকে bi-encoder ও ANN search দ্রুত top-K ≈ 100 candidates আনে। তারপর cross-encoder reranker (q, d) জোড়া একসাথে score করে top-K ≈ 5–10 বেছে LLM answer-এ পাঠায়।

Embedding models (bi-encoders)

Encode each side (query and document) independently into a fixed-size vector. Similarity is a dot product or cosine — O(1) per pair, allowing billion-scale ANN search with FAISS, ScaNN, or HNSW. Modern examples: OpenAI text-embedding-3-large, Cohere embed-v3, BGE-M3, E5-Mistral-7B.[21]

🔍Layman's versionplain English, no jargon

How does an AI know what's in your 10,000-doc knowledge base without reading all of it? Two specialised models: one fast-and-loose, one slow-and-precise.

Embeddings: a fancy index. Imagine every document in your library gets summarised into a list of numbers — say 1,000 numbers — that captures its meaning. Similar documents get similar numbers. Now you can search by meaning: "find me stuff related to climate insurance" finds documents that mean similar things, even if they don't share any words. The trick is: you can compare 1,000 numbers against a million other documents in milliseconds. That's how ChatGPT's "Search" can scan your entire Drive in seconds.

Rerankers: the tiebreaker. Embeddings are fast but sloppy. Sometimes the top 10 "most similar" documents aren't really the best 10. A reranker takes that shortlist and reads each one against your question, like a careful human librarian deciding which book is truly the best answer. Slow, but accurate.

The two-stage pipeline:

1. Embedding model narrows 10 million docs → 100 likely candidates (in 50ms).
2. Reranker picks the best 5 from those 100 (in another 200ms).
3. The LLM reads those 5 and writes the final answer.

This is what powers every "ChatGPT, search my docs" feature, every customer-support bot that knows your product manual, every legal-AI tool that scans case law.

The librarian analogy: embeddings are a librarian who skims the back cover of every book in milliseconds and grabs the 100 that look promising. Reranking is the senior librarian who reads those 100 covers more carefully and picks the 3 winners. The LLM is you, reading those 3 winners and writing the answer.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

RAG (retrieval-augmented generation) স্ট্যাকে LLM-এর সাথে দুই ধরনের বিশেষায়িত মডেল থাকে। Embedding model টেক্সটকে এমন একটি vector-এ সংকুচিত করে যাতে সমার্থক জিনিস কাছাকাছি পড়ে। Reranker (query, document) জোড়াকে cross-attention দিয়ে স্কোর করে বেশি নিখুঁত ফল দেয়।

Embedding (bi-encoder): query ও document আলাদা আলাদা করে নির্দিষ্ট আকারের vector বানানো হয়। সাদৃশ্য মাপা হয় dot product বা cosine দিয়ে, প্রতি জোড়ায় O(1), তাই FAISS, ScaNN বা HNSW দিয়ে বিলিয়ন-স্কেল ANN সার্চ সম্ভব। উদাহরণ: text-embedding-3-large, embed-v3, BGE-M3, E5-Mistral-7B।

Reranker (cross-encoder): query ও document জুড়ে পুরো transformer attention চালায়। অনেক নিখুঁত, কিন্তু প্রতি জোড়ায় O(n) এবং প্রায় 50–200 ms, তাই এটি দ্বিতীয় ধাপে, শীর্ষ প্রায় 100 candidate-এর ওপর ব্যবহার করা উচিত।

  • Stage 1 (bi-encoder): একবার encode করে মিলিসেকেন্ডে কোটি কোটির মধ্যে খোঁজা; recall ভালো, precision কম।
  • Stage 2 (cross-encoder): কোনো vector সংরক্ষণ নেই, টেক্সটের ওপর চলে; precision সেরা।

2025-এর আধুনিক স্ট্যাক: open-weight-এ E5-Mistral-7B-instruct বা BGE-M3 দিয়ে embed, Qwen3-Reranker বা Cohere Rerank v3 দিয়ে rerank, তারপর পছন্দের LLM দিয়ে উত্তর তৈরি। Hybrid retrieval (sparse BM25 + dense) BEIR-এ প্রায় সবসময় একা কোনোটির চেয়ে ভালো ফল দেয়।

চাকরির নিয়োগের উপমা: হাজার হাজার সিভি এলে প্রথমে একটি কম্পিউটার কিওয়ার্ড মিলিয়ে ঝটপট একশোটি বেছে নেয় (embedding)। তারপর অভিজ্ঞ HR ম্যানেজার সেই একশোটি মন দিয়ে পড়ে সেরা কয়েকজনকে ইন্টারভিউয়ের জন্য ডাকেন (reranker)। শেষে সিদ্ধান্ত নেন বস (LLM)।

Reasoning models & extended thinking

A new class of models trained to spend more compute at inference time on hard problems. Instead of answering immediately, they emit a chain of internal reasoning ("thinking tokens"), then produce a final answer. This is the most important capability shift since GPT-4.

Standard vs reasoning models

Reasoning models spend many more tokens on internal scratchpad, then answer.
এখানে Standard মডেল ও Reasoning মডেলের পার্থক্য দেখানো হয়েছে। Standard-এ user prompt থেকে সরাসরি one shot answer আসে; Reasoning মডেলে answer-এর আগে অনেক thinking tokens ("Let's think step by step…") খরচ হয়, তারপর final answer আসে।

The training trick: RL on reasoning chains

OpenAI's o1 paper showed that reinforcement learning on chain-of-thought traces dramatically improves math/physics/code reasoning — the model learns to think longer on hard problems.[13] DeepSeek-R1 replicated this with pure RL (no SFT), open-weights.[7] Anthropic's "extended thinking" exposes this as a togglable parameter.[28]

Engineering trade-offs

Costs

Reasoning models can use 5–50× more tokens per query. A "thinking budget" cap is essential — set it to your latency/cost ceiling.

Latency

TTFT is often slower (longer prefill). Streaming the thinking tokens can help UX.

Distillation

DeepSeek-R1 distilled into Qwen 1.5B–32B gives small open models with reasoning capabilities.[7]

🧠Layman's versionplain English, no jargon

Sometimes the AI needs to "think before it speaks." A regular AI answers instantly: you ask "What's 17 × 24?" and it blurts an answer (maybe wrong). A reasoning AI scribbles for 30 seconds first — breaking the problem into pieces, checking its work, considering alternatives — then gives you the answer.

Think of it like two students taking an exam.

• Standard AI = the kid who writes the first thing that pops into their head. Fast, sometimes brilliant, often sloppy.
• Reasoning AI = the kid who works through the problem on scratch paper, tries two methods, checks the answer. Slow, almost always right on hard stuff.

Where reasoning models win dramatically: math, logic, multi-step coding, planning complex tasks, scientific questions. OpenAI's o1/o3, Claude with "extended thinking," DeepSeek-R1 — these all spend 5–50× more "thinking time" than regular models, and the quality jump is real.

Where they're a waste: "Write me a thank-you email." "Summarise this article." "Translate this sentence." You'd be paying 50× more for the same answer. Use the regular model for everyday stuff.

The catch: reasoning models cost a lot. They're 5–50× more expensive per query, and they take longer. So pick them deliberately, like calling a math tutor for the hard homework but doing the easy drills yourself.

The cool part: you can limit the "thinking budget." Tell Claude "spend up to 5,000 tokens thinking, then answer." For easy questions it finishes early. For hard ones, it uses the full budget. You control the speed/quality dial.

The patient friend analogy: regular AI = your friend who blurts answers quickly. Reasoning AI = your friend who pauses, says "let me think about this," scribbles for a minute, then gives you a careful answer. You go to the patient friend for the important questions; the quick friend is fine for casual stuff.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Reasoning model এমন একটি নতুন শ্রেণির মডেল যা কঠিন সমস্যায় inference-এর সময় বেশি compute খরচ করে। সরাসরি উত্তর না দিয়ে প্রথমে অভ্যন্তরীণ chain of reasoning ("thinking tokens") লেখে, তারপর চূড়ান্ত উত্তর দেয়। GPT-4-এর পর এটিকেই সবচেয়ে গুরুত্বপূর্ণ সক্ষমতার পরিবর্তন বলা হচ্ছে।

প্রশিক্ষণের কৌশল: chain-of-thought-এর ওপর reinforcement learning (RL) প্রয়োগ করলে math, physics ও code reasoning অনেক ভালো হয়, কারণ মডেল কঠিন সমস্যায় বেশি ভাবতে শেখে। OpenAI-এর o1 এটি দেখিয়েছে; DeepSeek-R1 শুধু RL দিয়ে (SFT ছাড়া) open-weight আকারে তা পুনরায় করেছে; আর Anthropic-এ extended thinking একটি চালু/বন্ধ করার parameter। Process reward model-ও step-level পুরস্কার দিয়ে math-এ outcome-only supervision-কে ছাড়িয়ে গেছে।

  • কখন কাজে লাগে: math/physics/proof, কঠিন multi-step কোডিং agent, planning ও tool orchestration।
  • কখন অপচয়: chat, summarisation, extraction, সহজ Q&A ও classification; এসবে ছোট/দ্রুত মডেলই ভালো।

Engineering trade-off: প্রতি query-তে 5–50 গুণ বেশি token লাগতে পারে, তাই latency/খরচের সীমা অনুযায়ী budget_tokens (thinking budget) সীমা দেওয়া জরুরি। Prefill লম্বা হওয়ায় TTFT প্রায়ই ধীর হয়; thinking token stream করলে UX ভালো হয়। Distillation-এর মাধ্যমে R1-এর ক্ষমতা Qwen 1.5B–32B-এর মতো ছোট open মডেলে আনা গেছে।

অভ্যাসবশে reasoning মডেল নেবেন না। ব্যবহার করুন যখন (১) কাজটি math/code/agentic, (২) সাধারণ মডেল আপনার benchmark-এ আর এগোচ্ছে না, এবং (৩) latency সহ্য করা যায়। বেশিরভাগ chat/extraction/RAG-এ সাধারণ মডেল ও ভালো prompting-ই যথেষ্ট।

গণিত পরীক্ষার উপমা: সহজ অঙ্ক পরীক্ষার হলে অনেকে মুখে মুখে করে ফেলে। কিন্তু কঠিন জ্যামিতি বা বীজগণিতে ভালো ছাত্র খাতায় ধাপে ধাপে লেখে, নিজের উত্তর মিলিয়ে দেখে। এতে সময় বেশি লাগে, কিন্তু উত্তর ঠিক হওয়ার সম্ভাবনা বাড়ে। সব প্রশ্নে এত সময় দেওয়াও বোকামি।
