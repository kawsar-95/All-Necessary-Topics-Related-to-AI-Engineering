01

API-based vs self-hosted inference

Renting inference from an API and running open-weight models on your own GPUs are different businesses: one bills per token, the other per GPU-hour. The right answer depends on volume, utilisation, data rules and how much operations work you can absorb.

Two cost structures

An API bills per input and output token: you pay nothing while idle and the provider absorbs capacity planning. Self-hosting bills per GPU-hour whether or not requests arrive, so your cost per token depends almost entirely on utilisation.

DimensionHosted APISelf-hosted open weights
Time to first requestminutesdays to weeks (GPUs, serving stack, monitoring)
Cost modelper token, zero when idleper GPU-hour, paid even when idle
Model choiceprovider's catalogue, including closed frontier modelsany open-weight model you can fit
Data controlprovider's retention and region termsstays inside your network
Customisationprompts, some fine-tuningfine-tunes, LoRA adapters, custom decoding
Scaling and on-callthe provider's problemyour problem: autoscaling, upgrades, incidents

A break-even sketch

Self-hosted cost per million output tokens ≈ GPU price per hour ÷ (sustained tokens per second × 3,600 ÷ 1,000,000). With illustrative numbers — a $2.50/hour GPU sustaining 1,500 tokens/s across all concurrent requests — that is 5.4M tokens per hour, about $0.46 per million. At 20% utilisation the same GPU costs about $2.31 per million, five times more. Use your own measured throughput and current prices; the formula matters more than these numbers.

def self_hosted_cost_per_million(gpu_usd_per_hour, tokens_per_s, utilisation):
      tokens_per_hour = tokens_per_s * 3600 * utilisation
      return gpu_usd_per_hour / (tokens_per_hour / 1_000_000)
  
  print(round(self_hosted_cost_per_million(2.50, 1500, 1.0), 2))   # 0.46
  print(round(self_hosted_cost_per_million(2.50, 1500, 0.2), 2))   # 2.31

The common hybrid

Most teams end up hybrid: frontier APIs for hard, low-volume reasoning, and a small open model — self-hosted or provider-hosted — for high-volume narrow tasks such as classification, extraction or routing. Because vLLM, SGLang, Ollama and most hosted providers expose OpenAI-compatible endpoints, moving between them is often just a base-URL change [1][2].

Utilisation is the hidden variable. A self-hosted GPU that sits idle overnight doubles your effective cost per token. Measure the real shape of your traffic before buying capacity.
🖨️Layman's versionplain English, no jargon

There are two ways to get answers from an AI model: pay per use, or own the machine. Paying per use is simple — no setup, no cost when you're not using it. Running the model yourself means buying or renting powerful computers and keeping them running; each answer becomes cheap, but only while the machines stay busy.

The trap is an idle machine. If your own computers sit unused half the day, every answer they do produce costs twice as much. Owning only pays off when demand is steady and heavy.

Most companies mix both: they rent the cleverest, most expensive model for hard questions, and run a small model themselves for repetitive, high-volume jobs.

The print shop analogy: a print shop charges per page and you can walk in any time. A printing press of your own costs a fortune up front and needs a skilled operator, but if you print a newspaper every day, each copy is far cheaper. Print a few flyers a month and the press is just an expensive dust-collector.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

API-তে খরচ হয় প্রতি token হিসেবে, আর নিজের GPU-তে মডেল চালালে খরচ হয় প্রতি GPU-ঘণ্টায় — request আসুক বা না আসুক। তাই self-hosting-এ প্রতি token-এর খরচ প্রায় পুরোটাই নির্ভর করে utilisation-এর ওপর।

সূত্র: প্রতি মিলিয়ন token-এর খরচ ≈ GPU-এর ঘণ্টাপ্রতি দাম ÷ (সেকেন্ডে token × ৩৬০০ ÷ ১০,০০,০০০)। কাল্পনিক উদাহরণ: ঘণ্টায় $2.50-এর GPU সেকেন্ডে ১৫০০ token দিলে প্রতি মিলিয়নে প্রায় $0.46; কিন্তু মাত্র ২০% সময় ব্যস্ত থাকলে খরচ প্রায় পাঁচগুণ।

বেশিরভাগ দল hybrid পথ নেয়: কঠিন কাজে frontier API, আর বেশি volume-এর সরল কাজে (classification, extraction) ছোট open model। vLLM, SGLang, Ollama-র মতো server OpenAI-compatible endpoint দেয়, তাই বদলানো সহজ [1]।

ছাপাখানার উপমা: দোকানে ছাপালে প্রতি পাতার দাম দিতে হয়, কোনো প্রস্তুতি লাগে না। নিজের ছাপাখানা কিনলে শুরুতে বড় খরচ আর দক্ষ লোক লাগে, কিন্তু প্রতিদিন পত্রিকা ছাপলে প্রতি কপি অনেক সস্তা। মাসে কয়েকটা লিফলেট ছাপলে সেই মেশিন শুধু ধুলো জমায়।

Inference servers: vLLM, TGI, SGLang, Ollama, llama.cpp

An inference server loads model weights into accelerator memory, schedules many concurrent requests, manages the KV cache and streams tokens back. The choice shapes your throughput, hardware options and operational burden.

The landscape

ServerCore ideaBest for
vLLMPagedAttention KV-cache management plus continuous batching; 2–4× higher throughput than earlier systems at the same latency [3]high-throughput GPU serving with an OpenAI-compatible API [1]
SGLangRadixAttention for automatic KV reuse across calls, plus a frontend language for structured programs; up to 6.4× higher throughput reported [4]agentic and multi-call workloads, constrained JSON decoding
TGIHugging Face's Rust/Python serverexisting deployments — it is now in maintenance mode [5]
Ollamaone-command local runner with a simple REST API [2]laptops, dev boxes, small internal services
llama.cppC/C++ inference with CPU, GPU and mixed offload; GGUF model files [6]edge devices, CPUs, Apple silicon, minimal dependencies
TensorRT-LLMNVIDIA's compiled, kernel-optimised runtime [7]maximum throughput from a fixed NVIDIA fleet
TGI is in maintenance mode. Hugging Face now accepts only minor bug fixes and documentation changes for text-generation-inference [5]. For new deployments, start with vLLM or SGLang.

Starting each one

# vLLM: OpenAI-compatible server on port 8000
  vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.90 --enable-prefix-caching
  
  # SGLang
  python -m sglang.launch_server --model-path Qwen/Qwen2.5-7B-Instruct --port 30000
  
  # llama.cpp: a 4-bit GGUF file, all layers offloaded to the GPU if there is one
  llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf -c 8192 -ngl 99 --port 8080
  
  # Ollama
  ollama run llama3.2

Calling any of them the same way

from openai import OpenAI
  
  # The standard client, pointed at a self-hosted server instead of a cloud API.
  client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused-locally")
  reply = client.chat.completions.create(
      model="Qwen/Qwen2.5-7B-Instruct",
      messages=[{"role": "user", "content": "Classify: 'my parcel never arrived'"}],
      max_tokens=20,
  )
  print(reply.choices[0].message.content)

How to choose

  • Many concurrent users on datacentre GPUs → vLLM or SGLang.
  • Agents that resend long shared prefixes → SGLang's radix cache or vLLM's prefix caching.
  • A laptop, a CPU-only server or Apple silicon → llama.cpp or Ollama.
  • Maximum tokens per dollar on NVIDIA hardware, with engineers to spare → TensorRT-LLM.
☕Layman's versionplain English, no jargon

An inference server is the engine that actually runs an AI model. It loads the model into the graphics card's memory, juggles many people's questions at once, and sends the answers back word by word.

Different engines suit different scales. Some are built for a data centre serving thousands of people at once. Others run on one laptop with a single command. One popular older engine now only gets small fixes, so new projects usually pick a different one.

The nice part: most of them accept requests in the same format as the big cloud AI services, so an app can switch engines by changing a single address.

The coffee machine analogy: a busy café needs a big commercial espresso machine that pulls dozens of shots at once and never cools down. A student needs a cheap stovetop pot that works anywhere. Both make coffee — but pick the wrong one for your situation and you get either wasted money or a queue out the door.

03

Quantization: GGUF, AWQ, GPTQ, INT4/INT8

Quantization stores weights — and sometimes activations — in fewer bits. Smaller weights let a model fit on cheaper hardware, and because generating tokens is limited by memory bandwidth, they usually make it faster too.

Why fewer bits make inference faster

Weights dominate memory: bytes ≈ parameters × bits ÷ 8. An 8-billion-parameter model needs about 16 GB in 16-bit, 8 GB in 8-bit and roughly 4–5 GB at 4-bit (formats also store scales and metadata). Generating each token reads essentially all the weights, so decoding is usually limited by memory bandwidth rather than arithmetic — fewer bytes per weight means more tokens per second.

Model sizeFP16 / BF16INT8 / FP8about 4-bit
8B parameters~16 GB~8 GB~4–5 GB
70B parameters~140 GB (two 80 GB GPUs)~70 GB~35–40 GB (one 80 GB GPU, leaving room for KV cache)

The main methods

  • LLM.int8() keeps rare outlier dimensions in 16-bit and multiplies the rest — more than 99.9% of values — in 8-bit, halving inference memory without degradation even at 175B parameters [8].
  • SmoothQuant migrates activation outliers into the weights so both can be INT8 (W8A8), reporting up to 1.56× speedup and 2× memory reduction [9].
  • GPTQ uses approximate second-order information to quantize weights to 3–4 bits in one shot — a 175B model in about four GPU-hours with negligible accuracy loss [10].
  • AWQ shows that protecting about 1% of salient weights, chosen by activation magnitude, greatly reduces 4-bit error [11].
  • FP8 defines two 8-bit floating-point encodings (E4M3 and E5M2) that recent accelerators support natively [12].
  • NF4, introduced with QLoRA, is a 4-bit data type for normally distributed weights, used mainly for memory-efficient fine-tuning [13].
  • GGUF is not an algorithm but llama.cpp's single-file model format; it packages weights in many quantization types such as Q4_K_M or Q8_0, together with metadata [14][6].

Doing it

# llama.cpp: turn a 16-bit GGUF into a 4-bit K-quant
  llama-quantize model-f16.gguf model-q4_k_m.gguf Q4_K_M
  
  # vLLM: serve a checkpoint that was already quantized with AWQ
  vllm serve <org>/<model>-AWQ --quantization awq
Quantization quality is task-dependent. Average benchmark scores can hide regressions in long-context retrieval, maths, code or non-English text. Rerun your own eval suite (chapter 05) on the quantized model before switching traffic.
🗜️Layman's versionplain English, no jargon

Quantization is compression for AI models. A model is billions of numbers. Storing each one with a little less precision makes the whole thing two to four times smaller, so it fits on a cheaper chip — or even a laptop or phone — and usually answers faster.

The catch is that heavy squeezing shows. Gentle compression is almost invisible; aggressive compression can make the model slip on tricky tasks like maths or long documents. So you always test the compressed version on your own real tasks before trusting it.

The photo compression analogy: a RAW photo straight from a camera is huge. Saved as a high-quality JPEG it's a fraction of the size and looks identical on your phone. Push the compression too far and blocky smudges appear — usually in exactly the fine detail you cared about.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Quantization মানে weight কম bit-এ সংরক্ষণ করা। মেমরি ≈ parameter × bit ÷ ৮; যেমন ৮B মডেল 16-bit-এ প্রায় ১৬ GB, 4-bit-এ প্রায় ৪–৫ GB। প্রতিটি token তৈরিতে প্রায় সব weight মেমরি থেকে পড়তে হয়, তাই কম byte মানে সাধারণত দ্রুত উত্তর।

প্রধান পদ্ধতি:

  • LLM.int8(): outlier মান 16-bit-এ রেখে বাকিগুলো 8-bit-এ; মেমরি অর্ধেক [8]।
  • SmoothQuant: weight ও activation দুটোই INT8 [9]।
  • GPTQ: ৩–৪ bit-এ one-shot quantization [10]।
  • AWQ: গুরুত্বপূর্ণ প্রায় ১% weight রক্ষা করে 4-bit-এর ত্রুটি কমায় [11]।
  • GGUF: llama.cpp-এর single-file ফরম্যাট, যেমন Q4_K_M [14]।

সতর্কতা: গড় benchmark ভালো দেখালেও গণিত, কোড বা দীর্ঘ context-এ মান কমে যেতে পারে — নিজের eval দিয়ে যাচাই করুন।

ছবি compress করার উপমা: ক্যামেরার RAW ছবি বিশাল; ভালো মানের JPEG করলে আকার অনেক কমে, ফোনে দেখতে একই রকম লাগে। বেশি compress করলে ছবিতে ঘোলাটে দাগ পড়ে — ঠিক সেই সূক্ষ্ম জায়গায়, যেটা আপনার সবচেয়ে দরকার ছিল।
04

KV cache, prefix caching, speculative decoding

Three techniques that avoid redundant work: the KV cache stops recomputing the past, prefix caching shares that work across requests, and speculative decoding lets a cheap model draft tokens that the big model checks in bulk.

The KV cache and its size

During generation, attention needs the keys and values of every previous token. Caching them turns each new token into a small incremental computation — but the cache lives in GPU memory and grows with every token of every concurrent sequence:

KV bytes per token = 2 (K and V) × layers × KV heads × head dimension × bytes per value

For a Llama-3.1-8B-style model (32 layers, 8 KV heads, head dimension 128, 16-bit values) that is 2 × 32 × 8 × 128 × 2 = 131,072 bytes, about 128 KiB per token — roughly 1 GiB for a single 8K-token conversation. Multi-query attention [15] and grouped-query attention [16] shrink it by sharing key/value heads across query heads, which is why most current models use GQA.

PagedAttention

Naive servers reserve one contiguous buffer per request, sized for the maximum length, and waste most of it. vLLM's PagedAttention stores the KV cache in fixed-size blocks, like virtual-memory pages, giving near-zero waste and letting requests share blocks [3].

Prefix caching

Many requests begin with identical tokens: a system prompt, tool definitions, a long document. Automatic prefix caching keeps those KV blocks so a new request skips recomputing the shared part [17]; SGLang organises the same reuse as a radix tree [4]. Hosted APIs expose the idea as prompt caching: Anthropic uses cache_control breakpoints with 5-minute or 1-hour lifetimes [18], and OpenAI applies caching automatically to repeated prompt prefixes [19]. Either way the rule is the same: stable content first, variable content last.

Speculative decoding

A small draft model proposes several tokens; the large target model checks all of them in one forward pass and keeps the longest accepted prefix. Because acceptance uses a rejection-sampling rule, the output distribution is exactly the target model's [20][21]. Reported speedups: 2–3× on T5-XXL with identical outputs [20], 2–2.5× on the 70B Chinchilla model [21], more than 2.2× for Medusa's extra decoding heads [22], and 2.7–3.5× lower latency for EAGLE on LLaMA2-Chat 70B [23].

Speculative decoding: the draft guesses five tokens, the target verifies them together, keeps the agreed prefix and supplies the first corrected token. When drafts are usually right, each expensive pass yields several tokens.
Speculative decoding: ছোট মডেল পাঁচটি token আন্দাজ করে, বড় মডেল একসাথে যাচাই করে মিলে যাওয়া অংশ রাখে এবং প্রথম ভুলটির জায়গায় নিজের token দেয়।

Measure on your traffic

Speculative decoding pays off when the draft is usually right — templated replies, code, structured data — and helps most at small batch sizes, where the GPU has spare compute. Prefix caching pays off only if prompts really share long prefixes. Measure both on production-shaped traffic before relying on them.

🪚Layman's versionplain English, no jargon

These are three tricks to stop the AI doing the same work twice.

First, it keeps notes. While writing an answer, the AI keeps a running memo of everything it has read so far, so each new word doesn't require re-reading the whole conversation. Those notes take memory, which is why very long conversations are expensive.

Second, it shares notes between customers. If a thousand people's requests all begin with the same long instructions, the system works through that part once and reuses it.

Third, a fast helper guesses ahead. A small, quick model guesses the next few words; the big model checks the whole guess in one go and keeps the correct part. When the guesses are good, answers arrive two or three times faster — and the final text is exactly what the big model would have written anyway.

The carpentry workshop analogy: an apprentice cuts five pieces ahead from the plan while the master carpenter inspects them all in a single pass. Every piece that matches the plan is kept; at the first bad cut, the master makes that piece properly and the apprentice starts again from there. The furniture comes out exactly as the master would have made it — just sooner.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

KV cache: আগের token-গুলোর key ও value জমা রাখে, যাতে প্রতিটি নতুন token-এ পুরো ইতিহাস আবার হিসাব করতে না হয়। আকার = ২ × layer × KV head × head dimension × byte; ৮B-ধরনের মডেলে প্রতি token-এ প্রায় ১২৮ KiB। GQA এটি কমায় [16]।

PagedAttention KV cache-কে page-এর মতো ছোট block-এ রাখে, ফলে মেমরির অপচয় প্রায় শূন্য [3]।

Prefix caching: অনেক request-এর শুরু একই হলে (system prompt, টুল definition) সেই অংশ একবার হিসাব করে বারবার ব্যবহার করা হয় [17]। নিয়ম: স্থির অংশ prompt-এর শুরুতে, পরিবর্তনশীল অংশ শেষে।

Speculative decoding: ছোট draft মডেল কয়েকটি token আন্দাজ করে, বড় মডেল এক pass-এ সবগুলো যাচাই করে; ফলাফলের distribution বদলায় না, অথচ গতি ২–৩ গুণ পর্যন্ত বাড়ে [20][23]।

কাঠমিস্ত্রির কারখানার উপমা: শিক্ষানবিশ নকশা দেখে আগেভাগে পাঁচটি টুকরো কেটে রাখে, ওস্তাদ একবারে সবগুলো পরীক্ষা করেন। নকশার সাথে মেলা টুকরো রাখা হয়; প্রথম ভুল টুকরোটি ওস্তাদ নিজে কাটেন। আসবাব ঠিক ওস্তাদের মতোই হয়, শুধু আগে শেষ হয়।
05

Continuous batching and throughput tuning

GPUs are efficient only when they process many sequences at once. Continuous batching keeps the batch full by admitting and retiring requests at every decoding step instead of waiting for a whole batch to finish.

Static versus continuous batching

With static batching a batch starts together and finishes together, so short answers wait for the longest one and new requests queue outside. Orca introduced iteration-level scheduling: the scheduler decides at every decoding iteration, so finished sequences leave and waiting ones join immediately [24]. vLLM combined continuous batching with PagedAttention [3], and the technique is now standard in every serious server.

Static batching leaves slots idle while the longest request finishes and makes new requests queue. Iteration-level (continuous) batching refills a slot the moment its sequence ends.
Static batching-এ দীর্ঘতম request শেষ না হওয়া পর্যন্ত slot খালি পড়ে থাকে; continuous batching-এ কোনো sequence শেষ হলেই সেই slot-এ নতুন request ঢোকে।

Prefill and decode are different workloads

Processing the prompt (prefill) is compute-bound: many tokens in parallel. Generating (decode) is memory-bandwidth-bound: one token per sequence per step. Mixing a long prefill into a running batch stalls everyone's decode. Two fixes from recent research:

  • Chunked prefill splits long prompts into pieces interleaved with decode steps; Sarathi-Serve reports 2.6× higher serving capacity for Mistral-7B on a single A100 compared with vLLM [25].
  • Disaggregation runs prefill and decode on separate GPU pools; DistServe reports serving 7.4× more requests or meeting 12.6× tighter latency targets [26].

The knobs that matter

--max-num-batched-tokenstokens processed per scheduler stepprefill speed versus smooth decoding

Tune with a load test, not a guess

Replay realistic traffic — prompt- and output-length distributions plus arrival rate — and sweep one knob at a time while recording throughput, p95 time to first token and p95 time per output token. Stop raising concurrency when your latency target breaks; the point just before that is your real capacity per GPU.

🚌Layman's versionplain English, no jargon

A GPU is like a vehicle that's only efficient when it's full. Older systems loaded a group of questions, answered them all, and only then let the next group on — so quick questions waited for slow ones, and newcomers waited outside.

Continuous batching lets people get on and off at every step. The moment one answer is finished, a waiting question takes its seat. The machine stays full and many more people get served per hour.

There is a balance to strike: pack in too many at once and each person's answer comes out more slowly. Engineers test with realistic traffic to find the sweet spot.

The city bus analogy: a tour coach won't let anyone new board until every passenger has finished the whole tour. A city bus lets people on and off at every stop, so its seats are almost always taken. Same vehicle, far more passengers carried per day.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Static batching-এ একটি batch একসাথে শুরু হয়ে একসাথে শেষ হয় — ছোট উত্তরও দীর্ঘটির জন্য অপেক্ষা করে। Continuous batching (Orca-র iteration-level scheduling) প্রতিটি decoding ধাপে শেষ হওয়া request সরিয়ে নতুন request ঢোকায়, ফলে GPU সবসময় ভরা থাকে [24][3]।

Prefill (prompt প্রক্রিয়া) compute-নির্ভর, আর decode (token তৈরি) মেমরি-bandwidth-নির্ভর। দীর্ঘ prefill চলমান decode আটকে দেয়; সমাধান chunked prefill [25] অথবা prefill ও decode আলাদা GPU-তে চালানো [26]।

গুরুত্বপূর্ণ knob: --max-num-seqs, --max-num-batched-tokens, --gpu-memory-utilization, --max-model-len। অনুমানে নয়, বাস্তব traffic দিয়ে load test করে ঠিক করুন — latency লক্ষ্য ভাঙার ঠিক আগের বিন্দুই আপনার প্রতি-GPU সক্ষমতা।

শহরের বাসের উপমা: ট্যুর কোচ পুরো ভ্রমণ শেষ না হওয়া পর্যন্ত নতুন কাউকে তোলে না। শহরের বাস প্রতিটি স্টপে যাত্রী নামায় ও তোলে, তাই আসন প্রায় সবসময় ভরা থাকে — একই গাড়িতে দিনে অনেক বেশি মানুষ যাতায়াত করে।
06

Latency vs throughput trade-offs (TTFT, TPS)

Users feel latency; the finance team feels throughput. You need precise names for both, a latency target for each product surface, and the discipline to maximise throughput only within that target.

The vocabulary

MetricDefinitionMostly driven by
TTFT (time to first token)request sent → first token receivedqueueing, prompt length (prefill), network
ITL / TPOTtime between output tokens for one usermodel size, batch size, memory bandwidth
Output TPS per userabout 1 ÷ TPOTas above
End-to-end latencyabout TTFT + (output tokens − 1) × TPOTboth, plus answer length
System throughputoutput tokens per second across all usersbatching, utilisation
Goodputrequests per second that meet the latency targetsscheduling under SLOs

NVIDIA's benchmarking guide defines these metrics carefully and is a useful reference for measurement methodology [27]; DistServe frames serving quality as goodput under TTFT and TPOT targets [26].

The trade-off curve

Bigger batches raise total throughput but slow each user's token stream, and queues lengthen TTFT. There is no single best operating point — there is a best point for a given latency target. A chat interface might aim for p95 TTFT under about a second with smooth streaming; an overnight batch job cares only about tokens per dollar. (These are illustrative targets — set yours from user research and A/B tests.)

def e2e_seconds(ttft_s, tpot_s, output_tokens):
      return ttft_s + (output_tokens - 1) * tpot_s
  
  # 0.4 s to first token, 25 ms per token, a 300-token answer
  print(e2e_seconds(0.4, 0.025, 300))   # 7.875 seconds end to end

Report percentiles, not averages

Averages hide the tail that users complain about. Track p50, p95 and p99 for TTFT and TPOT separately, bucketed by prompt length — a 50,000-token prompt has a very different TTFT from a 500-token one.

Streaming changes perception. With streaming, perceived latency is roughly TTFT; without it, users wait for the full end-to-end time. For long answers, a fast TTFT and smooth streaming matter more than raw tokens per second.
🛂Layman's versionplain English, no jargon

There are two different questions: how fast is it for me, and how many people can it serve? "Time to first word" is how long you stare at a blank screen. "Words per second" is how quickly the answer then flows. "Throughput" is how many answers the whole system produces per hour, for everyone combined.

These pull against each other. Squeezing more people onto the same machine gets more total work done but makes each person's answer a little slower. The trick is to decide what "fast enough" means for each feature, then serve as many people as possible without breaking that promise.

And look at the slow cases, not the average. If one answer in twenty takes ten seconds, people notice — even when the average looks fine.

The airport security analogy: throughput is how many passengers the checkpoint clears per hour; latency is how long you stand in the queue. Pushing more people through each scanner raises throughput but lengthens your wait. Airports pick a target — "most people through in under fifteen minutes" — and staff the lanes to meet it.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত
  • TTFT (প্রথম token আসতে সময়): ফাঁকা স্ক্রিনে কতক্ষণ তাকিয়ে থাকতে হয়।
  • TPOT/ITL: দুটি token-এর মাঝের সময়; TPS = প্রতি সেকেন্ডে token।
  • মোট সময় ≈ TTFT + (output token − ১) × TPOT।
  • Throughput: সব ব্যবহারকারী মিলে সেকেন্ডে মোট token। Goodput: latency লক্ষ্য মেনে সেকেন্ডে কতটি request সফল হলো [26][27]।

বড় batch মানে বেশি throughput, কিন্তু প্রত্যেক ব্যবহারকারীর গতি কম। তাই প্রতিটি feature-এর জন্য latency লক্ষ্য ঠিক করুন, তারপর সেই সীমার ভেতরে throughput সর্বোচ্চ করুন। গড় নয়, p95/p99 দেখুন, আর prompt-এর দৈর্ঘ্য অনুযায়ী ভাগ করে মাপুন। Streaming থাকলে ব্যবহারকারীর অনুভূত দেরি মূলত TTFT।

বিমানবন্দরের নিরাপত্তা লাইনের উপমা: throughput হলো ঘণ্টায় কতজন যাত্রী পার হলেন; latency হলো আপনি কতক্ষণ লাইনে দাঁড়ালেন। প্রতিটি স্ক্যানারে বেশি মানুষ পাঠালে throughput বাড়ে, কিন্তু আপনার অপেক্ষাও বাড়ে।
07

GPU economics, edge inference, on-device models

The cost of a token is set by memory bandwidth, utilisation and hardware price. Small models running on the user's own device change the equation: near-zero marginal cost and full privacy, in exchange for capability.

A roofline mental model

At batch size 1, each new token requires reading roughly all model weights from memory, so an upper bound is tokens per second ≈ memory bandwidth ÷ weight bytes. An accelerator with about 3 TB/s of memory bandwidth serving a 16 GB model tops out near 190 tokens/s for a single stream, before any overhead. Batching amortises those weight reads across many sequences, which is why throughput rises with batch size until compute or KV-cache memory runs out.

What moves cost per token

  • Utilisation — idle GPUs are the biggest waste (see the first section of this chapter).
  • Batching and caching — continuous batching and prefix reuse raise tokens per GPU-hour.
  • Precision — FP8 or 4-bit weights move half or a quarter of the bytes per token.
  • Model size — the cheapest token comes from the smallest model that passes your evals.
  • Purchase model — on-demand, reserved and spot capacity carry very different hourly prices; spot suits batch work that tolerates interruption.

Edge and on-device inference

Small models now run on phones and laptops. Microsoft's phi-3-mini — 3.8 billion parameters trained on 3.3 trillion tokens — scored 69% on MMLU while being small enough to deploy on a phone [28]. llama.cpp [6] and Apple's MLX framework [29] are common runtimes on consumer hardware.

🧮Layman's versionplain English, no jargon

The price of an AI answer comes down to how much computer time it uses. Big models on expensive chips cost more per answer; the same chip handling many answers at once costs less per answer; and a chip sitting idle still costs money.

Small models can now run on your own phone or laptop. They aren't as clever as the giant ones in the cloud, but they answer instantly, work without internet, keep your data on your device, and cost nothing extra each time you use them.

Smart products use both: the small local model handles quick everyday tasks and hands the hard questions to the big cloud model.

The pocket calculator analogy: a calculator in your pocket answers instantly, works anywhere and costs nothing per sum — but it can't do your tax return. For that you call an accountant, who is slower and charges by the hour. You use the calculator for most sums and save the accountant for the hard cases.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Batch size ১ হলে প্রতিটি token-এর জন্য প্রায় সব weight মেমরি থেকে পড়তে হয়, তাই সর্বোচ্চ গতি ≈ memory bandwidth ÷ weight-এর আকার। প্রায় ৩ TB/s bandwidth-এ ১৬ GB মডেল একটি stream-এ সর্বোচ্চ প্রায় ১৯০ token/s দেয়; batching এই পড়ার খরচ অনেক request-এর মধ্যে ভাগ করে দেয়।

প্রতি token-এর খরচ কমানোর উপায়: GPU ব্যস্ত রাখা (utilisation), batching ও caching, কম precision (FP8 বা 4-bit), সবচেয়ে ছোট উপযুক্ত মডেল, আর batch কাজে সস্তা spot capacity।

On-device: phi-3-mini (৩.৮B parameter) MMLU-তে ৬৯% পেয়েছে এবং ফোনে চালানো যায় [28]। llama.cpp ও Apple MLX সাধারণ runtime [29]। সুবিধা: প্রায় শূন্য প্রান্তিক খরচ, offline চলে, পূর্ণ গোপনীয়তা; সীমাবদ্ধতা: ক্ষমতা, মেমরি, ব্যাটারি ও তাপ।

পকেট ক্যালকুলেটরের উপমা: পকেটের ক্যালকুলেটর সঙ্গে সঙ্গে উত্তর দেয়, যেকোনো জায়গায় চলে, প্রতিবার কোনো খরচ নেই — কিন্তু আয়কর রিটার্ন বানাতে পারে না। সেজন্য হিসাবরক্ষকের কাছে যেতে হয়, যিনি ধীর এবং ঘণ্টা ধরে টাকা নেন।

Between "call a frontier lab's API" and "run your own GPUs" sits a market of providers that host open-weight — and some closed — models for you. They differ in hardware, catalogue, latency, pricing and compliance features.

Same client, different base URL

Most of these expose OpenAI-compatible endpoints, so switching is often configuration rather than code:

import os
  from openai import OpenAI
  
  PROVIDERS = {
      "groq": ("https://api.groq.com/openai/v1", "GROQ_API_KEY"),
      "cerebras": ("https://api.cerebras.ai/v1", "CEREBRAS_API_KEY"),
      "local-vllm": ("http://localhost:8000/v1", None),
  }
  
  def client_for(name: str) -> OpenAI:
      base_url, key_var = PROVIDERS[name]
      return OpenAI(base_url=base_url, api_key=os.environ[key_var] if key_var else "unused")

Choosing: a checklist

  • Model availability — the exact model and version, its context length, and whether it is quantized.
  • Latency — measure p50 and p95 TTFT and output tokens per second from your region with your prompts.
  • Price — per-token rates, batch discounts, and minimums for dedicated capacity.
  • Limits — rate limits, concurrency caps and burst behaviour.
  • Data terms — retention, training use, regions and compliance certifications.
  • Escape hatches — OpenAI compatibility, and a second provider as a fallback (chapter 09).
"The same model" is not always the same. Providers may serve different quantizations, context limits or decoding defaults under the same model name. Run your eval suite against each provider before routing production traffic to it.
✈️Layman's versionplain English, no jargon

Inference providers are companies that run AI models for you on their own powerful hardware. You send a question over the internet and pay for what you use, without buying a single chip.

They compete on different things: some have special chips that answer remarkably fast, some offer a huge menu of models, some live inside a big cloud with its security and paperwork, and some pass your request to whichever company is best at that moment.

Because most accept the same style of request, switching between them is easy — but the "same" model can behave slightly differently at each one, so test before you switch.

The airline analogy: many airlines fly the same route. Some are faster, some cheaper, some offer more destinations, some come with your company's travel account and loyalty points. You book the one that fits this trip — and it pays to know a backup carrier for when your flight is cancelled.
🇧🇩বাংলা ব্যাখ্যাসহজ ভাষায় বিস্তারিত

Inference provider হলো এমন প্রতিষ্ঠান যারা নিজেদের hardware-এ open-weight (কখনো closed) মডেল চালিয়ে API হিসেবে দেয়।

  • Together AI ও Fireworks AI: অনেক open মডেল, fine-tuning ও dedicated endpoint [30][31]।
  • Groq: নিজস্ব LPU hardware, খুব কম latency [32]।
  • Cerebras: wafer-scale চিপ, খুব দ্রুত output [33]।
  • Replicate: ছবি, অডিও ও ভিডিওসহ নানা মডেল API-তে চালানো যায় [34]।
  • Amazon Bedrock: AWS-এর ভেতরে IAM, VPC ও compliance-সহ একাধিক কোম্পানির মডেল [35]।

বেশিরভাগই OpenAI-compatible, তাই শুধু base URL বদলালেই চলে। তবে একই নামের মডেল ভিন্ন provider-এ ভিন্ন quantization বা সেটিং-এ চলতে পারে — production-এ পাঠানোর আগে নিজের eval চালান।

এয়ারলাইনের উপমা: একই রুটে অনেক এয়ারলাইন ওড়ে — কেউ দ্রুত, কেউ সস্তা, কেউ বেশি গন্তব্যে যায়। এই যাত্রার জন্য যেটি মানানসই সেটি বুক করুন, আর ফ্লাইট বাতিল হলে একটি বিকল্প এয়ারলাইন জেনে রাখুন।
